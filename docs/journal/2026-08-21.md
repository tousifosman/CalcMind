# 2026-08-21

## `Create link` keypad button now follows Select group's §8.7 result carve-out

### Session log

1. User feedback on a live build: selecting a chain group whose last member is a
   result already keeps the operator column enabled for §8.7 continuation (2026-08-09),
   but `Create link` stayed disabled the whole time a group was selected — so linking a
   group's result required first collapsing the selection down to just the result cell.
   Asked for `Create link` to follow the same carve-out operators already get.
2. `Keypad.tsx`'s `canCreateLink` unconditionally excluded `groupMode`
   (`!groupMode && (...)`); changed it to mirror `operatorsEnabled`'s own rule exactly —
   enabled in group mode when `groupContainsResult(groupSelectedIds, nodes)`, otherwise
   the existing single-selection eligibility (number, result, or live reference).
3. `keymap.ts`'s group-mode branch of `dispatchEditorCommand` handled `backspace` and
   `operator` but fell through to a no-op for every other region, including
   `createLink`. Added a `createLink` case there, same shape as the existing `operator`
   case: find the result id in the group set and call `createLinkToValue(resultId)`
   directly — no bundled operator or empty number, matching the context-menu action's
   own contract.
4. Found `docs/ARCHITECTURE.md`'s §8.6 `Create link` bullet explicitly said "Disabled
   during Select group and Select all regardless" — flatly contradicted by the change,
   so it was wrong even before today for not matching the operator column's documented
   behaviour two sections earlier. Rewrote it to state the group-mode carve-out
   alongside the Select-all exclusion, which does still hold (§8.6's own "data-entry has
   no single keypad target" reasoning applies unchanged to `Create link`).
5. Updated `Keypad.test.tsx`'s existing "Select group with a result keeps operators
   enabled and equals disabled" test, which had asserted `keypad-link` stayed disabled
   with an inline comment claiming this was deliberate — flipped both the assertion and
   the comment. Added two new `keymap.test.ts` cases mirroring the existing
   operator-continuation test: `createLink` on a group with a result produces a free,
   chainless reference to that result and clears the group selection; `createLink` on a
   group without a result is a no-op that leaves the group selected.
6. Full verification: `tsc`, lint, and the full suite (858 tests, up from 856) all
   clean; `build:web` still emits `dist/`.

### Findings

None new — this followed the existing §8.7 group-mode pattern exactly rather than
surfacing anything unfamiliar.

### Knowledge revisions

**1. `Create link`'s group-mode disablement was never a deliberate decision — it was a
documentation claim that had already drifted from the operator column's own behaviour.**
*Previously believed (as stated in `ARCHITECTURE.md` before this entry):* `Create link`
is disabled during Select group "regardless," on the same footing as digits, equals, and
parens.
*Now known:* that blanket rule was only ever true for the *digit/editing* keys, which
have no group-mode carve-out. Operators already got the result carve-out on
2026-08-09, and neither that entry nor either of `Create link`'s own two 2026-08-11 /
2026-08-12 introduction entries record a reason it should be treated differently — it
reads as an oversight at introduction time, not a considered exclusion, given
`createLinkToValue` accepts a bare result id with no additional preconditions the
group case would violate.
*What established it:* re-reading `canCreateLink` and `operatorsEnabled` side by side
in `Keypad.tsx` at the user's report, and finding `dispatchEditorCommand`'s group-mode
branch had no `createLink` case at all (silent no-op) rather than an explicit rejection
— consistent with the restriction never having been deliberately wired end-to-end in
the first place.
Standing lesson: when a keypad key gets a new group-mode carve-out (as operators did),
check the *other* value-eligible keys (`Create link` today; a future `Add components`
once it's functional) for the same carve-out rather than assuming a documented "regardless"
was checked against every key it claims to cover.
