## Keypad stops sliding the whole screen; operator digits target the right operand; Copy finally does something

### Session log

1. Three requests in one message, with a screenshot showing a freshly-added number cell
   pinned to the right edge of the viewport, both it and the keypad visibly displaced.
2. **Root-caused the edge-drift before touching anything.** No auto-pan-to-selection feature
   exists in this codebase (checked — nothing in `canvas/`, `AppShell.tsx`, or `NumberNode.tsx`
   moves the viewport on selection). `NumberNode`'s edit-mode `TextInput` carries `autoFocus`,
   which react-native-web forwards straight through as a literal HTML `autofocus` attribute —

   a newly-focused, off-screen input into view. That ancestor is the app's root container
   (`body`/`#root`, `web/index.html`), so the entire screen — keypad included — dragged along
   with a cell added near the edge, even though `body { overflow: hidden }` was already set

   scroll-position change, which is exactly what the browser's focus algorithm performs).

   guard, matching the file's existing pattern). Native keeps the plain `autoFocus` prop; no
   browser there to scroll.

   rebuilt again, and re-confirmed. Without that A/B pair this would have been "the test passes"

## Auto-pan-to-edited-cell: the canvas moves instead of the keypad, with padding, opt-out toggle

### Session log

1. Direct follow-up to this same day's earlier `preventScroll` fix (decision #26): the user
   confirmed the keypad no longer moves, but pointed out the fix removed a *side effect* they
   still wanted — an edge cell used to end up visible (dragged there along with the whole
   page) even though the mechanism was wrong. Asked for the replacement explicitly: the canvas
   itself should pan to reveal the cell, with padding between it and the screen edge once
   panned, and a Settings toggle to turn it off.
2. Split the geometry from the mechanism before writing either: `canvas/autoPan.ts`'s
   `computeAutoPanTarget(rect, viewport, canvasSize)` is pure (no store, no Reanimated) — takes
   a world rect, the current pan/zoom, and the canvas's own laid-out screen size, returns the
   new `pan` needed to clear `AUTO_PAN_PADDING` (24dp, fixed screen-space like every other
   spacing token, not a world distance that would look tighter at higher zoom) on whichever
   edge is violated, or `null` if nothing needs to move. Unit-tested directly (11 cases:
   each of the four edges independently, simultaneous horizontal+vertical, the
   exactly-at-the-boundary no-op, zoom scaling the world-space delta, a non-zero starting pan,
   a rect wider than the padded viewport pinning one edge rather than trying to fit both).
3. `Canvas.tsx` already tracked its own screen size nowhere — added an `onLayout` ref (a ref,
   not state, since it's only read imperatively, never drives a render) and a `panIntoView`
   function that calls `computeAutoPanTarget` against the live shared-value pan/zoom, then
   animates toward the result via `withTiming` (220ms) and commits through the exact same
   `commitViewport` a released gesture already uses, from the animation's own `finished`
   callback rather than a fixed delay. This is the first use of `withTiming` anywhere in the
   codebase — extended `__mocks__/react-native-reanimated.js` to support it (collapses to the
   end value and fires the callback synchronously under Jest, matching how the mock already
   treats every other Reanimated primitive: real behaviour is a real-device-only concern here).
4. Exposed `panIntoView` through the existing `ViewportContext` (alongside `panX`/`panY`/`zoom`)
   rather than a new context, since it's the same "reach into Canvas's live pan/zoom from a
   descendant" problem `useNodeDrag` already solved for `zoom` alone. Added
   `useCanvasViewportOptional` (returns `null` instead of throwing) specifically because
   `NumberNode.test.tsx`'s existing 14 specs all render `<NumberNode>` standalone, with no
   `<Canvas>` ancestor — the throwing `useCanvasViewport` every other consumer uses would have
   broken all of them the moment `NumberNode` called it unconditionally.
5. `NumberNode` calls `panIntoView` from an effect keyed on `isEditing` (entering edit mode —
   added or tapped-into) and on the whole `node` object (not narrowed fields, since the
   narrowed `numberNode` binding isn't in scope until after the hooks-must-run-unconditionally
   early return) so it also re-fires as a number grows while being typed into, not just once on
   entry — a chain member can push itself further past the edge purely by gaining digits,
   without its own `position` moving.
6. Added the Settings toggle (`autoPanToEditedCell`, on by default) the same way the numeral
   font size preference already works — `preferencesStore.ts`, persisted via
   `persistence/preferences.ts`. Caught before it shipped, not live: `preferencesAdapter.write`
   replaces the *whole* persisted blob rather than merging (confirmed by reading both platform
   adapters directly, not assumed), so `setNumeralFontSize`'s pre-existing
   `write({ numeralFontSize: clamped })` call — harmless when it was the only field ever
   written — would have silently dropped `autoPanToEditedCell` from disk the next time either
   setter ran after the other. Fixed by centralising both setters' persistence through one
   `persist()` closure that writes every field's current value, not just the one that changed.
7. Settings sheet gained an `Auto-pan to Edited Cell` row (RN's `Switch`, first use in this
   codebase) below the existing numeral-size row, with a hairline separator between them

8. Verified live end to end, not just the suite: served `dist/`, tapped near the canvas's
   right edge to add a cell there. Screenshot + measured bounding boxes confirmed the cell
   lands exactly `AUTO_PAN_PADDING` (24px) from the visible edge post-pan, and the keypad
   itself never moves (still fixed at the bottom, confirming this is a genuinely different fix
   from decision #26's, not a reversion of it). Toggled the new Settings switch off and
   repeated the same tap: the cell stayed clipped at the edge exactly as it did before this
   feature existed, confirming the opt-out actually disables the behaviour rather than merely
   hiding a UI control.
9. Full suite (956 tests, up 18 net from pre-session — the load-sensitive

   all clean. Updated `ARCHITECTURE.md` §7 (new bullet, cross-referenced from decision #26's
   existing §8.5 bullet), §12.5 (second preference, the `write()`-doesn't-merge fix), and
   decision #32 in §16.

### Findings

**`preferencesAdapter.write()` replaces the whole persisted blob; it does not merge.** Both
platform adapters (`preferences.web.ts`'s `kv.set(KEY, JSON.stringify(prefs))`,
`preferences.native.ts`'s `writeFile(path, JSON.stringify(prefs), 'utf8')`) serialise exactly
the object they're given and overwrite the file/record wholesale — there is no read-modify-write
inside the adapter. This was invisible with one preference (`numeralFontSize`): a setter writing
`{ numeralFontSize: x }` alone *was* the whole blob by definition, so nothing was ever lost. It
only becomes a bug the moment a second independently-settable preference exists and each
setter still writes only its own field — the misleading part is that nothing fails and nothing
is visibly wrong *this session*; the dropped field only surfaces on the next app restart, as a
silently-reverted setting, with no error anywhere pointing at the cause. Generalisable: any
store wrapping a "replace the whole blob" persistence contract needs every setter to persist
the full current state, not just the field it changed, from the moment a second field exists —
checked by reading the adapter's actual write implementation, not assumed from the setter's own
single-field call.

### Knowledge revisions

None. Nothing here overturns a belief from an earlier entry — the `write()`-doesn't-merge gap
was a latent bug caught before it shipped, not a wrong belief acted on and then corrected.

## The animated auto-pan itself brought the keyboard-drags-the-page bug back on a real device

### Session log

1. User reported, with a real-device screenshot (mobile Safari, chained continuations several
   levels deep), that the keypad was moving again — the exact symptom decision #26's
   `preventScroll` fix was supposed to have closed for good, now apparently reintroduced by
   decision #32's own auto-pan feature shipped the same day.
2. Reproduced the reported scenario (5+ chained continuations from a result, each one
   triggering auto-pan) against the deployed build with Playwright/Chromium: zero page scroll,
   zero keypad movement, across every step — confirmed both by `window.scrollY` staying `0`
   throughout and by the keypad's own bounding-box `y` never changing. This ruled out a bug in
   the pan geometry or commit logic itself (already covered by `autoPan.ts`'s unit tests
   anyway) and pointed at something Chromium's engine simply doesn't reproduce.
3. Reasoned to the actual mechanism rather than guessing blind: decision #26's fix suppresses
   exactly one trigger — the browser's native `autoFocus`-attribute scroll-into-view, which
   fires once, at focus time. It does not (and structurally cannot, since it only wraps one
   `.focus()` call) suppress a *second*, independent WebKit behaviour: a focused control whose
   bounding rect changes later — for any reason, including a pure CSS transform with no new
   focus/scrollIntoView call — can still get scrolled back into view by Safari's own
   keyboard-accessibility heuristic. The animated auto-pan is exactly that: it moves the still-
   focused `TextInput` via `Canvas`'s Reanimated transform, continuously, for `withTiming`'s
   220ms. No amount of the *existing* fix touches this, because the existing fix only ever ran
   once, at the moment focus was first acquired.
4. Fixed by removing the one thing that heuristic keys off: `NumberNode` now blurs its own
   `TextInput` immediately before an actual pan starts, and refocuses (`preventScroll: true`,
   reusing the exact mechanism decision #26 already established) once the pan settles. Threaded
   as `onWillPan`/`onSettled` callbacks on `Canvas`'s `panIntoView` (`ViewportContext.tsx`) so
   Canvas only invokes them around a pan that's actually happening — a cell already comfortably
   in view, the overwhelmingly common case, never blurs anything.
5. Could not reproduce the bug itself locally (Chromium has no equivalent heuristic to
   trigger), so could not verify the fix by watching it stop happening — the closest available
   verification was confirming the fix introduces no *new* problem: rebuilt, re-ran the same
   5-deep continuation chain against the deployed build with the fix in place, confirmed typing,
   continuation, and panning all still work identically (same chain of results, same screenshot
   silhouette as before the fix), and that `window.scrollY`/keypad position still never move in
   Chromium either way. This is a case where the fix's correctness rests on reasoning about a
   documented third-party engine behaviour rather than a repro-and-verify loop — recorded
   explicitly as decision #33's revisit condition rather than claimed as verified live, since it
   wasn't and can't be in this environment.
6. Re-read the user's second sentence ("when the result goes out of view canvas do not adjust")
   against the actual implementation before treating it as a second bug: auto-pan only ever
   reads the currently-*editing* number's own rect (`NumberNode`'s effect, gated on
   `editingNodeId`) — a result node has no edit mode and triggers nothing, directly or
   indirectly, confirmed by tracing every call site of `panIntoView` (there is exactly one).
   Concluded this was describing the *same* bug from the user's own vantage point (a result
   scrolling out of view *because* the whole page moved), not a request for new logic asking the
   canvas to also chase a result's visibility — no change made against it beyond the fix above.
7. Full suite (956 tests; the same load-sensitive `snapSearch.profile.test.ts` flaked once
   under load this run too, 3/3 clean immediately after in isolation — see prior entries),
   `tsc`, lint, and `build:web` all clean. Updated `ARCHITECTURE.md` §7 (extended the auto-pan
   bullet with the callback mechanism) and decision #33 in §16.

### Findings

**A one-time `preventScroll: true` on `.focus()` does not cover every way WebKit can later
decide to scroll a focused element into view.** It suppresses only the trigger tied to that
specific focus call (here, the `autoFocus` HTML-attribute case decision #26 fixed). A focused
element's bounding rect changing afterward — by any means, including a pure CSS transform with
no further focus/scrollIntoView call — can independently re-trigger the browser's own
keyboard-accessibility "keep the focused control visible" behaviour. The generalisable shape:
any app that both (a) keeps real DOM focus on an input and (b) moves that input's on-screen
position programmatically after focus (an animation, a live-updating layout, anything) needs to
either blur across the move or expect this class of bug to resurface on a real device no matter
how thoroughly the *original* focus-time trigger was fixed. Not independently verifiable in this
environment: Chromium has no equivalent heuristic, so this class of bug has no local repro —
recorded as a known instrumentation gap, not resolved by adding a test that would pass either way.

### Knowledge revisions

**5. `preventScroll: true` on a web `.focus()` call is not a general "this element will never
cause the page to scroll" guarantee — it only covers that one focus call's own trigger.**
*Previously believed* (implicitly, from how decision #26 was written and closed): the
keyboard-drags-the-page class of bug was fully closed once `autoFocus`'s scroll was suppressed.
*Now known:* WebKit has at least one other independent trigger for the same visible symptom —
a focused element's bounding rect changing later, by any means — that `preventScroll` on the
original focus call does nothing to prevent.
*What established it:* live user report with a real-device screenshot, reproduced structurally
(not visually) by tracing which code path could move a focused input's screen position without
calling `.focus()` again; recorded as decision #33.
*Standing lesson:* a browser-quirk fix closes the *reported* trigger, not necessarily the whole
class of bug — treat "the keyboard moved again" from a *different* code path as a new instance
of the same class, not evidence the original fix was wrong.

3. Traced (2) to the exact mechanism, not just the symptom: `NumberNode`'s `TextInput` has

   was therefore *also* exiting edit mode exactly like a real one, mid-keystroke. The next
   digit then landed with `editingNodeId`/`selectedNodeId` both null, and
   `dispatchEditorCommand`'s digit case has an explicit branch for exactly that state:
   `editNumberNode(addNumberNode(caretPoint, char))` — start a brand new cell. That branch
   exists for a genuinely nothing-selected canvas tap; decision #33's own blur was landing the
   editor in that same state by accident.
4. Fixed (2) with a boolean ref, `suppressBlurDeselect` — armed by the auto-pan's own
   `onWillPan` (right before calling `.blur()`), read by the real `onBlur` handler (skips
   `deselectNode()` while armed), disarmed by `onSettled` (right after refocusing). A real
   blur — tapping away, moving focus elsewhere — happens with the ref at its default `false`
   and is unaffected; only the pan's own synthetic blur is suppressed, and only for its
   duration.

### Findings

**Calling `.blur()` on a focused element fires that element's own `onBlur` handler
synchronously, in both real WebKit and Chromium/jsdom-less React Native Web alike — this part
of the earlier bug's fix was never a browser-quirk concern, just an ordinary consequence of
wiring a side-effecting `onBlur` prop onto the exact element a *different* feature also needs
to blur for an unrelated reason.** The misleading part, in hindsight: decision #33's own
reasoning was entirely about a WebKit-specific, unverifiable-locally heuristic, which made it
easy to overlook that the blur call itself has a completely ordinary, always-reproducible
side effect through this app's own existing `onBlur={deselectNode}` wiring — a bug hiding in
the shadow of a much harder one, in the same commit, un-caught because verification effort
went entirely toward the exotic part.

### Knowledge revisions

**6. A component's own `onBlur` handler fires for *every* blur, including ones a sibling
feature triggers programmatically for an unrelated reason — not just for a "real" user-driven
blur.**
*Previously believed* (implicitly, writing decision #33's fix): calling `.blur()` on a ref to
suppress a WebKit scroll heuristic was a narrowly-scoped, side-effect-free DOM operation.
*Now known:* `.blur()` is exactly as "real" as any other blur to the element's own `onBlur`
prop — anything wired there (here, `deselectNode`, an existing and correct handler for a
genuine blur) fires regardless of *why* the element lost focus.
*What established it:* live user report (a stray cell appearing mid-type) reproduced
structurally by tracing the exact call path from `.blur()` through `onBlur` to
`dispatchEditorCommand`'s nothing-selected branch; recorded as decision #34.
*Standing lesson:* before calling an imperative DOM/native method (`.blur()`, `.focus()`,
`.scrollIntoView()`, ...) for a purely cosmetic or defensive reason, check what that same
method already wires up to on the target element — a call made for reason A can still trigger
every consequence already attached for reason B.
