# 2026-08-21

## Keypad stops sliding the whole screen; operator digits target the right operand; Copy finally does something

### Session log

1. Three requests in one message, with a screenshot showing a freshly-added number cell
   pinned to the right edge of the viewport, both it and the keypad visibly displaced.
2. **Root-caused the edge-drift before touching anything.** No auto-pan-to-selection feature
   exists in this codebase (checked — nothing in `canvas/`, `AppShell.tsx`, or `NumberNode.tsx`
   moves the viewport on selection). `NumberNode`'s edit-mode `TextInput` carries `autoFocus`,
   which react-native-web forwards straight through as a literal HTML `autofocus` attribute —
   and the *browser's own* autofocus algorithm scrolls its nearest scrollable ancestor to bring
   a newly-focused, off-screen input into view. That ancestor is the app's root container
   (`body`/`#root`, `web/index.html`), so the entire screen — keypad included — dragged along
   with a cell added near the edge, even though `body { overflow: hidden }` was already set
   (that CSS hides the scrollbar and blocks user-driven scroll; it does not block a programmatic
   scroll-position change, which is exactly what the browser's focus algorithm performs).
3. Fixed by taking the focus call away from the `autoFocus` prop entirely on web —
   `inputNode.focus({ preventScroll: true })` in the same effect that already does other
   browser-specific TextInput handling for this component (raw DOM ref, `Platform.OS === 'web'`
   guard, matching the file's existing pattern). Native keeps the plain `autoFocus` prop; no
   browser there to scroll.
4. **Verified the bug was real, not assumed**, before calling the fix done: saved the fix as a
   patch, reverted just `NumberNode.tsx` (`git checkout -- <path>`, not a full `git stash` —
   a full stash reverted every other file mid-session and had to be popped back immediately),
   rebuilt, and re-ran the same scripted repro. Confirmed a genuine 29px horizontal scroll on
   the unfixed build (`window.scrollX: 0 → 29`, the keypad's own bounding rect shifting by the
   same amount) and zero scroll on the fixed one. Restored the fix from the saved patch,
   rebuilt again, and re-confirmed. Without that A/B pair this would have been "the test passes"
   without ever having shown it would have failed before the fix — the exact gap `docs/journal/
   2026-08-03.md`'s revision 8/10 already named as a recorded mistake pattern.
5. **Operator + digit.** `dispatchEditorCommand`'s digit/decimal/sign case had one line —
   `if (selectedNode?.kind === 'operator') return;` — inherited from before continuation
   existed. Replaced it with: look at the chain member to the operator's right
   (`rightChainNeighborId`, new, mirrors the existing `leftChainNeighborId` backspace already
   uses); a **number** there gets edited in place (same treatment "select then type" already
   gets a plain number, just retargeted); **nothing** there gets a fresh number spliced in via
   `appendNumberNode` (already able to insert mid-chain, not just at the end — no new plumbing);
   a **reference** or **result** there stays inert, matching every other place those two kinds
   are already non-editable. `Keypad.tsx`'s own `selectionBlocksDigits` got the identical
   right-neighbour check so the on-screen key's greyed-out state can't disagree with what
   pressing it actually does. The "nothing there" case is not hypothetical — it's exactly the
   state last session's backspace-lands-on-left-neighbour change (decision #25) leaves behind
   when a chain's last operand gets backspaced away to nothing and then deleted.
6. **Copy.** Was a permanently-disabled placeholder (`disabled: true`, no `onPress`, documented
   explicitly as future work). Added `engine/copyText.ts`: `copyTextForNode` reuses each value
   kind's own display-content function (`formatForDisplay` for a number, `resultCellContent` for
   a result, `referenceCellContent` for a reference) rather than re-deriving text, so the
   clipboard always matches what the cell itself shows — including a stale result's last-good
   value and a dangling reference's last-known display, both real values even though neither is
   "current." Operator/paren/equals have none, so `Copy` disables for those exactly the same way
   it now enables for the other three. `store/commands.ts`'s `copyNodeValue` is the one place
   that actually touches `Clipboard.setString` — `Clipboard` imported from `'react-native'`
   directly, which resolves to the real native module on-device and to `react-native-web`'s own
   implementation on web (the existing `react-native$` → `react-native-web` webpack alias, no
   new plumbing) — a small enough win not to justify pulling in
   `@react-native-clipboard/clipboard` for. RN core's own `Clipboard` is deprecated (logs a
   console warning) but still functional in this RN version; noted as a revisit condition rather
   than switched pre-emptively.
7. **Copy As → Copy without result.** Offered only once the long-pressed cell is part of the
   active group selection (`groupSelectedIds.has(nodeId)`) — `Select group` or `Select all`,
   either way. `chainTextWithoutResult` (`engine/copyText.ts`) walks a chain's members, skips
   `equals`/`result` entirely, and renders everything else (number, operator, paren, reference)
   as the same glyph its own cell shows, space-joined — `12 + 5 = 17` copies as `12 + 5`, not a
   dangling trailing `=`. `copyGroupWithoutResult` (`store/commands.ts`) resolves the whole group
   selection into distinct chains + free nodes (same decomposition `deleteGroup` already does
   inline, not imported from `nodes/dragLifecycle.ts`'s `resolveSelectionUnits` — that file is
   nodes-layer and `commands.ts` never imports from `nodes/`, an existing layering boundary worth
   keeping rather than crossing for one call site) and joins each chain's/free node's text one
   per line.
8. Built the `Copy As` reveal as a nested row inside the same sheet rather than a separate
   flyout — "one item for now," so a flyout's extra positioning/dismissal machinery bought
   nothing. New `MenuItem.indent`/`onHoverIn` fields on the existing generic `MenuRow`.
   `onHoverIn` needed a `Platform.OS === 'web'`-style prop cast (`onMouseEnter` isn't in RN's
   `TouchableOpacityProps` types — no DOM lib in this project's tsconfig — but react-native-web's
   `TouchableOpacity` forwards unknown props to the host `View`, which understands it; same trade
   `Keypad.tsx`'s `skipTabOrder` already makes).
9. **Caught live, not by the unit suite: tap-after-hover collapsed the row it just revealed.**
   First draft had `Copy As`'s `onPress` *toggle* (`!expanded`) while `onHoverIn` always set
   `true`. A scripted Playwright `.click()` — which is a real mouse move-then-press, i.e. a
   hover immediately followed by a click on the same element — hovered (revealing the nested
   row), then the click's own `onPress` flipped it straight back to hidden. The unit tests never
   caught this because they called `onHoverIn`/`onPress` as two separate, deliberate `act()`
   calls rather than the same physical gesture a mouse click actually is. Fixed by making both
   handlers only ever *set* `true`, never toggle — there's no requested "collapse" affordance,
   only "reveal." Added a dedicated regression test that fires hover then press in the same
   sequence a real click would, and re-verified live (rebuilt, re-served, re-ran the same
   script) that `Copy As` → `Copy without result` → clipboard now works end to end
   (`"12 + 5"` from a `12 + 5 = 17` chain, confirmed via a `document.execCommand('copy')` spy
   since headless Chromium doesn't expose real OS clipboard read-back to the harness cleanly).
10. Full suite (903 tests), `tsc`, and lint all clean on the final pass. Updated
    `ARCHITECTURE.md` §8.5/§8.6 (including retiring the now-stale "`Copy` is a disabled
    placeholder" cross-reference in the `Add components`/`Notes` paragraph) and added decisions
    #26–#28 in §16, in the same commit as the code.

### Findings

- **`git stash` with no pathspec stashes the whole working tree, not "the file I'm looking at."**
  Wanted to temporarily revert one file to check a pre-fix repro; `git stash` took every
  uncommitted change in the session, not just `NumberNode.tsx`, and the harness's own
  file-change notifications for every other touched file fired as a result. `git stash pop`
  immediately after restored everything intact, but the safer tool for "revert just this one
  file, then bring it back" is `git diff -- <path> > x.patch && git checkout -- <path>` (revert)
  then `git apply x.patch` (restore) — scoped to exactly the file in question, no shared stash
  state to misuse.
- **Playwright isn't in this repo's own `node_modules`, but is installed globally** at
  `/opt/node22/lib/node_modules` (confirmed via `npx playwright --version` succeeding while a
  plain `require('playwright')` from a scratchpad script failed). `NODE_PATH=/opt/node22/lib/
  node_modules node script.js` resolves it without installing anything into the project.
- **RN-web `TouchableOpacity` forwards unknown props to its underlying host `View`**
  (confirmed by reading its source, not assumed) — the same mechanism `Keypad.tsx`'s
  `skipTabOrder` already relies on for a web-only `tabIndex`, now reused for `onMouseEnter`.
  Native's `TouchableOpacity` doesn't spread `...props` the same way, but an unrecognised prop
  is simply unused there, not an error — safe either direction.
- **A result node's `chainId` is never `null`** — `finalizeChain` sets it to the result's own
  source chain the moment the result is created (§9). A `Copy As` code path defending against
  "a lone free result contributes nothing" is therefore unreachable through the ordinary command
  set; tested anyway via a directly-constructed document (same technique `NodeContextMenu.test
  .tsx`'s dangling-reference fixtures already use), since the branch is real code even if nothing
  in this app today can put a result in `groupSelectedIds` without also chain-attaching it.
