## PR preview deploy: `workflow_dispatch` `number` input serializes as a float

### Session log

1. Follow-up to 2026-08-06's PR-preview work (PR #130, merged). Two problems
   surfaced once it actually ran against real GitHub infrastructure:
   - The live Pages site stayed on the *old* `actions/deploy-pages` build from
     before that PR, because Settings → Pages → Source was still "GitHub
     Actions" rather than "Deploy from a branch" — confirmed by comparing the
     bundle hash and `last-modified` header the live site served against what
     was actually on the `gh-pages` branch tip. Talked the user through the
     Settings UI to flip it by hand (mobile Safari's tab row hides Settings
     off-screen — worth remembering if this comes up again).
   - Manually running `deploy-pr-preview.yml` against PR #133 failed at
     checkout: `fatal: couldn't find remote ref refs/pull/133.0/head`.
2. The log's own printed `with:` block showed the ref as
   `refs/pull/133.0/head` — not `133`. `pr_number` was declared
   `type: number` in `workflow_dispatch.inputs`; GitHub stores that as a
   float internally, so every expression interpolation of it
   (`${{ inputs.pr_number }}`) renders `"133.0"`, not `"133"`. That string
   then flows untouched through the `determine` job's output into the
   `refs/pull/<n>/head` ref, which doesn't exist with a `.0` in it.
3. Fix: changed `pr_number`'s input type from `number` to `string`. Nothing
   in the workflow ever does arithmetic on it — it's only ever concatenated
   into ref paths, a `destination_dir`, and a comment body — so there was no
   reason to have chosen `number` beyond it "being a number" conceptually.

### Findings

**`workflow_dispatch` inputs declared `type: number` serialize into
expressions with a trailing `.0`.** GitHub stores the value as a float
regardless of what the user types, and `${{ inputs.foo }}` renders that float
directly — `133` becomes `"133.0"` wherever it's interpolated into a string.
Misleading symptom: the input *looks* right everywhere in the Actions UI (the
run form just shows `133`), and the workflow YAML looks correct too — the
`.0` only appears once you read the *expanded* `with:` block in a run's log,
which is easy not to check when a checkout step fails with what looks like a
generic "ref not found." Fix/avoidance: declare any `workflow_dispatch`
input as `type: string` unless the workflow actually does numeric
comparison or arithmetic on it — text-only usage (refs, paths, comment
bodies, as here) has nothing to gain from `type: number` and everything to
lose from this quirk.

## Suppress OS soft keyboard on number edit

### Session log

1. Bug report with screenshot: editing a number showed the iOS system numeric
   keyboard stacked on the custom keypad. Architecture §8.5 already treats the
   app keypad as the soft-input surface; the OS keyboard is redundant.
2. Root cause was the open thread left by P2.6 (`docs/journal/2026-08-03.md`):
   `NumberNode`'s edit `TextInput` used the platform default for
   `showSoftInputOnFocus`, deliberately, until P2.8 wired keypad presses into
   the same edit target. P2.8 (and P7.2) did that wiring; the prop was never
   added.
3. Set `showSoftInputOnFocus={false}` on the number-edit `TextInput` only.
   Label and value-slider bound inputs keep the system keyboard. Unit test
   asserts the prop. RN-web maps the same prop to
   `virtualkeyboardpolicy="manual"` — no separate `inputMode` needed for the
   web path this session checked.

### Findings

**`showSoftInputOnFocus={false}` is the one-line native fix for "custom keypad
+ OS keyboard both visible," and RN-web already forwards it.** Mechanism:
native RN suppresses the IME while leaving the field focusable (caret /
hardware keys still work); react-native-web sets
`virtualkeyboardpolicy="manual"` on the host `<input>`. Misleading symptom:
the custom keypad looks correct and receives presses, so it is easy to assume
the OS keyboard is a separate bug in focus-steal prevention (`Keypad`'s
`onMouseDown` preventDefault) rather than the edit `TextInput` inviting the
IME by default. The 2026-08-03 deferral already named the fix; the gap was
simply never closing it after P2.8.

### Knowledge revisions

**2. Soft-keyboard suppression was deferred until keypad wiring, then never
applied.**
*Previously believed (as an open thread, not a standing design):* leave
`showSoftInputOnFocus` unset on `NumberNode` until P2.8, then decide.
*Now known:* with keypad + hardware dispatch in place, the answer is
`showSoftInputOnFocus={false}` on the number editor; label/slider inputs stay
default so they can use the OS keyboard.
*What established it:* the deferred note in `2026-08-03`, the live iOS
screenshot of both keyboards, and the fact that P2.8/`dispatchEditorCommand`
already update `raw` without needing the IME.

## Soft-keyboard suppression needed `inputMode="none"` on web

### Session log

1. After PR #136 merged (`showSoftInputOnFocus={false}`), the reporter still
   saw the OS virtual keyboard while editing a number — same stacking with
   the custom keypad.
2. Re-read RN-web's `TextInput`: `showSoftInputOnFocus={false}` only sets
   `virtualkeyboardpolicy="manual"`. Separately, `keyboardType="numeric"`
   still emits `inputMode="numeric"`. Safari (and other mobile browsers)
   honour `inputMode` for which soft keyboard to raise and largely ignore
   `virtualkeyboardpolicy`, so the numeric pad kept appearing.
3. Fix: set `inputMode="none"` on the number-edit `TextInput` and drop
   `keyboardType="numeric"` so it cannot reintroduce a numeric inputMode.
   Keep `showSoftInputOnFocus={false}` for native. Label / slider inputs
   untouched.

### Findings

**On react-native-web, `showSoftInputOnFocus={false}` is not a soft-keyboard
suppressor by itself.** It only sets `virtualkeyboardpolicy="manual"`. The
attribute browsers actually use to keep the IME down is `inputMode="none"`.
Worse, leaving `keyboardType="numeric"` sets `inputMode="numeric"`, which
actively invites the OS numeric pad on iOS Safari. Misleading symptom: desktop
Chrome never shows a soft keyboard, so a desktop web smoke that checks
`virtualkeyboardpolicy="manual"` looks green while mobile Safari still pops
the pad. The RN-web issue thread (#2421) and the Expensify patch both pointed
at `inputMode='none'` as the real mapping; upstream RN-web never tied
`showSoftInputOnFocus` to that.

### Knowledge revisions

**3. `showSoftInputOnFocus={false}` alone closes the native gap, not the
mobile-web one.**
*Previously believed (this day's earlier entry, revision 2 / PR #136):*
`showSoftInputOnFocus={false}` is the one-line fix cross-platform, and
RN-web's `virtualkeyboardpolicy="manual"` mapping means no separate
`inputMode` is needed.
*Now known:* keep `showSoftInputOnFocus={false}` for native, but mobile web
needs `inputMode="none"` and must not set `keyboardType="numeric"`. Desktop
web verification cannot prove soft-keyboard absence.
*What established it:* reporter still seeing the OS keyboard after #136;
RN-web source mapping of the two props; `inputMode` precedence over
`keyboardType` in that same file.
*Standing lesson:* a soft-keyboard claim needs a touch/mobile surface, or at
least a DOM attribute check for `inputMode="none"` — not only
`virtualkeyboardpolicy`.

## Selection focus ring was painted under flush chain neighbours

### Session log

1. User asked to visually show the cell that currently has focus, calling out
   that a read-only result still holds focus because typing an operator there
   starts §8.7 continuation.
2. P7.2 already drew an outset `selectionFocusColor` ring on `Cell` for every
   selected / group-selected node, including results. Live check showed the
   DOM node present, but mid-chain operators looked unfocused and results only
   showed a partial edge.
3. Root cause: idle positioned nodes all return `zIndex: 0` from
   `useNodeDrag`'s animated style, and chain members sit flush, so later
   siblings paint over the outset ring. Misleading symptom: the ring "exists"
   in DevTools and unit tests on a lone `OperatorNode` pass, while a real
   formula chain hides it.
4. Fix (PR #140): elevate the selected wrapper to `SELECTED_NODE_Z_INDEX` (10)
   while idle; whiten/thicken the ring (`#FFFFFF`, 3px / 4px outset); cover
   result + stacking in `SelectionFocus.test.tsx`; note the stacking rule in
   §8.6.
5. Live Chromium: mid-chain `÷` and result `2.4` both show a full surround;
   continuation from a focused result still works. Screenshots under
   `/opt/cursor/artifacts/screenshots/final_*_ring.webp`.

### Findings

**An outset focus ring on a flush chain member is invisible unless the
selected wrapper stacks above its neighbours.** Mechanism: NodeLayer places
every member at the same idle `zIndex: 0`; document order then wins, so the
next cell covers the 3–4px of ring that sticks out into its box. Unit tests
that mount a single node never exercise that. Misleading symptom: DevTools
shows `visibility: visible` and a light border colour, which looks like a
contrast problem rather than a paint-order problem.

### Knowledge revisions

**4. "Focus is always visible" (P7.2) was true in isolation, false in a chain.**
*Previously believed:* painting an outset ring on `Cell` with
`selectionFocusColor` satisfied P7.2's "Focus is always visible" for every
kind, including results.
*Now known:* the ring must also win the sibling paint order — elevate the
selected node's wrapper above idle neighbours (and keep it below connectors /
live drag). Colour/thickness alone cannot fix a ring that is under the next
cell.
*What established it:* live Chromium on `12 ÷ 5 = 2.4` with the ring in the
DOM but not surrounding mid-chain `÷`; z-index 10 after the fix made the full
ring visible.
*Standing lesson:* an outset decoration on chain members needs an explicit
stacking rule, or a test that mounts a multi-member chain and asserts the
selected wrapper's z-index — a single-node ring assertion is not enough.
