# 2026-08-17

## Identity ring moved outset (matches selection focus); result pattern propagates through references

### Session log

1. User attached a screenshot of the deployed app and named two gaps against the shipped
   design directly: (a) the identity ring on a declaring/referenced cell is drawn *inside*
   the cell — wanted as an *outer* border instead, one that becomes white on selection; (b)
   a reference cell whose value ultimately comes from a result should carry the same §1.2 dot
   pattern the result itself has (colour unchanged, pattern only), and that has to propagate
   through a reference that points at another reference, not just a direct number/result link.
2. Read the screenshot against the current code rather than guessing at "source cell": the
   inset ring only ever renders on a *declaring* cell (`identityHue` prop — a labelled number,
   or a result something references), never on a reference cell itself (references pass
   `labelHue` and fill with the hue instead, per §11.1's existing rule) — so "border on the
   source cell" in the request is exactly `Cell.tsx`'s existing `identityRing`, not the
   reference's own structural border.
3. Moved `identityRing` from inset (`top/left/right/bottom: 0`, radius `cornerRadius -
   borderBand`) to the exact geometry the P7.2 selection focus ring already uses (`top/left/
   right/bottom: -SELECTION_FOCUS_OUTSET`, radius `cornerRadius + SELECTION_FOCUS_OUTSET`).
   The two rings were already mutually exclusive by `selected` (ring shows unselected, focus
   ring replaces it selected) and already the same border width by coincidence
   (`IDENTITY_RING_WIDTH === SELECTION_FOCUS_WIDTH === tokens.borderBand`), so this reuse
   makes literal what the request asked for: "the same border, recoloured white on select,"
   not two different chrome elements that happen to hand off to each other.
4. That alone reintroduced the exact bug class `2026-08-08`'s "Selection focus ring was
   painted under flush chain neighbours" entry already named and fixed once for the
   *selected* case: an outset ring on an unselected declaring cell is just as paintable-over
   by a flush neighbour that happens to sit later in `nodeIds`' paint order. Extended
   `useNodeDrag`'s existing `SELECTED_NODE_Z_INDEX` elevation (previously keyed only on
   `useNodeSelected`) to also elevate when `useSourceIdentityHue` is defined — same
   mechanism, same constant, one more trigger condition.
5. Verified live in a served `dist/` build (per the standing lesson re-cited in yesterday's
   entry: tsc/lint/tests are not enough on their own) and found a **second**, more serious
   instance of the same "outset-ring-gets-clipped" bug class, this time not about z-index at
   all: the identity ring rendered in the DOM with the correct colour and radius (confirmed
   via `page.evaluate` reading its computed style) but was **completely invisible on
   screen** for any result cell. Root cause: `Cell`'s band applies `overflow: hidden`
   whenever it carries a `bandBackground` (the P7.3 dot texture, unconditional on every
   result) to clip that texture to the rounded corner — and the ring, still a *child* of
   that same band View at the time, got clipped away with it. This could not have been
   caught by any existing test: Jest's renderer never computes real layout/overflow, so a
   ring with exactly correct props and exactly zero visible pixels looks identical to a
   passing test either way.
6. Fixed structurally, not by special-casing: introduced a `cellOuter` wrapper View around
   the band, and made the identity ring and the selection focus ring **siblings** of the
   band rather than children of it — both now position themselves outset against
   `cellOuter`, which is never clipped. The band keeps its own `overflow: hidden` for the
   texture, now applied unconditionally (previously gated on `!selected`, a trade-off that
   existed only because the focus ring used to be a clipped sibling too) — a strict
   simplification, not a new trade-off, once the rings no longer share the band's clip.
7. Added `textureSize()` to `ResultDotTexture.tsx`, shared by `ResultNode` and the new
   `ReferenceNode` texture use: sizes the SVG to the band's actual content box via
   `sideBorderWidths(groupPosition, …)` rather than assuming both left and right always
   carry a border. This silently corrects a latent sizing bug from yesterday's chain-grouping
   change: `ResultNode`'s texture width was still hardcoded as `bandWidth - 2 ×
   borderBand`, which was only ever exactly right for a `'solo'` cell — and a result is
   *never* `'solo'` in practice (it's always the last member of its own chain, so always
   `'end'`, carrying a border on one side only). Not user-visible before today (the offset
   is 3dp, below what a screenshot comparison would flag), but real, and now correct for
   every group position rather than only the one that never occurs.
8. `ReferenceNode` gained `showResultPattern`, computed from the existing
   `identitySourceId(nodes, id)` (`engine/identity.ts`) — already walks a reference→reference
   chain to its ultimate number/result source, so nested propagation needed no new logic,
   only a `kind === 'result'` check on whatever it resolves to. Passes the same
   `ResultDotTexture` as its `bandBackground` when true; colour/fill/border logic is
   untouched, exactly matching "don't change anything with the colour, just the pattern."
9. Verified live end to end: built `dist/`, drove three chained-continuation rows through the
   real keypad (`12+15+52=`, continue `+15+12=`, continue `+30=`) in a scripted browser
   session, and confirmed by screenshot that both source results show their own outset ring
   in their identity hue while unselected, both leading reference cells show the dot pattern
   in their fill hue, and the newest result shows the white focus ring in the same outset
   spot — nothing clipped, nothing hidden behind a neighbour. Cross-checked the DOM directly
   (`page.evaluate`) to confirm ring count/colour/radius independent of visual squinting.
10. Added test coverage for the new propagation rule (`ReferenceNode.test.tsx`: number
    target → no texture; direct result target → texture; reference-to-reference-to-result →
    texture; dangling → no texture) and extended `IdentityHue.test.tsx`'s existing
    referenced-result test to assert the texture and the ring now coexist on one cell, since
    that exact combination is what the clipping bug broke. Full suite (834 tests, the same
    already-documented load-sensitive `snapSearch.profile.test.ts` flaking once under load
    and passing clean in isolation immediately after — not new, see `2026-08-08`/`2026-08-15`/
    yesterday's entries), `tsc`, lint, and `build:web` all clean.
11. Updated `ARCHITECTURE.md` §8.6 (focus ring z-index elevation), §11.1 (ring geometry +
    pattern propagation) and §11.3 (band/ring sibling structure, `textureSize`), plus a new
    decision #21 in §16, all in the same commit as the code.

### Findings

**An RN/RN-web View's `overflow: hidden` clips *all* of its children, including an
absolutely-positioned one whose offsets place it entirely outside the parent's own box.**
Nothing about a negative `top`/`left` inset exempts a child from its parent's clip region —
clipping is a property of the parent's painted box, evaluated independent of where a child's
own geometry says it should be drawn. The misleading part: the child's computed style
(`page.evaluate` on the real DOM) showed the exactly-correct `border-color` and
`border-radius`, so everything *upstream* of paint was verified right, and the bug was
invisible to any tool that stops at "did the props reach the element" rather than "did a
pixel actually land on screen." Generalisable: an outset ring/badge/overflow decoration must
be a sibling of whatever clips its own content, not a descendant of it, whenever the two are
ever true at once — and this needs checking again if a *third* clipped-band feature is ever
added, since it would need to join the same `cellOuter` sibling arrangement rather than being
nested back inside the band "for convenience."

## `=` becomes a hard stop; operator cells narrower

### Session log

1. Two more requests in one message: (a) don't allow a cell to be added after `=`, and
   disable the equals key once a chain already has one; (b) reduce the horizontal padding
   inside operator cells.
2. Traced (a) into `keymap.ts`'s `dispatchEditorCommand` rather than assuming it was a
   missing feature: `appendMembersToChain` (`store/commands.ts`) inserts a new member
   right after whatever node id it's given, and nothing in the dispatch function stopped
   that anchor from being the `=` cell itself. Selecting `=` and pressing a digit, `(`/`)`,
   an operator, or `=` again all reached the generic append path and spliced a new member
   in immediately after the equals node — reproduced live before touching anything, not
   assumed from reading the code. The existing guard pattern for `result` (a full
   early-return block covering every command region) was the template; `equals` needed
   the identical treatment, since a result and its `=` are both "this chain is done,
   nothing appends past here," not two different rules.
3. The second half — disabling the keypad's `=` key once the chain already has one — is a
   different case from the first: it has to fire when *any* member of an already-`=`'d
   chain is selected (not only the `=` cell itself, which the block above already fully
   blocks), because `case 'equals':` was still reachable from every other selected member
   and would splice a *second* `=` in front of the existing equals+result pair — visibly
   broken (`1+2=` then select `1`, press `=`, produced two `=` nodes back to back). Added
   `chainHasEquals(nodeId, nodes, chains)` (new export, `keymap.ts`) — walks the selected
   node's own chain for an existing equals member — and used it in two places that have to
   agree: `Keypad.tsx`'s `EqualsKey` `disabled` prop (so the button visibly greys out) and
   a guard inside `dispatchEditorCommand`'s own `equals` case (so a hardware Enter/`=`
   press, which never goes through the on-screen button's `disabled` prop at all, can't do
   what the button already refuses to). Learned this the specific way: `AppShell.tsx`'s
   keydown listener calls `dispatchEditorCommand` directly, so a UI-only disable is
   cosmetic unless the dispatch function enforces the same rule itself — the keypad
   component was never the actual authority, just a mirror of one.
4. For (b), measured before guessing: built `dist/`, served it, and read
   `getBoundingClientRect()` on both an operator cell and its glyph's text range via
   Playwright rather than eyeballing a screenshot. `operatorWidth: 34` left ~10.5dp of
   padding on each side of a ~13dp-wide `+` glyph — more than double `numberPaddingX`'s
   already-trimmed 4dp for the equivalent number-cell padding, so the mismatch was real,
   not just a hunch. Cut to `26`.
5. That number happens to fall under `chains/bounds.ts`'s `SNAP_DISTANCE` (28) — a fact
   `chains/snapping.test.ts` names explicitly in a comment ("operatorWidth (34) ≥
   SNAP_DISTANCE, so boundary 1 is not also a candidate") for one specific fixture. Rather
   than picking a value just to dodge that coupling, ran the full suite first: every test,
   including that one, passed unchanged — the fixture's boundary positions are derived from
   `widthOf`/tokens rather than hardcoded, and `resolveSnapCandidate`'s "nearest wins"
   tie-break resolves the now-tighter geometry correctly on its own. No snapping code or
   test needed to change. This was worth checking rather than assuming either way: a
   passing suite here is direct evidence, not a guess about tie-break behaviour.
6. Left `equalsWidth` and paren-cell width alone: only "operator cells" were named, and
   `ParenNode` sharing `operatorWidth` is existing, deliberate design (§1.2) — shrinking it
   alongside operators keeps that pairing intact rather than special-casing it apart.
7. Added test coverage for both new behaviours before calling it done: `keymap.test.ts`
   gained a `chainHasEquals` unit-test block plus two `dispatchEditorCommand` tests
   (selecting `=` rejects every key; selecting a non-`=` member of an already-`=`'d chain
   rejects `=` specifically, and confirmed only one equals node exists after), and
   `Keypad.test.tsx` gained a block asserting `keypad-equals`'s `disabled` prop tracks
   `chainHasEquals` for a single selection (group-mode's blanket equals-disable already had
   coverage from before this session).
8. Verified live end to end, not just via the suite: built `dist/`, drove the keypad
   through `1 + 2 =`, selected the `=` cell directly and pressed digit/`()`/operator/`=`
   (member count unchanged before/after, confirming nothing appended), then selected the
   `1` cell and confirmed `keypad-equals` read as disabled (`opacity: 0.35`, the same
   disabled treatment every other greyed key gets) purely from being part of an already-`=`
   chain, not from being `=` itself. Re-measured the operator cell's padding afterward to
   confirm the token change actually took (26dp cell, ~6.6dp padding either side).
9. Full suite (840 tests; the same already-documented load-sensitive
   `snapSearch.profile.test.ts` flaking once under load, clean in isolation — see prior
   entries), `tsc`, and lint all clean. Updated `ARCHITECTURE.md` §1.2 (`operatorWidth`),
   §8.5 (new `=`-disables-once-a-chain-has-one bullet), §8.7 (why `=` is a hard stop rather
   than another append-after-anchor target), and decision #22 in §16, all in the same
   commit as the code.

## A selected group's focus ring merges into one outline

### Session log

1. User asked for a specific visual: when a group (`Select group`/`Select all`) is
   selected, the interior borders between its cells should disappear so the whole thing
   reads as one big selected cell, not a row of individually-ringed ones.
2. Confirmed the actual bug before touching anything: `SelectionFocus.test.tsx` already
   had a test proving every member of a group gets its own `-selection-focus` testID
   (`useNodeSelected` returns true for every id in `groupSelectedIds`), and `Cell.tsx`'s
   `selectionFocus` ring was still a uniform 4-sided `borderWidth` — unlike the band, which
   already had `sideBorderWidths(groupPosition, …)` from the earlier chain-grouping work
   (`2026-08-16`). So two flush, both-selected cells each drew a complete outset ring,
   doubling up a visible white line on the shared seam between them — the band's own
   interior-seam fix never got extended to the ring drawn on top of it.
3. The direct fix — reuse `sideBorderWidths(groupPosition, SELECTION_FOCUS_WIDTH)` for the
   ring, same as the band — is not safe unconditionally. `groupPosition` is a *chain*-
   structural property (start/middle/end/solo), true regardless of what's selected. An
   ordinary single selection (tap one number in the middle of an otherwise-unselected
   chain) still needs a *complete* ring: that cell's neighbours are not selected, so there
   is no seam to merge across, and blindly applying the mask would have silently dropped
   the left/right border off every mid-chain single selection — a real regression, not a
   refinement. The two states share `selected` (`useNodeSelected`) but need different ring
   shapes, and nothing in `Cell` previously distinguished them.
4. Added `useNodeGroupSelected(id)` (`useNodeSelected.ts`) — specifically
   `groupSelectedIds.has(id)`, as opposed to the union `useNodeSelected` already computes —
   and a new `groupSelected` prop on `Cell`, threaded through all six node components
   alongside the existing `selected`. The ring's side-border-width call becomes
   `sideBorderWidths(groupSelected ? groupPosition : 'solo', SELECTION_FOCUS_WIDTH)`:
   `'solo'` always yields a full ring, so an ungrouped selection is byte-for-byte the same
   as before this change. A node can be both the primary keypad target *and* a group
   member (a group's result becomes the continuation target, §8.6) — group membership
   alone decides the ring shape either way, since that cell is still one flush member of
   the "one big cell" the whole group reads as.
5. Corner rounding needed no change — `cornerRadii(groupPosition, …)` on the ring was
   already keyed off the same structural `groupPosition`, and since `Select group` always
   selects a chain's *entire* membership (§8.6 — never a partial subset), the group's own
   start/end coincide exactly with the chain's structural start/end already. Only the
   side-border-width call was missing the group/solo distinction; the corner math was
   already correct for this case by construction.
6. Added test coverage before calling it done: `SelectionFocus.test.tsx` gained a
   3-member group-selection test asserting the exact `borderLeftWidth`/`borderRightWidth`
   pair at each position (start: left border, no right; middle: neither; end: right
   border, no left), plus a companion test proving an ordinary single selection on a
   structurally-middle cell still gets the full ring on both sides — the regression this
   change could most easily have introduced, made explicit rather than left to be noticed
   later.
7. Verified live: built `dist/`, drove `1 + 2 + 3 =` through the real keypad, double-
   clicked a cell to trigger `Select group`, and confirmed by screenshot (full view and a
   tight zoom) that the whole chain reads as one continuous rounded outline with no
   interior lines at any seam — matching the request exactly, not just passing the new
   unit tests' specific assertions.
8. Full suite (842 tests; the same already-documented load-sensitive
   `snapSearch.profile.test.ts`, clean this run), `tsc`, and lint all clean. Updated
   `ARCHITECTURE.md` §8.6 and §11.3, plus decision #23 in §16, in the same commit as the
   code.

None beyond what's in the session log — this was a real but narrowly-scoped gap in
