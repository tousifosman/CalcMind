# 2026-08-03 — The design meets the evidence; P0 and P1 land

> Partly back-filled. The three design rounds are reconstructed from commits `11c1ef1`,
> `4141b4e`, `e7a8f30`; P0 (`08620f9`), P1 (`08de0fc`) and the pull-request sequence are
> first-hand.

A single theme runs through the whole day: **a design derived from a picture is a
hypothesis.** Three rounds of confronting it with the actual reference application
changed the domain model, promoted one interaction from "phase 6 polish" to "the point of
the app", and uncovered an entire headline feature that had been missed. Then P0 and P1
did the same thing at the implementation level — twice, something that type-checked
cleanly did not work at all until it was run.

## Session log

### 1. Grounding the design in observed behaviour (`11c1ef1`)

`tydligapp.com` was unreachable from this environment, but the reference app's own
release screenshots and a detailed published review were not. The design moved from
inferred to observed, and several assumptions did not survive:

- **Linking is communicated by colour identity, not merely by a connector line.** A
  referenced result gains a hue; every reference to it shares that hue; the connector is
  drawn in it. Unreferenced results get no hue. `docs/assets/linking-model.svg` was added
  for this visual language.
- **Continuation is the primary way links get made** (§8.7): with a result selected,
  pressing an operator seeds a new chain that references it. This is not phase-6 polish —
  it is the ordinary path, and the plan was amended to say so.
- **Parentheses ship in v1** (§10.2). They sit on the reference keypad, so users expect
  grouping; retrofitting would cost a node kind plus a schema migration.
- **Number display is locale-formatted while storage stays canonical** (§10.3), so
  documents survive being opened in another locale.
- Keypad, selection and context menus documented from observation, which closed the open
  "keypad model" question.

Two named weaknesses of the reference app were deliberately designed *out* rather than
copied: it has no snapping, and it reports a broken reference as a bare `?` with no
explanation (§11.2).

### 2. Extending from the mature 1.6 release (`4141b4e`)

The material used in round 1 was from versions 1.0/1.1. Getting to 1.6 required solving
an environment problem first (see Findings — TLS), after which the developer's final
screenshots were retrievable via the iTunes lookup API.

What 1.6 changed:

- **Labels are a headline feature**, rendered above the cell in the value's identity hue,
  and applied to *results* as often as to inputs. `label` moved from `NumberNode` to the
  node base.
- **Dependencies fan out.** One value feeding four consumers, with four connector curves
  radiating from it. Edges are therefore keyed by `(source, reference)`, not by source.
- Extension path documented for `^`, postfix/prefix operators and function application —
  all absorbed by precedence climbing without restructuring the parser.
- **Graphs are canvas objects that sweep a referenced input.** Recorded as the clearest
  argument for the dependency structure being a real graph: a graph node is just another
  consumer.

### 5. P1 — Canvas pan and pinch-zoom (`08de0fc`)

The infinite viewport per §7:

- `src/canvas/coords.ts` — `worldToScreen` / `screenToWorld`, property-tested with
  `fast-check` as exact inverses.
- `src/canvas/Canvas.tsx` — one-finger pan, pinch-to-zoom about the pinch centroid, zoom
  clamped to `[ZOOM_MIN, ZOOM_MAX]`. Gesture updates drive Reanimated shared values every
  frame; the Zustand store is written **only on release** (pan/pinch) or after a 200 ms
  debounce (wheel), per §11.4's "commit only on release" rule — which is what keeps
  viewport interaction out of undo history. Web gets scroll-to-pan and
  ctrl/cmd+wheel-to-zoom-at-cursor.
- `src/app/AppShell.tsx` — `GestureHandlerRootView` + `Canvas`. `App.tsx` finally lost the
  placeholder calculator UI scaffolded on day 1.

Rendering structure worth remembering: an **outer** view carries the screen-space
translate, an **inner** view nested inside it carries the scale (`transformOrigin: '0 0'`),
and children will be positioned with plain `left`/`top` equal to their *world*
coordinates. Because the translate wraps the scale, a world point lands at exactly
`worldToScreen(x, y)` — the component mirrors `coords.ts` structurally instead of
duplicating its arithmetic.

Getting this to actually run, as opposed to compile, took five separate fixes. All are in
Findings below, because each is a durable fact about the toolchain.

### 10. Development plan split out and expanded

`ARCHITECTURE.md` §15 moved to `docs/DEVELOPMENT_PLAN.md`, P0/P1 struck through, and P2–P7
expanded from one-line phase criteria into 53 tasks, each carrying an objective, the architecture
sections it implements, the files it touches, its dependencies, and tickable acceptance criteria.

Built once, reverted at the user's request because it had been done under a model they hadn't
intended to use for it, then rebuilt. The second pass kept the same shape deliberately — the shape
was not what was wrong — and found one thing the first had missed: §8.6's long-press context menus
had no task at all, despite being the only route to `Delete` and to `Select group`, both of which
P2's own acceptance criteria and P3.7 depend on. Ordinary expansion-of-a-summary work, and the gap
was invisible without walking §8 line by line.

Three structural choices worth recording:

- **§15 stays as a numbered stub** rather than renumbering §16 and §17 up. Those are cited from the
  journal, from commit messages and from inside `ARCHITECTURE.md` itself, so renumbering trades
  every existing citation for tidiness.
- **Tasks cite architecture sections instead of restating them**, so the plan cannot drift into a
  second competing description of the design — the same reasoning that reduced
  `docs/journal/README.md` to a pointer earlier in the day.
- **Each phase ends with a "Phase exit check" quoting §15's original criteria verbatim.** The
  expansion is auditable against what it replaced: if every task is ticked and the exit check still
  fails, the expansion missed something. This is what would have caught the §8.6 gap mechanically.

Ordering within phases puts dependencies first, which departs from a naive reading of §15 twice:
the locale display/storage boundary (§10.3) leads P2, because it is the one thing that corrupts
documents if retrofitted rather than designed in; and text measurement (§8.1) precedes the node
views, because P3's layout pass needs the same `widthOf`.

### 11. P2.1 — the locale display/storage boundary (`src/engine/format.ts`, `numeric.ts`)

Implemented `isCanonicalRaw` / `splitRaw` (locale-independent, regex-based) and
`formatForDisplay` / `parseUserInput` / `decimalSeparatorFor` (the `Intl.NumberFormat`
boundary), plus a `fast-check` round-trip test across four locales (`en-US`, `de-DE`,
`fr-FR`, `en-IN`).

The one real design decision: `Intl.NumberFormat.prototype.format` gained a
precision-preserving string overload in a recent edition of ECMA-402, which would have let
grouping run on the raw digit string directly rather than through a JS `number` — no
`Number.MAX_SAFE_INTEGER` ceiling at all. Not used. See Findings and revision 13 for why.

### 12. P2.2 — text measurement and node width (`src/chains/measure.ts`)

`widthOf` per §8.1: symbol cells (`operator`, `paren`, `equals`) return a fixed design
token; number and result cells measure their *displayed* string (§10.3, so `locale` is a
parameter) plus `2 × numberPaddingX`, floored at `nodeHeight`.

The real question was how to measure text at all. Neither platform offers what this needs:
React Native has no synchronous `measureText` for an arbitrary string outside rendering a
component and waiting for `onLayout`, and a DOM canvas (`measureText`) only covers web — the
task's own acceptance criteria rule that out explicitly ("works identically on web and
native"). A rendered-and-measured approach is also asynchronous, which conflicts with §8.1's
requirement that a chain re-flows *in the same commit* as the edit that changed a member's
`raw` — there is no frame in which layout can wait on a native measurement pass.

`measure.ts` instead sums a fixed per-glyph advance-width table (digits treated as
tabular/equal-width, separately-sized punctuation and signs), scaled linearly for
`fontSize`. This is calibrated by inspection, not by rendering and sampling a real font — the
same epistemic status as the §11.1 identity palette before P6.8 checks it. `ReferenceNode` is
left unhandled (throws): it isn't created before P6, and sizing it needs the target node's
resolved value, which this signature has no document map to look up. Ticked P2.2's boxes in
`DEVELOPMENT_PLAN.md` with a pointer back here.

## Findings

### Environment

- **Chromium cannot reach HTTPS through the egress proxy with default TLS settings.** Its
  TLS 1.3 ClientHello is reset by the MITM proxy. `--ssl-version-max=tls1.2` fixes it
  **without weakening certificate verification** — the right lever, as opposed to
  disabling verification.
- **`tydligapp.com` is unreachable by any client from here**, not just by `fetch`: the
  origin serves no TLS on 443, and plain HTTP to that host is refused by the egress
  allowlist. A browser hits the same wall. Do not retry it.
- **The iTunes lookup API is a viable source for an app's official screenshots**,
  including for older versions — useful when a product site is unavailable.
- A user-supplied **MHTML archive** is a complete offline substitute for a site: unpacking
  it yielded 34 images including the developer's own feature illustrations.

### Agent instruction files

- **`AGENTS.md` is the cross-tool convention**, read by Cursor, Copilot and Codex among
  others. It is plain markdown with no frontmatter, at the repo root.
- **Claude Code does not read it.** It reads `CLAUDE.md` only. A claim repeated across a
  number of third-party guides — that Claude Code falls back to `AGENTS.md` when no
  `CLAUDE.md` exists — is false and is not in the official documentation. The supported
  bridges are a `@AGENTS.md` import line in `CLAUDE.md`, or `ln -s AGENTS.md CLAUDE.md`.
  **Prefer the import:** creating a symlink on Windows requires administrator rights or
  Developer Mode, so the symlink is not portable.
- **Cursor also supports `.cursor/rules/*.mdc`** — YAML frontmatter (`description`, `globs`,
  `alwaysApply`) controlling activation, subdirectories allowed. Precedence is Team Rules >
  Project Rules (`.cursor/rules/`) > User Rules. Rules apply to Agent Chat only; they do not
  affect Tab completion or inline edit.
- **An `alwaysApply: true` rule is a per-request token tax**, since it loads on every single
  request — the guidance is to keep such rules under ~200 words. Reason enough to keep
  `calcmind.mdc` a pointer rather than a copy of anything.
- `.cursorrules` at the repo root is the legacy form: still honoured, deprecated, not worth
  adding now.

### Toolchain

- **`react-native-reanimated` v4 + `react-native-gesture-handler` v3 is broken under
  webpack.** That pairing depends on the newer `react-native-worklets` package;
  reanimated's own hook barrel (`hook/index.js`) throws in that combination, and because
  it is a barrel, **the first failure silently kills every export after it** — including
  `useSharedValue`, which then reads as `undefined` with no error pointing at the cause.
  Pinned to reanimated 3.19.5 + RNGH 2.32.0, the pairing reanimated's own
  `devDependencies` test against, and dropped `react-native-worklets`.
- **Webpack must be told about two globals Metro provides for free:**
  `__DEV__` (via `DefinePlugin`) and `process` (via `ProvidePlugin` → `process/browser`;
  webpack 5 dropped automatic Node polyfills, and reanimated reads the bare `process`
  global with no `typeof` guard, e.g. `PlatformChecker.js`).
- **`publicPath` must differ by mode.** Relative (`'./'`) in production for GitHub Pages
  subpaths — but webpack-dev-server needs an **absolute** `'/'` to route to its in-memory
  bundle. This refines, and partly contradicts, the day-1 finding that relative paths are
  simply correct.
- **`#root { display: flex }` is mandatory for a react-native-web app.** Flex properties
  only apply *inside* a flex container, so without it every `View`'s `flex: 1` resolves to
  nothing and the entire tree renders at 0×0 — silently, with no error. This gap had
  existed since day 1 and only surfaced the first time the web build was opened in a
  browser rather than type-checked.
- **Neither reanimated nor gesture-handler has a working jest-environment fallback** for
  the native/UI-thread runtime they normally drive. Manual mocks in `__mocks__/` supply
  just the surface the canvas uses. Their ESM-only builds also need whitelisting in
  `transformIgnorePatterns`.
- **RN's jest preset adds a `"react-native"` export condition** for parity with Metro,
  which routes some packages (`immer`) to an ESM bundle Jest won't transform by default —
  so a package with a perfectly good CJS build can still need whitelisting. `nanoid` and
  `fast-check` are ESM-only outright.

- **TypeScript's lib types lag the runtime for `Intl.NumberFormat`.** `lib.es2023.intl.d.ts`
  types `format()`'s string overload as `StringNumericLiteral` (a template-literal type), not
  `string` — so even with that lib included, a plain `string` variable holding a numeral still
  fails to type-check against it. `@react-native/typescript-config`'s `lib` array doesn't
  include `es2023.intl` at all, so the overload isn't visible to `tsc` in this project
  regardless. **Misleading symptom:** the compiler error names only the `number | bigint`
  overload, giving no hint that a newer, string-accepting one exists upstream.
- **Whether Hermes implements that string-precision overload is unverified, and this
  environment cannot check.** No Android/iOS emulator is available here, and the web build
  exercises the browser's engine, not Hermes. `docs/journal/GUIDELINES.md`'s own rule —
  verify before claiming — cuts the other way too: don't build on an engine behaviour you
  can't verify either. `groupInteger` (`format.ts`) stays inside `Number.isSafeInteger` and
  falls back to ungrouped digits beyond it, so correctness never depends on the answer.

### Correctness

- **A no-op command was not reliably detected as one.** `applyCommand` stamped `updatedAt`
  unconditionally *before* checking for an empty immer patch set, so "a no-op recipe
  records no history" only passed when two `Date.now()` calls landed in the same
  millisecond — a flaky test masking a real bug. Fixed by filtering the `updatedAt` patch
  out of the emptiness check. **Generalisable: any unconditional timestamp write defeats
  patch-based change detection.**

## Knowledge revisions

**1. Identity hue was gated on the wrong condition.**
*Previously believed:* a value gains an identity hue when something references it.
*Now known:* identity is granted by being referenced **or** by being labelled. The
developer's own labels illustration colours three plain *inputs* purely because they
carry labels.
*What established it:* the product site's feature illustrations (`e7a8f30`).

**2. A label is not a property of a cell.**
*Previously believed:* `label` belongs to a `NumberNode`.
*Now known:* it belongs to the **identity**. The compound-interest screenshot renders
"Initial Deposit" above the declaration *and* above both references to it, so editing a
label must update every cell sharing that identity. `label` moved to the node base.
*What established it:* the 1.6 screenshots (`4141b4e`), confirmed by the site (`e7a8f30`).

**3. Value sliders were missing from the design entirely.**
*Previously believed:* the feature set was complete.
*Now known:* selecting a number raises a slider popover; scrubbing cascades through the
whole dependent subgraph live, including graphs. Specified in §8.8, with the gesture
coalesced into **one** undo entry and autosave suppressed until release. Scheduled as
**P6b**, not left to polish, because this is what makes the dependency graph *felt* rather
than merely correct.
*What established it:* the product site's own feature list (`e7a8f30`).

**4. Implicit multiplication is real, but narrower than assumed.**
*Now known:* a factor followed by an open paren multiplies (`10,000 ( 1 + … )`), while two
adjacent numbers stay **invalid** — `12 34` is far more likely a mis-snap than a product.
*What established it:* observed reference behaviour; recorded as decision #4.

**5. Linking is a colour language, not a line.** See session log §1. The connector alone
was assumed sufficient; hue identity is the primary carrier, and the design now shows
*all* connectors rather than only the selected one (decision #13), because the reference
app hides them and its own review names that as confusing.

**6. Continuation is the product, not a phase-6 feature.**
*Previously believed:* linking is late-phase work.
*Now known:* continuation is how users normally create links, so if P6 slips the app ships
as "a canvas of unrelated sums and loses the point". The plan records pulling continuation
forward into P4 as the mitigation.

**7. Dependency edges are 1-to-N.**
*Previously believed:* keying an edge by its source value was sufficient.
*Now known:* one value commonly feeds several consumers with a connector per consumer, so
edges are keyed by `(source, reference)`.

**8. "The web build succeeds" did not mean "the web build works."**
*Previously believed:* green `tsc` + a successful `build:web` meant the web target was
healthy. It had never once been opened in a browser.
*Now known:* it rendered 0×0. Every P1 acceptance check is now run in a real browser (dev
server *and* production build) before the phase is called done.

**9. Newest dependency versions are not the safe default.**
*Previously believed:* install current majors of reanimated and gesture-handler.
*Now known:* pin the pairing the library itself tests against. Two majors ahead cost a
debugging session on an error that pointed nowhere near its cause.

**10. A merged pull request does not pick up later commits on its branch.**
*Previously believed and asserted to the user:* PR #4 covered P1 as well, since P1 landed
on the same long-lived branch.
*Now known:* PR #4 merged at `39af473` with `08620f9` (P0) as its parent — P1 (`08de0fc`)
was pushed after the merge and was **not** on `main`. A merged PR is finished and cannot
track new work.
*What established it:* the user said `main` didn't have the latest code, and
`git log origin/main` confirmed it. PR #5 opened for P1.
*Standing lesson:* verify against `origin/main` before claiming work has landed. "It's on
the branch" and "it's in `main`" are different claims, and only the second one deploys.

**11. Agent instructions were written for one tool without checking whether a shared
convention existed.**
*Previously believed:* Claude Code is the consumer, so `CLAUDE.md` is where project
instructions go.
*Now known:* `AGENTS.md` is the cross-tool convention and Cursor reads it natively, so the
substance belongs there with per-tool files as pointers. Getting this wrong would not have
failed loudly — it would have quietly given Cursor no instructions at all, which is the
same failure mode as revision 8: absence of an error read as success.
*What established it:* the user said they would also be using Cursor; the file conventions
were then verified against current sources rather than recalled, which is what caught the
false "Claude Code falls back to `AGENTS.md`" claim before it was built on.
*Standing lesson:* when writing a config file whose format is outside what you can verify
locally, check it. A config in a stale or wrong format produces no error, just silence.

**12. `ARCHITECTURE.md`'s own status banner had been wrong for two phases.**
*Previously believed:* the design document was current, since its design sections were being kept
in step as the design changed.
*Now known:* its header still read "design proposal, not yet implemented… the repository currently
holds a bare React Native scaffold with a conventional keypad calculator in `App.tsx`" — false from
the moment P1 deleted that calculator. Several sessions read straight past it.
*What established it:* noticed while moving §15 out, not by anything that checks.
*Standing lesson:* a document's **status claims** go stale in a way its body does not, because
nothing you do while editing the body forces you to re-read the header. When a phase lands, re-read
the top of every document that describes project state — not only the sections you changed.

**13. "Renders through `Intl.NumberFormat`" does not mean "hand it the raw string."**
*Previously believed:* `formatForDisplay` could pass `raw`'s integer part straight to
`Intl.NumberFormat.prototype.format`, since a recent ECMA-402 edition added a
precision-preserving string overload for exactly this.
*Now known:* that overload types as `StringNumericLiteral`, not `string`, so it fails to
compile even with the right `lib` entry — and this project's `lib` array doesn't carry that
entry regardless. More importantly, whether Hermes (React Native's engine) implements the
newer spec text can't be checked in this environment, and building display correctness on
an unverifiable engine behaviour is the same mistake as trusting `tsc` for the web target
(revision 8). `groupInteger` converts through a plain JS `number` and only groups within
`Number.isSafeInteger`, falling back to ungrouped digits beyond it.
*What established it:* the `tsc` error naming only the `number | bigint` overload, then
reading `lib.es2023.intl.d.ts` directly to find the string overload's actual type.
*Standing lesson:* a spec addition being real doesn't make it available — check both the
type declarations in *this* project's `lib` array and the target runtime, not just whether
the feature exists somewhere.

## Addendum — P2.1 review corrections (PR #23)

### Session log

14. Code-review feedback on `format.ts` identified two problems and addressed both:

    - **Separator caching** (`decimalSeparatorFor`, `groupSeparatorFor`): both functions
      constructed a fresh `Intl.NumberFormat` on every invocation. Since both run on every
      keystroke in the display layer, module-level `Map` caches were added; each locale tag
      is resolved at most once per session.

    - **`parseUserInput` silent mis-normalisation** (`bf21500`): when the locale group
      separator is `'.'` (e.g. de-DE), blindly stripping it would accept `'13.5'` and
      return `'135'` — a silently different number. Added a validation step: when
      `group === '.'`, the integer portion is split on `'.'` and each segment checked
      (first 1–3 digits, subsequent exactly 3 digits); failure throws before stripping.
      Regression tests added to lock the boundary.

### Findings

#### Correctness

- **Intl group separator can alias the canonical decimal point.** In de-DE, `'.'` is the
  thousands separator and `','` is the decimal. Blindly calling `text.split('.').join('')`
  on a de-DE group then checking `isCanonicalRaw` would accept `'13.5'` (a valid
  canonical decimal!) and return `'135'`. The misleading symptom: the existing tests only
  exercised valid grouped input (`'1.234,56'`) and the round-trip property, neither of
  which exposes inputs that happen to look canonical after stripping. The guard must check
  placement before stripping, not just check canonicality after.

### Knowledge revisions

**14. `parseUserInput` was incorrectly passing a class of de-DE inputs.**
*Previously believed:* strip the group separator, replace the decimal separator with
`'.'`, then reject if the result isn't canonical — that three-step sequence was thought
sufficient.
*Now known:* when `group === '.'`, an input like `'13.5'` passes through stripping as
`'13.5'` then passes `isCanonicalRaw` unchanged, yielding `'135'` — the wrong number
with no error. The guard must validate group-separator placement *before* stripping, not
merely validate the result *after*.
*What established it:* reviewer analysis of `format.ts:66-79`; the alias between de-DE's
group glyph and canonical `'.'` is the mechanism; the misleading symptom is that the
existing round-trip property test never generates inputs with wrong group placement, so it
passed.
*Standing lesson:* when a locale separator shares its glyph with a canonical character,
stripping and re-validating is not enough — placement must be checked in the original
locale context.

## Addendum — P2.3 Node CRUD commands (issue #11)

### Session log

15. Implemented the P2.3 commands: `addNumberNode`, `addOperatorNode`, `addParenNode`,
    `addEqualsNode`, `setNodeRaw`, `deleteNode` in `src/store/commands.ts`, backed by new
    node factories (`createNumberNode`/`createOperatorNode`/`createParenNode`/
    `createEqualsNode`) in `src/model/factories.ts`. Added `ParenSide` as a named type
    alongside the existing `OperatorSymbol`, since the paren factory needed the same union
    `ParenNode` already declared inline.

    `setNodeRaw`'s 500ms coalescing (§13) is implemented entirely in the command, not in
    `documentStore.applyCommand`: a module-level `lastRawEdit` (node id, timestamp, and the
    undo-stack length right after it landed) lets a follow-up call detect "still the same
    edit burst" without the store knowing coalescing exists. When it matches, the two most
    recent undo entries are popped and replaced with one whose forward patches are the
    concatenation `[previous, latest]` and whose inverse patches are `[latest⁻¹,
    previous⁻¹]` — correct because every `setNodeRaw` patch is a single same-path `replace`
    on `raw`, so patches never need reordering relative to each other, only concatenating in
    the right direction per list.

    `deleteNode` removes the chain's own empty shell along with the dangling member id:
    the schema's `Chain.members` is documented `1..*` (§6 mermaid diagram), so a chain
    reduced to zero members is deleted rather than left behind as a construct nothing else
    in the model expects to exist.

    12 new tests covering undo/redo per command, the no-op case, and three coalescing

### Findings

#### Correctness

- **Coalescing lives at the command layer, not the store.** `documentStore.applyCommand`
  stays a plain "one recipe → one undo entry" primitive; `setNodeRaw` merges the top two
  undo-stack entries itself after calling it. This keeps the store's undo/redo logic free
  of per-command special cases, at the cost of each coalescing command needing to
  reimplement the merge. §13 also specifies a coalesced gesture for the P6b value slider —
  if a third coalescing command shows up, that duplication is the signal to lift the
  pattern into the store as a `coalesceKey` parameter on `applyCommand` rather than before.

### Open threads

- **Coalescing pattern may need to move into the store.** See the finding above — currently
  fine as one instance in `setNodeRaw`; revisit if P3 (drag) or P6b (slider) need the same
  thing and the module-level-tracking approach gets copy-pasted a second time.
