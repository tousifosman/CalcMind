## Link-creating keys signal themselves; `=` selection stops looking more alive than it is

### Session log

1. Three related keypad requests in one message, all about the gap between what a key
   *looks like* it will do and what it *actually* does when pressed:
   - An operator on a selected result (or free number) already spins off a new linked
     cell (§8.7 continuation) — nothing about the key itself said so beforehand.
   - Selecting `=` (§9's hard stop, `2026-08-17`) correctly rejects every key except an
     operator, but the keypad never greyed out the ones it rejects — they still rendered
     enabled, and pressing them silently did nothing.
   - `()` on a selected result was a pure no-op, inherited from the `result` block's
     blanket `return` for anything that isn't `operator`.
2. Read all three as one theme before touching code: each is either a key whose visible
   state lies about what it does, or a key that does nothing when the same "make a link"
   logic already used elsewhere would give it an obvious, consistent job. Scoped the fix
   accordingly rather than three unrelated patches.
3. **Link tint.** Added `operatorCreatesLink`/`parenCreatesLink` to `Keypad.tsx`, and an
   `accentKeyLink` style (`identityHues[0]`, the same blue `Create link`/`linkKey`
   already use — reused, not a new colour, so the two chrome pieces read as one signal).
   `operatorCreatesLink` is true for a selected result, a selected *free* number not
   being edited (mirrors `dispatchEditorCommand`'s own continuation-vs-extend-in-place
   split exactly — a number already in a chain, or one being typed into, extends in
   place instead), or a `Select group`/`Select all` set containing a result (identical
   `continueFromValue` path, every operator). `parenCreatesLink` is narrower — true only
   for a selected result, since `()` on a free number groups within its own new chain
   rather than linking (pre-existing, unrelated behaviour, left alone).
4. **`=` selection now greys out what it rejects.** Added `'equals'` to
   `selectionBlocksDigits` and `selectionBlocksNumberEditing` in `Keypad.tsx` — this was
   the actual gap behind "all the buttons look activated": `2026-08-17`'s dispatch-level
   hard stop was real and tested, but nothing in the keypad's own disabled-state
   computation had ever been told about it, so the UI and the dispatch function
   quietly disagreed about which keys did anything. First full verification pass (live,
   not just the suite) caught this directly: scripted a browser session, selected `=`,
   read every key's `aria-disabled` attribute, and found digit/decimal/sign/paren/
   `Create link` all reporting *not* disabled despite `dispatchEditorCommand` already
   rejecting every one of them. The operator column deliberately stays live — see next.
5. **An operator on selected `=` converts it, in place, instead of doing nothing.**
   `2026-08-17`'s hard stop treated every command the same (reject); this session gives
   the one command that has an obvious, useful meaning here real behaviour instead.
   Added `convertEqualsToOperator(equalsId, op)` (`store/commands.ts`), modelled closely
   on `appendOperatorAndNumber`/`deleteNode`: removes the equals node from `chain.members`
   and inserts a fresh `[operator, empty number]` pair at exactly the position `=` held,
   in **one** `applyCommand` draft mutation — not two sequential top-level commands
   (delete, then append), specifically so undo can't strand the chain mid-conversion
   (equals gone, new operator not yet there, or the reverse). The paired result
   disappears for free: `finalizeChain`'s existing `recomputeChain` already drops a
   chain's result the moment it has no `=` (confirmed by reading `engine/graph.ts`
   directly rather than assuming — this is the same mechanism a bare `deleteNode(equalsId)`
   already relies on, tested since a `2026-08-16`-adjacent continuation test).
6. **`()` on a selected result wraps a new link in parens.** Added
   `continueFromValueWithParens(valueNodeId)` (`store/commands.ts`), the same
   `continuationAnchor` placement `continueFromValue` uses, but building
   `[openParen, reference, closeParen]` instead of `[reference, operator, number]` — no
   operand to focus for typing, so the caller selects (doesn't edit) the close paren,
   which is enough on its own for a following operator or `=` to extend the new chain in
   place (the same append-after-anchor targeting a selected paren already gets
   elsewhere — no new plumbing needed for that part).
7. Added test coverage at every layer before calling any of the three done:
   `commands.test.ts` gained dedicated `describe` blocks for both new command functions

   existing equals-hard-stop tests were updated in place (their old blanket "every
   command no-ops" assertions were the exact thing decision #24 changed on purpose, not

   dispatch; `Keypad.test.tsx` gained a link-tint block (result / free number / editing
   number / chain-member number / live reference / group-with-result / nothing-selected,
   seven cases) and an equals-selection block asserting the exact enabled/disabled set
   per key, including that history (undo/redo/backspace) stays live throughout.
8. Verified live end to end for all three, not just the suite: built `dist/`, drove

## Backspace stops being a blanket delete-the-cell

### Session log

1. Three backspace requests, same session as the keypad-signalling work above but a
   separate message: a selected result should refuse backspace entirely (it's derived,
   not user input); a selected operator should delete and land the selection on its
   left neighbour instead of fully deselecting; a selected *number* should erase one
   digit at a time — whether or not it's actively being edited — and only delete the
   cell once it's already empty, at which point it should also land on the left
   neighbour.
2. Read the existing code before changing it, since two different branches already
   existed for "backspace on a number" (`editingNumber` truthy vs. a plain
   tap-selected, not-editing number), and they behaved completely differently — the
   editing path already trimmed one character at a time (close to what the number
   request wanted), the non-editing path deleted the whole cell immediately.
   `editingNumber` turned out to be a reference to the *same* node object as
   `selectedNode` when they match, so `selectedNode.raw` reads identically either way —
   the two paths could genuinely merge into one, not just be made to look similar.
3. Added `leftChainNeighborId(node)` (`keymap.ts`) — the same chain-index-minus-one
   lookup `moveSelectionAlongChain` (P7.2 arrows) already computes, factored out since
   backspace-on-operator and backspace-on-empty-number both need it now.
4. Rewrote the `backspace` case in `dispatchEditorCommand` as four kind-specific
   branches in front of the old catch-all (delete + full deselect, now only reached by
   paren/equals/reference — nobody asked for those to change too):
   - `result` → return, no-op. Group-mode backspace (`deleteGroup`) is a separate branch
     entirely and stays untouched even when the group contains a result — deleting a
     whole finished formula as a unit is still a deliberately different, still-wanted
     command from backspacing the read-only answer cell on its own.
   - `number` → non-empty `raw`: trim one character, call `editNumberNode` unconditionally
     (harmless when already editing — every one of its effects is idempotent against the
     same node) so a tap-selected number becomes the live edit target the same way a
     digit press already does. Empty `raw`: delete and land on `leftChainNeighborId`,
     or fully deselect if there isn't one.
   - `operator` → delete and land on `leftChainNeighborId`, or fully deselect.
5. Added `backspaceDisabled` to `Keypad.tsx`, gating the on-screen key visually the same
   way `dispatchEditorCommand` now gates it functionally — `!groupMode && selectedKind
   === 'result'` (the `!groupMode` guard is what keeps Select-group's own
   delete-the-whole-thing backspace live even over a result-containing group).
6. Added test coverage before calling any of the three done: `keymap.test.ts`'s
   pre-existing "backspace still deletes a selected result" test was flipped in place
   (title and assertions both — this was the exact behaviour the request changed on
   purpose) and gained two new `describe` blocks (number-trim-then-delete-and-land, four
   cases including the free-chainless-number fallback; operator-lands-on-left-neighbour,
   two cases including no-neighbour fallback). `Keypad.test.tsx` gained a
   `backspaceDisabled` block covering the single-result case, an unaffected
   selected-number/nothing-selected case, and the Select-group-with-a-result case
   staying enabled.
7. Verified live end to end, not just the suite: built `dist/`, drove the real keypad
   and canvas taps. Selected a finished result and confirmed backspace's own
   `aria-disabled` reads `"true"` and the chain is byte-for-byte unchanged after
   pressing it. Selected an operator mid-chain and confirmed the selection ring lands on
   the number to its left after one backspace. Built `12 + 5`, tap-selected the
   not-yet-edited `12`, and walked backspace through three presses: `12` → `1` (now
   editing, confirmed via the real `<input>` element's `value`, not just the cell's
   rendered text — the non-editing `<Text>` carries no separate testID, so the first
   read needed a fallback path in the verification script itself) → `` (still selected,
   still present) → cell deleted entirely, nothing selected (no left neighbour, since it
   was the chain's first member) — screenshotted the end state showing `12` gone and
   `+ 5` left behind, matching exactly.
8. Full suite (869 tests), `tsc`, and lint all clean on the final pass. Updated
   `ARCHITECTURE.md` §8.5 and added decision #25 in §16, in the same commit as the code.

## Value slider follow-up: fixed a pin-toggle resize bug, connector colour, Step field + vibration

### Session log

1. User feedback on 2026-08-17's `Show slider`/pin feature (PR #158, live preview
   deployed): checking `Keep open` visibly made the popover *bigger*. Also requested: the
   drag bar should appear/disappear on check/uncheck rather than the container itself
   coming and going (which was the resize bug's actual cause), tighten the space around
   it since the bar's own footprint is small; the connector line should match the
   popover's own colour rather than the cell's identity hue; and a Step field (default
   `0.1`) between the range bounds, with the phone vibrating once per step while
   dragging.
2. **Root cause of the resize bug**: `DragHandle` was only mounted in the tree at all
   when `pinned` (`{pinned ? <DragHandle .../> : null}`) — its own padding/margin/bar
   height (originally ~20px) only entered the popover's flex layout once that condition
   flipped true, so the box visibly grew. Fixed by always mounting the container at a
   fixed size and moving the pin-dependent part down to paint only: the bar's opacity
   toggles with `pinned` (via two static `StyleSheet.create` entries,
   `dragHandleBarVisible`/`dragHandleBarHidden`, rather than an inline conditional style
   object — the latter tripped `react-native/no-inline-styles`, which this codebase
   otherwise keeps clean), and the drag gesture itself is disabled while unpinned via
   `Gesture.Pan().enabled(pinned)` rather than the whole `GestureDetector` being absent.
   Also reduced the container's own padding (`paddingVertical` 6→3, `marginBottom` 4→2)
   per the request to tighten the reserved space now that it's always visible.
3. Connector colour: was `rolePalette.number.border` (the cell's identity hue, teal for a
   plain number) — changed to a new `POPOVER_BORDER_COLOR` constant (`#D1D5DB`, the same
   gray `boundInput`'s border and the drag bar already used), and gave the popover itself
   an explicit 1px border in that same colour so the line has something on the window to
   visibly terminate at, rather than just picking a new colour with nothing to tie it to.
4. Step field: a new `Step` labelled input, positioned between the min/max bound inputs
   in `boundsRow` (replacing what had been a bare flex spacer). Backed by its own
   `step`/`stepText` state pair, mirroring the existing `range`/`minText`/`maxText`
   pattern exactly (numeric state used for computation, text state for the live draft,
   `commitStep` validating and reverting on blur/submit same as `commitBound`) — reset to
   the `0.1` default whenever the slider (re)opens on a different node, same lifecycle as
   the inferred range.
5. Continuous dragging now quantizes to the Step grid rather than landing on an arbitrary
   fraction: added `quantizeToStep(value, step, range)` to `inferSliderRange.ts`, rounding
   to the nearest multiple of `step` measured from `range.min` via `Decimal` (not plain
   float division — `0.33 * 10` is `3.3000000000000003` in JS, and the quantizer's own
   `Decimal` arithmetic snaps that back to an exact `3.3` rather than propagating the
   noise). Tap's existing integer-snap mode is untouched and stays the separate, coarser
   affordance it always was (§8.8's original Tydlig-observed behaviour) — Step only
   governs continuous dragging.
6. Vibration: `Vibration.vibrate(10)` (a short tick, not `vibrate()`'s 400ms default —
   that would read as one continuous buzz across many step crossings) fires from
   `writeFraction` exactly when the quantized value differs from
   `lastQuantizedValueRef.current`, a ref rather than component state or the `value` prop
   for the same reason `rangeRef`/`integerSnapRef` already are refs in this file: it has
   to be read-and-written synchronously inside the gesture callback itself, not depend on
   a React re-render having landed between two fast `onUpdate` calls in one native
   gesture. Confirmed react-native-web's `Vibration.vibrate` (`window.navigator.vibrate`
   under 'vibrate' in navigator) is safe to call under this project's jest preset with no
   extra setup — spied via `jest.spyOn(Vibration, 'vibrate')` in tests, never the real
   native call.
7. Full verification: `tsc`, lint (one `no-inline-styles` warning surfaced and was fixed
   as above, not suppressed), and the full suite (854 tests, up from 841) all clean.
   `build:web` emits `dist/`. Verified live against the served build with Playwright: the
   popover's screen bounding box is pixel-identical before and after pinning; the Step
   field shows `0.1` by default in the right position; the connector renders as a thin
   gray line (matching the popover's own new border) rather than teal; a real (multi-step,
   not a single-pixel) drag on a `0, 10` range landed on a clean `3.7`, confirming the
   step grid actually governs a real gesture and not only the unit-level math.
8. `docs/ARCHITECTURE.md` §8.8 rewritten for the Step field, vibration, the fixed-size
   handle, and the chrome-coloured connector, in the same commit as the code; decision
   #22 added to §16 citing #21's own resize regression.

### Findings

**Conditionally mounting a component to gate a *visual* toggle also gates its layout
footprint, even when that wasn't the intent.** `{pinned ? <DragHandle/> : null}` reads as
"show/hide an affordance," but React (any renderer) applies that at the mount/unmount
level - the component's own padding and children only enter the parent's flex layout
once mounted, so a flex `alignItems`/`padding`-bearing wrapper appearing and disappearing
necessarily resizes its parent unless the parent has a fixed height that ignores it. The
fix pattern is general and worth naming: when a toggle should change *paint* only (a bar
becoming visible, a gesture becoming active) without changing *layout*, keep the
component mounted always and drive the toggle through props into styles/opacity/`enabled`
instead of through JSX presence. The same 2026-08-17 session that introduced this bug
already used the *correct* version of this pattern for the connector line (an absolutely
positioned sibling, conditionally rendered - harmless, since absolute positioning removes
it from flex flow entirely) right next to the *wrong* version for the handle (a normal
flex child) - the same conditional-render idiom is safe or unsafe purely depending on
whether the thing being toggled participates in layout, which is easy to miss reviewing
the diff in isolation.

### Knowledge revisions

**1. The three pinned behaviours (dismiss-suppression, connector, drag) reading as one
`pinned` flag (2026-08-17, decision #29) was correct, but incomplete: a fourth thing
implicitly followed pinned too, and got it wrong.**
*Previously believed:* gating the connector's render and the drag handle's *render* both
on `pinned` was the natural continuation of "one flag drives three behaviours."
*Now known:* the handle's gesture *behaviour* (draggable or not) should follow `pinned`,
but the handle's own *mounted presence* must not - that has to stay constant so the
popover's size stays constant regardless of `pinned`. The connector was fine to
conditionally render because it's `position: absolute` and therefore already outside the
popover's flex flow; the handle isn't, so the identical-looking pattern broke for it.
*What established it:* user-reported live resize; reproduced by inspecting the two
screenshots from 2026-08-17's own verification pass side by side, where the popover's
top edge visibly shifted a fixed offset when `Keep open` was checked - a difference that
existed in the shipped PR and was not caught by that session's own live verification,
because the verification script never compared the popover's screen bounding box before
and after pinning, only that the check-related testids appeared/disappeared.
Standing lesson: when a live-verification pass in this project checks "does X appear,"
it should also check "does everything *else* stay where it was" for exactly this class
of bug - a Playwright bounding-box comparison catches what a testid-presence assertion
cannot.

**A solid-coloured square swapped in for "checked" reads as a colour change, not a
tick, regardless of how obviously it's meant to be one.** The prior mark was
technically present and technically differently coloured when checked - functionally
correct, visually silent. A checkbox's affordance is the *glyph*, not the fill colour;
skipping the glyph and relying on fill/border colour alone under-communicates state
change to a user scanning quickly, even though every accessibility prop
(`accessibilityState.checked`) was already correct throughout - this was a purely
visual gap invisible to the test suite (which asserted `accessibilityState`, never
what a human would actually see) until a live screenshot at real zoom was inspected.

class of reason the prior section's revision names: it checked that the checkbox
toggled, not what the checked state actually looked like up close.

## Same-day, third round: popover position bugs, both from live device use

### Session log

1. Two more pieces of feedback on the same live preview, this time both about the
   popover's *position* rather than its chrome, and both reported from a real phone
   rather than the desktop browser this session had been verifying against: (1) the
   popover visibly shifts sideways as the scrubbed cell's digit count changes; (2) a
   screenshot showing the connector line hanging in empty space, not touching the
   cell it was supposed to connect to - described as "getting connected... after I
   move the [canvas] a bit," i.e. correct only once panning stops.
2. **Bug 1 root cause**: the popover's horizontal anchor read `widthOf(node, locale,
   fontSize)` live, every render. That width tracks the cell's digit count - which
   the very act of dragging the slider changes continuously, since scrubbing rewrites
   the cell's own displayed value. So the anchor point itself moved mid-drag, on top
   of (and independent from) the actual value change the user was making. Fixed by
   capturing the cell's width once when the slider opens on a node (`anchorCellWidth`,
   reset in the same effect that already resets `range` per node-open - identical
   lifecycle, identical reasoning) rather than re-reading it every render. The popover
   still opens visually centered under the cell's *starting* width; it just stops
   re-centering as that width changes underneath it.
3. **Bug 2 root cause, found by tracing exactly where the popover's screen position
   comes from**: `ValueSlider` computes its position from `documentStore.document.
   viewport` - the *committed* viewport. `Canvas.tsx`'s own header comment already
   documented why that lags a gesture in progress: pan/pinch/wheel drive Reanimated
   shared values every frame for smooth 60fps, and only commit into the store on
   release (or a debounce, for wheel) - a commit calls `notifyDocumentDirty`, so
   committing every frame would spam autosave. Every *other* piece of canvas UI
   (nodes, connectors) lives inside `Canvas`'s own Reanimated-driven transform and
   gets live tracking for free without needing the committed store value at all. The
   slider popover can't join that transform - it's deliberately a fixed screen
   overlay, independent of pan/zoom, so its own drag-to-reposition offset means
   something consistent - so it was the one piece of screen-space UI actually reading
   the throttled value, and paid for it exactly as designed: correct only once the
   gesture released and the store caught up.
4. Confirmed this diagnosis against an existing precedent before building anything:
   `canvas/ViewportContext.tsx` already exists for exactly this class of problem,
   built for node-drag, with its own header comment naming the identical failure mode
   ("reading the Zustand store mid-gesture would be a frame behind a pinch"). Node-drag
   solves it by reading the Reanimated shared values directly via context - but that
   context's Provider only wraps `Canvas`'s own children, and `ValueSlider` is mounted
   as a *sibling* of `Canvas` in `AppShell`, outside that Provider's subtree, so it
   can't consume the context directly without either restructuring where it mounts or
   duplicating shared-value ownership.
5. **Rejected fix**: making `Canvas.tsx`'s `commitViewport` fire every gesture frame
   instead of only on release, which would trivially make `ValueSlider`'s existing
   read of the committed store value live. Rejected on two grounds: it directly
   contradicts §7's own documented "commit only on release" rule, and `setViewport`
   unconditionally calls `notifyDocumentDirty` on every real change - firing that 60
   times a second during every pan would reintroduce the exact autosave-spam problem
   the release-only commit was built to prevent, for the sake of one consumer that
   has a better option available.
6. **Fix taken**: a new ephemeral `uiStore.liveViewport: { pan, zoom } | null`,
   generalizing node-drag's own bridge pattern (`useNodeDrag.ts`'s `runOnJS(updateDrag)`
   → `uiStore.setDragSnap`, already proven safe: ephemeral state never touches
   autosave or undo) rather than the Reanimated-context route, specifically because it
   needed to reach a consumer outside `Canvas`'s own subtree. `Canvas.tsx`'s
   `pan.onUpdate` and `pinch.onUpdate` now call `runOnJS(publishLiveViewport)` after
   updating the shared values (`onWheel` calls it directly - already JS-thread, no
   `runOnJS` needed); `commitViewport` clears it back to `null` right after writing the
   committed value, so a late-mounting reader always falls back cleanly. `ValueSlider`
   reads `liveViewport ?? committedViewport` in the one place it already computed
   `viewport` for every position/connector calculation, so both the popover position
   and the connector line's cell-side endpoint pick up the fix from a single change.
7. Considered and rejected a fuller Reanimated-idiomatic alternative (`Animated.View`
   + `useAnimatedStyle` worklets reading the shared values directly, matching how
   `Canvas`'s own transform is built) as disproportionate here: it would need `Canvas`
   restructured to expose a non-transformed overlay slot inside its own
   `ViewportContext.Provider` (its Provider currently wraps only its transformed

### Findings

**This session's own earlier live-verification passes on this same feature (both
2026-08-17's original PR and the first two rounds of same-day follow-up above) never
screenshotted *during* an active gesture - only before it started and after it fully
released.** That is precisely the blind spot both of today's bugs live in: bug 1 only
manifests while a value is actively changing (mid-drag), and bug 2 only manifests while
a pan is actively in progress (mid-gesture, pre-release) - a screenshot taken only at
rest either side of the gesture cannot distinguish "tracked correctly throughout" from
"wrong throughout the gesture, then snapped correct on release," because both produce
an identical *before* and an identical *after*. `Vibration.vibrate` doesn't show up in
a screenshot either, but that was a Jest-level behaviour with its own assertion; this is
a case where only a live tool that can pause mid-gesture (Playwright's separate
`mouse.move`/`mouse.down` without an intervening `mouse.up`) actually exercises the
state a screenshot-before/screenshot-after pass structurally cannot reach. Generalisable:
verifying "does X track a live gesture" needs a mid-gesture observation, not just
before/after ones - the same shape of gap as this project's own long-standing "tsc
passing isn't the same as the app rendering" lesson (2026-08-03), one level more
specific.

### Knowledge revisions

**2. `documentStore.document.viewport` was implicitly treated as "the" canvas viewport
for any reader, since it's the only place viewport ever gets written.**
*Previously believed:* not stated as a belief anywhere in this file before now, but
implicit in how `ValueSlider.tsx` was written across all three of this feature's prior
sessions (2026-08-17 and this day's first two rounds) - every position calculation read
`documentStore`'s committed viewport directly, with nothing questioning whether that
value could be stale relative to what's on screen.
*Now known:* the committed viewport is deliberately a frame-or-more *behind* the
canvas during an active gesture (§7's "commit only on release," which predates this
feature and was never in question) - it is the source of truth for anything that reads
it *between* gestures, but not for anything that must stay visually attached to the
canvas *during* one. `ViewportContext.tsx` already encoded this exact distinction for
node-drag; this feature simply hadn't needed to cross it yet, since nothing about
opening or dragging the slider itself required panning the canvas mid-interaction -
until a real user did exactly that with it pinned open.
*What established it:* live user report of a real device, screenshot showing the
disconnected line, reproduced by tracing the actual data path this session before
attempting a fix - not by first checking whether a fix could be true.
Standing lesson: `document.viewport` is the *committed* state, not "the current
viewport" - any new screen-space UI this project adds should ask which one it needs
before wiring up either.
