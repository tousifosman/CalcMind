# 2026-08-19

## Value slider follow-up: fixed a pin-toggle resize bug, connector colour, Step field + vibration

### Session log

1. User feedback on 2026-08-17's `Show slider`/pin feature (PR #158, live preview
   deployed): checking `Keep open` visibly made the popover *bigger*. Also requested: the
   drag bar should appear/disappear on check/uncheck rather than the container itself
   coming and going (which was the resize bug's actual cause), tighten the space around
   it since the bar's own footprint is small; the connector line should match the
   popover's own colour rather than the cell's identity hue; and a Step field (default
   `0.1`) between the range bounds, with the phone vibrating once per step while
   dragging.
2. **Root cause of the resize bug**: `DragHandle` was only mounted in the tree at all
   when `pinned` (`{pinned ? <DragHandle .../> : null}`) — its own padding/margin/bar
   height (originally ~20px) only entered the popover's flex layout once that condition
   flipped true, so the box visibly grew. Fixed by always mounting the container at a
   fixed size and moving the pin-dependent part down to paint only: the bar's opacity
   toggles with `pinned` (via two static `StyleSheet.create` entries,
   `dragHandleBarVisible`/`dragHandleBarHidden`, rather than an inline conditional style
   object — the latter tripped `react-native/no-inline-styles`, which this codebase
   otherwise keeps clean), and the drag gesture itself is disabled while unpinned via
   `Gesture.Pan().enabled(pinned)` rather than the whole `GestureDetector` being absent.
   Also reduced the container's own padding (`paddingVertical` 6→3, `marginBottom` 4→2)
   per the request to tighten the reserved space now that it's always visible.
3. Connector colour: was `rolePalette.number.border` (the cell's identity hue, teal for a
   plain number) — changed to a new `POPOVER_BORDER_COLOR` constant (`#D1D5DB`, the same
   gray `boundInput`'s border and the drag bar already used), and gave the popover itself
   an explicit 1px border in that same colour so the line has something on the window to
   visibly terminate at, rather than just picking a new colour with nothing to tie it to.
4. Step field: a new `Step` labelled input, positioned between the min/max bound inputs
   in `boundsRow` (replacing what had been a bare flex spacer). Backed by its own
   `step`/`stepText` state pair, mirroring the existing `range`/`minText`/`maxText`
   pattern exactly (numeric state used for computation, text state for the live draft,
   `commitStep` validating and reverting on blur/submit same as `commitBound`) — reset to
   the `0.1` default whenever the slider (re)opens on a different node, same lifecycle as
   the inferred range.
5. Continuous dragging now quantizes to the Step grid rather than landing on an arbitrary
   fraction: added `quantizeToStep(value, step, range)` to `inferSliderRange.ts`, rounding
   to the nearest multiple of `step` measured from `range.min` via `Decimal` (not plain
   float division — `0.33 * 10` is `3.3000000000000003` in JS, and the quantizer's own
   `Decimal` arithmetic snaps that back to an exact `3.3` rather than propagating the
   noise). Tap's existing integer-snap mode is untouched and stays the separate, coarser
   affordance it always was (§8.8's original Tydlig-observed behaviour) — Step only
   governs continuous dragging.
6. Vibration: `Vibration.vibrate(10)` (a short tick, not `vibrate()`'s 400ms default —
   that would read as one continuous buzz across many step crossings) fires from
   `writeFraction` exactly when the quantized value differs from
   `lastQuantizedValueRef.current`, a ref rather than component state or the `value` prop
   for the same reason `rangeRef`/`integerSnapRef` already are refs in this file: it has
   to be read-and-written synchronously inside the gesture callback itself, not depend on
   a React re-render having landed between two fast `onUpdate` calls in one native
   gesture. Confirmed react-native-web's `Vibration.vibrate` (`window.navigator.vibrate`
   under 'vibrate' in navigator) is safe to call under this project's jest preset with no
   extra setup — spied via `jest.spyOn(Vibration, 'vibrate')` in tests, never the real
   native call.
7. Full verification: `tsc`, lint (one `no-inline-styles` warning surfaced and was fixed
   as above, not suppressed), and the full suite (854 tests, up from 841) all clean.
   `build:web` emits `dist/`. Verified live against the served build with Playwright: the
   popover's screen bounding box is pixel-identical before and after pinning; the Step
   field shows `0.1` by default in the right position; the connector renders as a thin
   gray line (matching the popover's own new border) rather than teal; a real (multi-step,
   not a single-pixel) drag on a `0, 10` range landed on a clean `3.7`, confirming the
   step grid actually governs a real gesture and not only the unit-level math.
8. `docs/ARCHITECTURE.md` §8.8 rewritten for the Step field, vibration, the fixed-size
   handle, and the chrome-coloured connector, in the same commit as the code; decision
   #22 added to §16 citing #21's own resize regression.

### Findings

**Conditionally mounting a component to gate a *visual* toggle also gates its layout
footprint, even when that wasn't the intent.** `{pinned ? <DragHandle/> : null}` reads as
"show/hide an affordance," but React (any renderer) applies that at the mount/unmount
level - the component's own padding and children only enter the parent's flex layout
once mounted, so a flex `alignItems`/`padding`-bearing wrapper appearing and disappearing
necessarily resizes its parent unless the parent has a fixed height that ignores it. The
fix pattern is general and worth naming: when a toggle should change *paint* only (a bar
becoming visible, a gesture becoming active) without changing *layout*, keep the
component mounted always and drive the toggle through props into styles/opacity/`enabled`
instead of through JSX presence. The same 2026-08-17 session that introduced this bug
already used the *correct* version of this pattern for the connector line (an absolutely
positioned sibling, conditionally rendered - harmless, since absolute positioning removes
it from flex flow entirely) right next to the *wrong* version for the handle (a normal
flex child) - the same conditional-render idiom is safe or unsafe purely depending on
whether the thing being toggled participates in layout, which is easy to miss reviewing
the diff in isolation.

### Knowledge revisions

**1. The three pinned behaviours (dismiss-suppression, connector, drag) reading as one
`pinned` flag (2026-08-17, decision #21) was correct, but incomplete: a fourth thing
implicitly followed pinned too, and got it wrong.**
*Previously believed:* gating the connector's render and the drag handle's *render* both
on `pinned` was the natural continuation of "one flag drives three behaviours."
*Now known:* the handle's gesture *behaviour* (draggable or not) should follow `pinned`,
but the handle's own *mounted presence* must not - that has to stay constant so the
popover's size stays constant regardless of `pinned`. The connector was fine to
conditionally render because it's `position: absolute` and therefore already outside the
popover's flex flow; the handle isn't, so the identical-looking pattern broke for it.
*What established it:* user-reported live resize; reproduced by inspecting the two
screenshots from 2026-08-17's own verification pass side by side, where the popover's
top edge visibly shifted a fixed offset when `Keep open` was checked - a difference that
existed in the shipped PR and was not caught by that session's own live verification,
because the verification script never compared the popover's screen bounding box before
and after pinning, only that the check-related testids appeared/disappeared.
Standing lesson: when a live-verification pass in this project checks "does X appear,"
it should also check "does everything *else* stay where it was" for exactly this class
of bug - a Playwright bounding-box comparison catches what a testid-presence assertion
cannot.
