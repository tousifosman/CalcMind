# 2026-08-11

## Keypad `=` key narrower than the operator keys

### Session log

1. User reported the equals sign "feels smaller than the rest of the operators" and asked
   for verification.
2. First pass checked the canvas node cells (`OperatorNode.tsx` / `EqualsNode.tsx`,
   `tokens.ts`): `operatorWidth: 34` vs `equalsWidth: 35`, same `nodeHeight`, same
   `glyphTextStyle` font size — confirmed those boxes are not smaller, and reported that as
   the answer.
3. User pushed back with a phone screenshot of the *on-screen keypad*, not the canvas —
   a different component entirely (`src/keypad/Keypad.tsx`'s `EqualsKey`, styled by
   `equalsKey`, vs `OperatorKey`'s `accentKey`). That component hadn't been checked.
4. Reproduced against the running web build (`npm run web` + Playwright) at several
   viewport sizes: the on-screen `=` key measured 86px wide against 92px for `÷ × − +`,
   consistently, height identical (57.2px) in every case. Root cause: `accentKey` resets
   `marginHorizontal: 0` so the operator keys fill the column; `equalsKey` never did, so it
   kept `key`'s default `marginHorizontal: KEY_GAP / 2` (3px) on both sides — 6px narrower
   than its siblings for no design reason.
5. Fixed by adding `marginHorizontal: 0` to `equalsKey` (`src/keypad/Keypad.tsx`). Re-measured:
   all five keys now 92px. `tsc`, lint, full test suite (756 tests), and `build:web` all pass.

### Findings

**A shared base style plus a per-variant override style is only as safe as every variant
remembering to override the same properties.** `key` sets `marginHorizontal` for the
generic (grey, data-entry) keys; `accentKey` cancels it because operator keys are meant to
fill their column edge-to-edge; `equalsKey` was added later and only overrode the two
properties that were visibly different (`backgroundColor`, `marginBottom`), not realising
it also needed to cancel `marginHorizontal` the way its sibling variant did. Nothing failed
loudly — the key just rendered 6px narrower, small enough to read as "feels off" rather
than "obviously broken," which is exactly the shape of bug a screenshot catches and a
diff review doesn't.

### Knowledge revisions

**1. "The equals cell isn't smaller" was true for one of the two places `=` is drawn, not both.**
*Previously believed (stated to the user as the answer):* verifying `tokens.ts` and the
canvas `EqualsNode`/`OperatorNode` components was sufficient to answer "does the equals
sign look smaller" — those tokens are equal, so the answer was no.
*Now known:* CalcMind draws `=` in two independent places — the canvas node cell and the
on-screen keypad key — with separate style definitions. The canvas version was fine; the
keypad version had a real 6px width bug. A verification claim about "the equals sign" needs
to name which of the two it checked, and check both before answering "not smaller."
*What established it:* user-supplied screenshot of the deployed keypad, then reproduced and
measured in a local Playwright session against `npm run web`; fixed in
`src/keypad/Keypad.tsx`.
Standing lesson: when a symbol/control is rendered by more than one component in the
codebase, a verification answer about "how it looks" is only as complete as the number of
render sites checked — grep for every place the same glyph or role is drawn before
answering, not just the first one found.
