## `Create link` context-menu action

### Session log

1. User asked for two things: (a) confirm that selecting a number cell and pressing an
   operator appends the operator plus an empty number next to it, and (b) add a
   `Create link` item to the context menu.
2. (a) turned out to already be built and tested: §8.7 continuation
   (`continueFromValue` / `dispatchEditorCommand`'s `selectedNode?.kind === 'number' &&
   !editingNumber` branch, `keymap.test.ts`'s "operator with a selected (not editing)
   number" case) already does exactly this — a tap-selected, not-editing number plus an
   operator press builds `[reference→N, ⊕, empty number]` under it. Verified live in the
   web build rather than trusting the passing tests alone (`AGENTS.md`'s standing
   instruction) — screenshotted `5` selected, `+` pressed, `3` typed, and the chain
   appeared correctly under the source with a connector.
3. (b) was new: added `createLinkToValue` in `commands.ts` — a `Create link` menu item on
   the same value kinds continuation accepts (number, result, live reference) that drops a
   free, unattached reference near the source (reusing `continuationAnchor`'s placement and
   stacking so it doesn't land on an existing occupant) and selects it, with no operator and
   no bundled number. This is the third way to make a link, alongside continuation (§8.7)
   and drag-to-link (§11) — for when the user wants a linked cell parked somewhere on the
   canvas without committing to an operation on it yet. From there it's an ordinary free
   node: drag it onto a chain via the normal snap path, or operator-continue from it like
   any other live reference.
4. Wired through `NodeContextMenu` → `ContextMenuOverlay` → `AppShell.tsx`. Tests added in
   `commands.test.ts` (placement, stacking, eligibility, undo/redo) and
   `NodeContextMenu.test.tsx` (presence/absence per node kind, handler wiring). `ARCHITECTURE.md`
   §8.6 and §8.7 updated to document the new item and the third linking path.
5. Verified live (not just typechecked): built and served the web target, drove it with a
   headless Playwright/Chromium session (installed ad hoc into the scratchpad, not the
   project's `package.json`, since it wasn't already a project dependency), long-pressed a
   selected number, confirmed `Create link` appears in the menu alongside `Copy` / `Delete` /
   `Select group` / `Label`, clicked it, and confirmed a new connected reference cell appeared
   below the source with the source's identity hue and a connector arrow.

### Findings

**The project's pre-installed Chromium needs the headless_shell binary, not the ordinary
`chromium` one, under this Playwright version.** `chromium.launch({ executablePath:
'.../chromium' })` with default `headless: true` fails immediately with "Old Headless mode has
been removed from the Chrome binary" — Playwright 1.48's launch args still pass
`--headless=old` for the standard binary, which the installed Chromium build no longer supports.
Pointing `executablePath` at `chromium_headless_shell-*/chrome-linux/headless_shell` instead
works with the same launch call. Misleading symptom: the error names a Chrome headless-mode
deprecation, not a Playwright/browser version mismatch, so it reads like a browser-flag problem
rather than a "wrong binary" problem.

### Knowledge revisions

None — (a) was a confirmation of existing, already-tested behaviour, not a correction of one.

## Continuation was firing on chain-member operands, not just free values

### Session log

1. User reported: `1 + 2 =`, then select `2` (an operand of the already-`=`'d chain, not
   the result) and press `+` — it created a link instead of extending `1 + 2 =` into
   `1 + 2 + _`. This directly contradicts point 2 above, which took the existing
   `selectedNode?.kind === 'number' && !editingNumber` continuation branch at face value
   because its own test used a free (`chainId: null`) number and never exercised a number
   that was already a chain member.
2. Confirmed the bug live before touching anything (screenshots `bug-1`…`bug-3`): building
   `1 + 2 = 3`, selecting `2`, pressing `+` spun off a reference to `2` in a new chain below,
   exactly as reported.
3. Root cause was two-fold:
   - `dispatchEditorCommand`'s number-continuation branch fired for *any* selected,
     not-editing number, regardless of `chainId` — it never distinguished "a free-standing
     value" from "an operand still inside a formula."
   - Underneath that, `appendMembersToChain` (which `appendOperatorAndNumber` calls) always
     pushed new members to the **array end**, not to the position right after the node
     named as `afterNodeId`. That's invisible for ordinary typing, where the node being
     extended is always already the chain's last member, but it means the "extend in place"
     fix couldn't have worked correctly even after fixing the branch above — appending after
     `2` in `1 + 2 = 3` would have landed the new operator+number *after* the result,
     producing `1 + 2 = 3 + _` (nonsensical: content after a result is Invalid per
     `validateChain`'s `nodeAfterResult` check).
4. Fixed both: `appendMembersToChain` now splices new members at `anchorIndex + 1` instead
   of always at the array end (§8.5). `dispatchEditorCommand` now checks the selected
   number's `chainId`: `null` (free) still triggers §8.7 continuation; anything else
   (already a member of a chain, `=`'d or not) extends that chain in place via
   `appendOperatorAndNumber` instead. No new engine bookkeeping was needed — `writeChainDerived`
   already looks up `=`'s index fresh on every recompute rather than assuming it's last, and
   `validateChain` already treats a trailing operator + empty operand as Incomplete (dropping
   the stale result) regardless of what comes after it once nothing sits past the result. Verified
   with `1 + 2 = 3` → select `2` → `+` → chain reads `1 + 2 + _` with the stale `3` gone →
   type `6` → recomputes to `1 + 2 + 6 = 9` (`bug-4` screenshot), live in the web build.
5. Added regression coverage: `commands.test.ts` (`appendOperatorAndNumber` inserting after a
   non-last anchor) and two `keymap.test.ts` cases (chain member with `=`, and mid-chain member
   with no `=` yet) asserting no reference is created and the chain extends in place.
   `ARCHITECTURE.md` §8.7 rewritten to state the free-vs-chain-member distinction explicitly.

### Findings

**`validateChain`'s "content after the result is Invalid" rule only looks at position
relative to the *result*, not the `=`.** So an insert that displaces `=` rightward but leaves
the result (once recomputed) as the true last member is fine — the rule that would have made a
naive "always append after `=`'s old index" fix unsafe doesn't actually apply once you let
`writeChainDerived` re-locate `=` itself on each recompute rather than caching its position.
Worth knowing before reaching for a more defensive insert-position calculation than the code
needs.

### Knowledge revisions

**1. Continuation firing on "any selected, not-editing number" was only checked against a free number.**
*Previously believed (this day's earlier revision, point 2 above):* the existing
`selectedNode?.kind === 'number' && !editingNumber` continuation branch, and its passing test,
meant selecting *any* not-yet-editing number and pressing an operator correctly builds
`[reference→N, ⊕, empty]` — confirmed "live" by testing only a free-standing number.
*Now known:* that branch doesn't distinguish a free-standing number from one that's already a
member of an existing chain (mid-formula, or already `=`'d). For the latter, an operator must
extend that chain in place instead — continuation is for values, and a chain-member operand
isn't standing alone the way a result or an unchained number is. Fixed by gating continuation
on `chainId === null`; a chain member now goes through `appendOperatorAndNumber`, which itself
needed fixing to insert after the anchor's actual index rather than the chain's array end.
*What established it:* user reproduction (`1 + 2 =`, select `2`, press `+` created a link) and
live confirmation of the fix.
*Standing lesson:* a passing test for a claim is only as strong as the fixture it exercises —
this session's own "verified live" a few hours earlier used the one input shape (a free number)
that happened not to expose the gap.

## Keypad `=` key narrower than the operator keys

### Session log

1. User reported the equals sign "feels smaller than the rest of the operators" and asked
   for verification.
2. First pass checked the canvas node cells (`OperatorNode.tsx` / `EqualsNode.tsx`,
   `tokens.ts`): `operatorWidth: 34` vs `equalsWidth: 35`, same `nodeHeight`, same
   `glyphTextStyle` font size — confirmed those boxes are not smaller, and reported that as
   the answer.
3. User pushed back with a phone screenshot of the *on-screen keypad*, not the canvas —
   a different component entirely (`src/keypad/Keypad.tsx`'s `EqualsKey`, styled by
   `equalsKey`, vs `OperatorKey`'s `accentKey`). That component hadn't been checked.
4. Reproduced against the running web build (`npm run web` + Playwright) at several
   viewport sizes: the on-screen `=` key measured 86px wide against 92px for `÷ × − +`,
   consistently, height identical (57.2px) in every case. Root cause: `accentKey` resets
   `marginHorizontal: 0` so the operator keys fill the column; `equalsKey` never did, so it
   kept `key`'s default `marginHorizontal: KEY_GAP / 2` (3px) on both sides — 6px narrower
   than its siblings for no design reason.
5. Fixed by adding `marginHorizontal: 0` to `equalsKey` (`src/keypad/Keypad.tsx`). Re-measured:
   all five keys now 92px. `tsc`, lint, full test suite (756 tests), and `build:web` all pass.

### Findings

**A shared base style plus a per-variant override style is only as safe as every variant
remembering to override the same properties.** `key` sets `marginHorizontal` for the
generic (grey, data-entry) keys; `accentKey` cancels it because operator keys are meant to
fill their column edge-to-edge; `equalsKey` was added later and only overrode the two
properties that were visibly different (`backgroundColor`, `marginBottom`), not realising
it also needed to cancel `marginHorizontal` the way its sibling variant did. Nothing failed
loudly — the key just rendered 6px narrower, small enough to read as "feels off" rather
than "obviously broken," which is exactly the shape of bug a screenshot catches and a
diff review doesn't.

### Knowledge revisions

**2. "The equals cell isn't smaller" was true for one of the two places `=` is drawn, not both.**
*Previously believed (stated to the user as the answer):* verifying `tokens.ts` and the
canvas `EqualsNode`/`OperatorNode` components was sufficient to answer "does the equals
sign look smaller" — those tokens are equal, so the answer was no.
*Now known:* CalcMind draws `=` in two independent places — the canvas node cell and the
on-screen keypad key — with separate style definitions. The canvas version was fine; the
keypad version had a real 6px width bug. A verification claim about "the equals sign" needs
to name which of the two it checked, and check both before answering "not smaller."
*What established it:* user-supplied screenshot of the deployed keypad, then reproduced and
measured in a local Playwright session against `npm run web`; fixed in
`src/keypad/Keypad.tsx`.
Standing lesson: when a symbol/control is rendered by more than one component in the
codebase, a verification answer about "how it looks" is only as complete as the number of
render sites checked — grep for every place the same glyph or role is drawn before
answering, not just the first one found.
