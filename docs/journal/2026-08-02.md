## Session log

### 1. Initial scaffold (`4d6de70`, PR #1)

A TypeScript Expo project with a working calculator UI, `react-native-web` for web
support, and a GitHub Actions workflow building the web export and deploying it to
GitHub Pages on every push to `main`.

The calculator UI here was a placeholder — a conventional button-grid calculator. It
existed to prove the toolchain end to end (native project + web export + Pages deploy),
not because it was the product. It survived until P1 finally deleted it.

### 2. Expo removed in favour of bare React Native CLI (`5af5aa8`, PR #2)

Reversed the scaffold's central technology choice one commit later. Stated reason:
**avoid any dependency that can later acquire a price.** Expo's build story routes
through EAS, a vendor build service. Everything in the tree after this commit is open
source and builds locally or in CI with no vendor service required.

Mechanics:

- Native `android/` and `ios/` projects scaffolded via `@react-native-community/cli`.
- `expo-status-bar` → React Native's built-in `StatusBar`.
- `expo export --platform web` → a plain Webpack config (`react-native-web` +
  `babel-loader`), still emitting a static site to `dist/` with **relative** asset paths
  so it works from a GitHub Pages project subpath.

This is decision #1 in the architecture document's decisions log, with "needing many
native modules makes manual linking painful" recorded as the condition to revisit under.

### 3. First architecture document (`7856e3f`, PR #3 opened)

The pivot from "a calculator app" to the actual product: **a free-form canvas where
numbers and operators are nodes that snap into formula chains, with auto-created
read-only result nodes.** A visual reference was supplied; the document includes an SVG
trace of it with colours and geometry sampled from the source pixels rather than eyeballed.

Scope covered in the first draft: domain model, snapping and layout algorithms, the
evaluation engine and its reactive dependency graph, the on-disk JSON document format
with migrations and atomic writes, testing strategy, and a phased plan (P0–P7) with
per-phase acceptance criteria. Nine Mermaid diagrams, verified to parse under Mermaid v11.

## Findings

- **The web build must use relative asset paths in production.** GitHub Pages serves
  project sites from `https://<user>.github.io/<repo>/`, so an absolute `publicPath`
  produces a page that loads nothing. (This finding acquires an important exception on
  2026-08-03 — see that entry.)
- **`react-native-web` + `babel-loader` is sufficient to replace `expo export`.** No
  bundler-specific Expo behaviour turned out to be load-bearing for this project.
- **Deploy is on `main` push.** Anything not merged to `main` is not deployed. This
  matters more than it sounds — see 2026-08-03's revision about PR #4.

## Knowledge revisions

**Previously believed:** Expo is the sensible default for a React Native app, including
for the web export path.
**Now known:** For this project it is a liability, because the build service behind it is
a vendor dependency that can acquire a price. Bare RN CLI plus a hand-written Webpack
config covers everything needed here.
**What established it:** Explicit project constraint — no dependency that can start
charging. Acted on the same day the scaffold landed.

**Previously believed (implicitly, from the scaffold):** CalcMind is a calculator with
buttons.
**Now known:** It is a canvas. Numbers and operators are draggable objects that snap into
chains; results are generated nodes. The button-grid UI was scaffolding, not a prototype.
**What established it:** A supplied visual reference, traced into `docs/assets/`.
