## P7.2 — Full keyboard support

### Session log

1. Picked up P7.2 (#118). P2.8 already had left/right along a chain, digits/ops/
   equals/backspace/escape, and one shared `dispatchEditorCommand`. Gaps for this
   task: between-chain arrows, a keyboard equivalent for every keypad action
   (notably `+/-` and dismiss), visible selection focus, sane tab order, and
   Ctrl/Cmd+Z undo (called out as open under P7.1 / P6b.2).
2. Extended `keymap.ts`: `ArrowUp`/`ArrowDown` jump to the nearest other chain
   (or free node), landing on the member closest in x; `_` / `F9` map to `sign`;
   `Ctrl/Cmd+Z` / `Shift+Z` / `Y` map to undo/redo; Escape still deselects, and a
   *second* Escape with nothing focused dismisses the keypad (mode-strip chevron
   equivalent) without changing §8.5's primary Escape meaning.
3. `AppShell` keydown listens in capture phase, passes modifiers into
   `commandFromHardwareKey`, `preventDefault`s handled keys, and lets undo/redo
   (and F9 sign) through even when an `INPUT` is focused so Ctrl+Z hits the
   document stack rather than the browser's text-undo.
4. Selection focus ring on `Cell` (`selectionFocusColor`), driven by
   `useNodeSelected` across every node kind — covers both `selectedNodeId` and
   `groupSelectedIds`. Keypad data-entry keys take `tabIndex={-1}` on web so Tab
   does not walk ~20 digit/op buttons; mode-strip dismiss and clear-confirm stay
   tabbable (~4 tab stops).
5. Unit tests for between-chain arrows, undo/redo dispatch, Escape dismiss, sign
   mapping, and the focus ring. Live Chromium pass: typed `10+5=` then continued
   `*2=` to `30` keyboard-only, ArrowUp between chains, Ctrl+Z/Shift+Z, F9 sign.
   Screenshots under `/opt/cursor/artifacts/screenshots/p72-*.png`.
6. Ticked P7.2; flipped its P7 mermaid node green. Updated §8.5's hardware map.

### Findings

**react-native-web's `TextInput` `onKeyPress` only synthesises printable keys.**
F9 (and other function keys) never reach `NumberNode`'s `onKeyPress`, so a
hardware `+/-` mapped only there is dead while editing. Misleading symptom: `_`
(printable) toggles sign fine from the same handler, which makes F9 look
"broken in the keymap" rather than unreachable. Fix: handle F9 on the same raw
`keydown` listener that already owns Enter/Space for the gesture-handler trap,
and also allow it through AppShell's capture listener when an input is focused.

### Knowledge revisions

**1. "Escape deselects" and "dismiss keypad" are two actions, not one.**
*Previously believed (briefly, mid-implementation):* mapping Escape to both
deselect and hide-keypad in one press was a fine keyboard equivalent for the
mode-strip chevron.
*Now known:* that collapses §8.5's explicit "Escape deselects" into a dismiss,
and hides the keypad the first time the user only meant to clear selection.
First Escape deselects; a second Escape with nothing focused dismisses —
chevron equivalent without rewriting Escape's primary meaning.
*What established it:* §8.5's own Escape bullet, plus the P7.2 criterion that
*every* keypad action (including dismiss) needs a keyboard equivalent.
*Standing lesson:* when one key is already claimed by the architecture doc,
stack a second press (or a modifier) for the new action rather than overloading
the first press.

## P7.3 — Result dot texture

### Session log

1. Picked up P7.3 (#119). Geometry source of truth is §1.2 plus
   `docs/assets/formula-reference.svg` (4×4 `userSpaceOnUse` tile, 1-unit rects at
   `(1,0)` and `(3,2)` in `#FFD1CF`).
2. Added `ResultDotTexture` (`react-native-svg` `Pattern`) and wired it through a new
   `Cell` `bandBackground` slot so the identity ring stays above the dots. `ResultNode`
   keeps the solid role fill + border; texture is overlay only (decision #9).
3. Extended the Jest `react-native-svg` mock with `Pattern`. Updated `ResultNode` tests
   to assert tile size, both dot positions/colour, and `url(#…)` fill — and that the
   solid fill is still present without relying on the texture for meaning.
4. Updated §11.3 (texture shipped), decision #9 wording, dependency table SVG note;
   ticked P7.3 boxes and flipped its P7 mermaid node green.
5. Browser-verified on the web target: typed `12 =`, confirmed the salmon result cell
   shows the dotted fill (not flat), and the DOM carries `result-dots-*` with the
   §1.2 rects.

### Findings

**`Cell` needed an underlay slot, not a child, for the texture.** Putting the SVG as the
first child painted *after* the identity ring and covered the ring's border. Mechanism:
absolute-fill siblings stack in document order; the ring is only a transparent-centre
border, so a later full-rect underlay hides it. Misleading symptom: "identity ring
vanished on results once the texture landed." Fix: render `bandBackground` *before* the
ring inside `Cell`.

**`StyleSheet.absoluteFillObject` is not in this RN type surface.** Prefer
`StyleSheet.absoluteFill` — the Object alias either is absent or untyped under
`react-native` 0.86 / the project's TS config.

### Knowledge revisions

**1. Decision #9's "deferred to v1.1" is closed by shipping, not by overturning.**
*Previously believed (as the decision row still read):* the texture stayed deferred.
*Now known:* P7.3 ships the §1.2 pattern; the decision that survives is that it remains
*decorative* — hue + border still carry read-only-ness without it. The revisit condition
("tests as load-bearing for comprehension") is unchanged and still open.
*What established it:* P7.3 acceptance criteria and the updated decision #9 row.

## Manual PR preview deploys

### Session log

1. Asked whether a PR could be deployed to a temp path before merging, without
   waiting for it to land on `main`. `deploy-web.yml` at the time only ran on
   push to `main` (or manual `workflow_dispatch` of the *same* job, which
   would just redeploy over production) via `actions/deploy-pages`.
2. `actions/deploy-pages` publishes to the single `github-pages` Actions
   environment — the whole artifact it's given *is* the site, replacing
   whatever was live. There's no path-scoping and no way to run a second,
   PR-scoped deploy alongside it while that's the Pages source.
3. Switched the Pages source to a branch (`gh-pages`) instead: `deploy-web.yml`
   now commits `dist/` to the branch root via `peaceiris/actions-gh-pages`
   with `keep_files: true`, and a new `deploy-pr-preview.yml` commits a given
   PR's build under `pr-preview/pr-<n>/` on the same branch — directory
   structure does the scoping a branch source needs, in place of the single
   deployment a GitHub Actions source gives you.
4. `deploy-pr-preview.yml` is `workflow_dispatch`-triggered (PR number +
   deploy/remove choice), checks out `refs/pull/<n>/head` (works for fork PRs
   too, without needing the contributor's branch), builds, publishes, and
   comments the preview URL back on the PR. A `pull_request: types: [closed]`
   trigger runs the removal side automatically so `gh-pages` doesn't
   accumulate one directory per PR forever.
5. Updated README's Deployment section: the one-time repo setup is now
   "Deploy from a branch" → `gh-pages` / root, not "GitHub Actions" — that
   setting itself is outside version control and has to be flipped by hand in
   Settings → Pages by whoever has repo admin.

### Findings

**`actions/deploy-pages` has no path scoping — it *is* the site, not a layer
onto it.** Every successful run replaces the entire live deployment; there is
exactly one `github-pages` environment per repo when Pages' source is set to
"GitHub Actions". A second, PR-scoped deploy cannot coexist with it under that
source. Coexistence needs the other Pages source kind — "Deploy from a
branch" — where the artifact is just files at paths on a branch, and separate
deploys can occupy separate directories on it.

**The 2026-08-02 relative-`publicPath` choice generalises to arbitrarily
nested subpaths for free.** It was made for the single top-level GitHub Pages
subpath (`/<repo>/`); serving the same production build from
`/<repo>/pr-preview/pr-<n>/` needed no webpack change at all — relative paths
don't care how deep the page is nested.

### Knowledge revisions

**1. "Deploy is on `main` push; anything not merged is not deployed" no
longer holds without qualification.**
*Previously believed:* per 2026-08-02's Findings — restated and leaned on
again in 2026-08-03's revision 10 — nothing not merged to `main` is ever
deployed.
*Now known:* that's still true of the *production* URL, which only ever
tracks `main`. It's no longer true in general: `deploy-pr-preview.yml` can put
any open PR's build live at a temp URL on demand, independent of merge state.
Anyone re-deriving "unmerged ⇒ unreachable" from the earlier findings should
check this entry first.
*What established it:* this session's PR-preview workflow.
*Standing lesson:* a finding recorded as unconditional ("anything not merged
to main is not deployed") is only as durable as the deploy mechanism it
describes — worth re-checking after any change to *how* deploys happen, not
just *what* triggers them.

### Open threads

- `keep_files: true` on the `main` deploy (needed so it doesn't delete
  `pr-preview/` directories on every push) also means it never prunes stale
  root-level files from earlier builds — `bundle.<oldhash>.js` files
  accumulate on `gh-pages` forever. Not user-visible (`index.html` always
  points at the current bundle) but the branch will grow unbounded; a
  periodic prune step would close this if it ever matters.
- The Settings → Pages source switch (GitHub Actions → Deploy from a branch)
  is a manual, out-of-repo step nothing in this session could perform — it
  needs a repo admin, and until it happens neither workflow has actually run
  against real GitHub infrastructure. Verify end-to-end once that's flipped:
  confirm `gh-pages` gets created on the first `main` push, and run
  `deploy-pr-preview.yml` against a real open PR.
