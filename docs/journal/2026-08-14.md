# 2026-08-14

## Keypad's two columns didn't align row-for-row once both had six rows

### Session log

1. User attached an annotated screenshot (yellow guide lines) from a real device: now that
   `()` moved into the accent column, the main column (digit grid + number-editing row +
   history row) and the accent column (operators + `()` + `=`) both stack six rows — and the
   guide lines showed those six rows drifting further out of alignment the lower they got.
2. Root cause: `digitKey` has always been 48px tall; the generic `key` base (and therefore
   `accentKey`, `OperatorKey`, `EqualsKey`, and everything else built on `Key`) has always been
   44px. That 4px-per-row gap was invisible while the two columns had different row counts —
   nothing lined up row-for-row anyway — and only became a visible, accumulating stagger once
   they matched at six rows each (4px × 4 rows before the shared final two rows = 16px of drift
   by the bottom, matching what the screenshot showed).
3. Fixed by unifying the height: `key`'s base height and `accentKey`'s explicit override both
   moved from 44 to 48, matching `digitKey`. `gridEditingKey` (decimal/`+/-`'s override) no
   longer needs its own `height: 48` — it was only ever there to match a `key` default that
   is now already 48 — so simplified it down to just the background-colour override that's
   still actually special about it. `EqualsKey` needed no change: it never overrode `key`'s
   height itself, so the base bump reaches it automatically.
4. Verified live: served the web target at a phone-sized viewport and read back each row's
   exact bounding box (Playwright `boundingBox()`, not just eyeballing a screenshot) — every
   key is 48px tall, and paired rows on the two columns (`keypad-digit-7`/`keypad-op-divide`,
   `keypad-link`/`keypad-paren`, `keypad-undo`/`keypad-equals`) sit at identical `y`.
5. Added a `Keypad.test.tsx` case asserting one representative key per row across both
   columns all report the same rendered height (48), so a future one-off override doesn't
   quietly reopen the drift.

### Findings

**A per-row pixel misalignment can hide for a long time behind unequal row counts.** The
44-vs-48 height gap between `key` and `digitKey` predates every keypad-layout change made this
week — it just never mattered while the accent column had 5 rows against the main column's 6.
Moving `()` into the accent column (an earlier change this week) made the counts match, which is
what turned a latent inconsistency into a reported bug. Worth remembering when a layout change
makes two previously-independent regions start being compared against each other for the first
time: check the assumptions each one was built under, not just the new code path.
