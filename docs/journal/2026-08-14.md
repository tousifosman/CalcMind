## Keypad's two columns didn't align row-for-row once both had six rows

### Session log

1. User attached an annotated screenshot (yellow guide lines) from a real device: now that
   `()` moved into the accent column, the main column (digit grid + number-editing row +
   history row) and the accent column (operators + `()` + `=`) both stack six rows — and the
   guide lines showed those six rows drifting further out of alignment the lower they got.
2. Root cause: `digitKey` has always been 48px tall; the generic `key` base (and therefore
   `accentKey`, `OperatorKey`, `EqualsKey`, and everything else built on `Key`) has always been
   44px. That 4px-per-row gap was invisible while the two columns had different row counts —
   nothing lined up row-for-row anyway — and only became a visible, accumulating stagger once
   they matched at six rows each (4px × 4 rows before the shared final two rows = 16px of drift
   by the bottom, matching what the screenshot showed).
3. Fixed by unifying the height: `key`'s base height and `accentKey`'s explicit override both
   moved from 44 to 48, matching `digitKey`. `gridEditingKey` (decimal/`+/-`'s override) no
   longer needs its own `height: 48` — it was only ever there to match a `key` default that
   is now already 48 — so simplified it down to just the background-colour override that's
   still actually special about it. `EqualsKey` needed no change: it never overrode `key`'s
   height itself, so the base bump reaches it automatically.
4. Verified live: served the web target at a phone-sized viewport and read back each row's
   exact bounding box (Playwright `boundingBox()`, not just eyeballing a screenshot) — every
   key is 48px tall, and paired rows on the two columns (`keypad-digit-7`/`keypad-op-divide`,
   `keypad-link`/`keypad-paren`, `keypad-undo`/`keypad-equals`) sit at identical `y`.
5. Added a `Keypad.test.tsx` case asserting one representative key per row across both
   columns all report the same rendered height (48), so a future one-off override doesn't
   quietly reopen the drift.

### Findings

**A per-row pixel misalignment can hide for a long time behind unequal row counts.** The
44-vs-48 height gap between `key` and `digitKey` predates every keypad-layout change made this
week — it just never mattered while the accent column had 5 rows against the main column's 6.
Moving `()` into the accent column (an earlier change this week) made the counts match, which is
what turned a latent inconsistency into a reported bug. Worth remembering when a layout change
makes two previously-independent regions start being compared against each other for the first
time: check the assumptions each one was built under, not just the new code path.

## Operator on a selected reference was linking-to-a-link instead of extending

### Session log

1. User asked why the number keys and `Create link` were disabled with a reference (a
   linked cell) selected. Point 1 (digits) was already-correct, pre-existing behaviour
   explained without a code change. Point 2 surfaced a real bug while explaining it: with
   a reference selected, pressing an operator was §8.7-continuation-linking — creating a
   *second* reference pointing at the first — rather than extending the formula the
   reference is part of. User confirmed that's wrong: "pressing the operator should add
   the operator and then an empty number cell," not spin off a new linked cell.
2. This is the same shape of bug fixed for numbers on 2026-08-11 (`1 + 2 =`, select `2`,
   press `+` used to link instead of extending), just for the other value kind
   continuation was ever applied to. Same root cause: `dispatchEditorCommand`'s
   `selectedNode?.kind === 'reference'` branch called `continueFromValue` unconditionally
   for any live reference, regardless of whether that reference was already the operand of
   some formula (chain member) or freshly dropped by `Create link` (still free).
3. Unlike the number case, the fix doesn't need a `chainId === null` branch at all — a
   reference should *never* continuation-link on an operator press, free or not. A
   reference is already a link; the only sensible operator-key behaviour is "keep
   computing with what this points to" (`appendOperatorAndNumber`, same append-after-
   anchor mechanism as the number-in-chain fix), never "link to this link." A free
   reference just becomes the first member of its own new chain the same way a free
   number does when extended (`appendMembersToChain` creates one when the anchor has
   none) — so `ref ⊕ _` lands right where the reference already is, not somewhere new.
4. `continueFromValue` itself is untouched — still generic over number/result/live
   reference, since the explicit `Create link` context-menu action (`createLinkToValue`)
   legitimately still wants to link from a reference (chaining links is a real, requested
   feature there, just not the implicit operator-key gesture). Only the dispatcher's
   reference branch changed which command it calls.
5. Verified live: `12 + 2 = 14`, `Create link` on the result → free reference `14`. Select
   it, press `+` → previously created a second reference pointing at the first; now builds
   `14 + _` in place, right there. Filled in `3` → `14 + 3`, recomputes correctly.
6. Rewrote the one `keymap.test.ts` case that asserted the old (wrong) continuation
   behaviour for a chain-member reference, and added a second case covering a still-free
   reference (the exact scenario reported). `ARCHITECTURE.md` §8.7's continuation
   pseudocode and surrounding prose updated — `V` is now explicitly "a free number or a
   result," not "...or a live reference"; a new paragraph explains the reference
   extend-in-place rule on its own. `continueFromValue`'s doc comment in `commands.ts`
   updated to match (still generic on purpose, but the dispatcher no longer reaches it
   with a reference).

### Findings

None beyond what's in the session log.

### Knowledge revisions

**1. Continuation was never supposed to apply uniformly to "any live reference" — only to a fresh, standalone one, and even that reading doesn't survive contact with actual use.**
*Previously believed:* per §8.7 (written 2026-08-04/05-era, reaffirmed as recently as
2026-08-11's revision about numbers): "a value V (number, result, or live reference)" is the
continuation-eligible set — pressing an operator on any of the three should create a new link.
This was a deliberate design choice, not an oversight — `continueFromValue`'s own doc comment
said so explicitly ("Numbers and live references are included so a value (or an existing link to
one) can seed another link").
*Now known:* a live reference should never continuation-link on an operator press, regardless of
whether it's a free-standing reference or already a chain member. It always extends in place
instead — the same rule chain-member numbers already got on 2026-08-11, just applied
unconditionally rather than gated on `chainId`. The "chain a link off a link" capability the old
design wanted is still available, just only through the *explicit* `Create link` context-menu
action, never through the implicit operator key.
*What established it:* direct user testing against the live app (`12 + 2 = 14` → `Create link` →
select the reference → `+`), reported as visibly wrong; confirmed by reproducing it before the
fix and re-verifying after.
*Standing lesson:* a documented, deliberate design decision is not immune from being wrong once
someone actually presses the key — "we chose this on purpose" recorded in a doc comment carries
no more weight against live evidence than an accidental default would. Two corrections to the
same mechanism (numbers on the 11th, references now) in one week is also worth noticing as a
pattern: continuation's original "any selected non-editing value" framing kept being too broad
each time it met a value that already had a place in an existing formula.

## `Create link` keypad button widened to match a selected linked cell

### Session log

1. Immediate follow-up to the operator-on-a-reference fix above: the user asked for the
   `Create link` keypad button to also enable when a linked cell (reference) is selected —
   consistent with the context-menu `Create link` action, which already accepts a live
   reference.
2. `canCreateLink` (`Keypad.tsx`) widened from `number | result` to `number | result |
   live reference` — a dangling reference (target gone) stays ineligible, same as it
   rejects every other data-entry key. `dispatchEditorCommand`'s `createLink` handler
   (`keymap.ts`) widened to match, with its own `targetExists` guard so it can never call
   `createLinkToValue` with a dangling reference (which would throw).
3. This is deliberately the opposite direction from the operator-key fix just above:
   pressing **operator** on a reference now always extends in place, never links; pressing
   **`Create link`** on a reference always links (chains a second reference off the
   first), never extends. The two keys are meant to diverge here — one is "keep computing
   with this", the other is "I explicitly want another link to this" — and the explicit
   action should not inherit the implicit one's narrower scope.
4. Verified live: `12 + 2 = 14` → `Create link` on the result → reference `14` selected →
   `Create link` button now reads enabled (vivid blue, not the disabled fade) → pressing
   it drops a second reference pointing at the first, with a connector between them.
5. Rewrote `Keypad.test.tsx`'s reference test (it previously asserted `disabled: true`)
   into two: live reference (now enabled) and dangling reference (still disabled, new
   coverage using the same inline-node construction pattern
   `NodeContextMenu.test.tsx` already uses for dangling fixtures). Also discovered while
   writing this that `dispatchEditorCommand({ region: 'createLink' })` had **no dispatch-
   level test coverage at all** before now — only `Keypad.tsx`'s own "reports the region"
   test existed, which never touched the actual command dispatch. Added a full
   `describe('dispatchEditorCommand: Create link keypad button (§8.6)')` block: number,
   result, live reference, dangling reference (no-op), and nothing-selected (no-op).
6. `ARCHITECTURE.md` §8.5's `Create link` bullet corrected — it previously said the
   keypad button was deliberately narrower than the menu action ("no live-reference
   source here"); that's no longer true, and the paragraph now says so.

### Findings

**A component-level "the button reports the right key press" test does not cover the
dispatcher's handling of that press.** `Keypad.test.tsx` had a passing test asserting
`onKeyPress` was called with `{ region: 'createLink' }`, which reads as coverage for
"pressing Create link works" but says nothing about what `dispatchEditorCommand` actually
does with that region — the dangling-reference guard, the eligibility check, all of it
was unexercised. Worth checking, when a UI-level test exists for a key press, whether a
corresponding dispatcher-level test exists too; they cover different halves of the same
feature and one does not imply the other.

### Knowledge revisions

None — this follows directly from the reference-eligibility work above, not a separate
correction.
