## Continuation placement under the source group's first cell

### Session log

1. User asked that a newly created link appear underneath the first cell of the
   group the link is created from, and that a second link in the same spot stack
   under the occupant while still starting at that first-cell x.
2. Updated §8.7 placement in `continueFromResult`: `continuationAnchor` aligns
   `C'.anchor` with the source chain's first cell (`chain.anchor`) and stacks
   through a contiguous column of occupants at `CONTINUATION_OFFSET.y` pitch.
   Dropped the old half-cell-right offset from the result.
3. Tests cover first-cell alignment, repeated stacking, and "drifted occupant
   still blocks y but not x". Architecture §8.7 rewritten to match.

### Findings

**Keypad 1→N continuations no longer land on one coincident anchor.** The
2026-08-05 open thread ("repeated keypad continuations still stack") was the
default placement always using `result + CONTINUATION_OFFSET`, so every fan
consumer shared endpoints until dragged apart. Misleading symptom then: "only
one connector." Placement now walks the first-cell column, so each new
continuation gets its own row and connectors separate without a manual drag.

### Knowledge revisions

**1. Continuation anchors under the source group's first cell, not below-right of R.**
*Previously believed:* §8.7 / `linking-model.svg` proportions place C' half a
cell right and 1.5 cells down from the source *result*.
*Now known:* C' starts under C's first cell (x = C.anchor.x); vertical pitch is
unchanged; occupied landing rows push further down while x stays on that first
cell.
*What established it:* explicit product direction this session; matches Tydlig's
"on the line below" wording already quoted in §1.1.

**2. Continuation stacking needs bounds overlap, not same-row left-edge banding.**
*Previously believed (this day's earlier revision):* treating a column occupant as
"same left-edge x within half a cell, and same row within `pitch/2`" was enough
to stack under "a cell already there."
*Now known:* a free number in the gap under the group (or slightly x-offset but
still under the first cell's width) overlaps the default landing slot without
matching that band — the link painted on top. Collision must be AABB overlap
against the first cell's horizontal span.
*What established it:* user screenshot of `63 − 3 = 60` continuation covering a
pre-existing green cell; regression tests for gap occupant and offset left edge.

## Group-mode keypad: disable (not hide) non-history keys

### Session log

1. User: when a group is selected, disable all keypad keys except undo /
   redo / backspace; if the group has a result, keep operator buttons
   available too. (First pass hid the keys; user clarified disable.)
2. `Keypad` reads `groupSelectedIds` and leaves the full layout visible,
   setting `disabled` on digits, number-editing, and `=`. History stays
   enabled. Operator column (`÷ × − +`) stays enabled only when
   `groupContainsResult` is true; otherwise those ops are disabled too.
3. `dispatchEditorCommand` mirrors that: while a group is active, digits /
   editing / equals / parens no-op; backspace calls new `deleteGroup` (one
   undo entry for the whole set); operator continues from the group's
   result via `continueFromResult`.
4. `selectGroup` prefers a result in the chain as the primary keypad
   target so continuation does not need an extra tap after double-tap /
   Select group.
5. §8.5 / §8.6 updated. Live-checked on PR #144 (hide pass, then disable
   pass).

### Findings

**Select-group fixtures must go through `appendOperatorAndNumber` +
`appendEqualsNode`, not three free `add*Node` calls plus a lone
`appendEqualsNode` on the last number.** Misleading symptom: `selectGroup`
appears to ignore the result (group size 1, operators stay disabled) because
only the equals-append path created a chain, and the tapped operator was
still free.
