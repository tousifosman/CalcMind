### Session log

### Findings

**Keypad 1→N continuations no longer land on one coincident anchor.** The
2026-08-05 open thread ("repeated keypad continuations still stack") was the
default placement always using `result + CONTINUATION_OFFSET`, so every fan
consumer shared endpoints until dragged apart. Misleading symptom then: "only
one connector." Placement now walks the first-cell column, so each new
continuation gets its own row and connectors separate without a manual drag.

### Knowledge revisions

**1. Continuation anchors under the source group's first cell, not below-right of R.**
*Previously believed:* §8.7 / `linking-model.svg` proportions place C' half a
cell right and 1.5 cells down from the source *result*.
*Now known:* C' starts under C's first cell (x = C.anchor.x); vertical pitch is
unchanged; occupied landing rows push further down while x stays on that first
cell.
*What established it:* explicit product direction this session; matches Tydlig's
"on the line below" wording already quoted in §1.1.

**2. Continuation stacking needs bounds overlap, not same-row left-edge banding.**
*Previously believed (this day's earlier revision):* treating a column occupant as
"same left-edge x within half a cell, and same row within `pitch/2`" was enough
to stack under "a cell already there."
*Now known:* a free number in the gap under the group (or slightly x-offset but
still under the first cell's width) overlaps the default landing slot without
matching that band — the link painted on top. Collision must be AABB overlap
against the first cell's horizontal span.
*What established it:* user screenshot of `63 − 3 = 60` continuation covering a
pre-existing green cell; regression tests for gap occupant and offset left edge.
