## Session log

1. User asked to move the keypad's bottom two rows on the number side — the number-editing
   row (`Create link`, `Add components`, `Notes`) and the history row (`Undo`, `Redo`,
   `Backspace`) — to the top of that same column, ahead of the digit grid. First read of the
   request ("those two rows will be the first two rows of buttons on the operator side")
   sounded like a cross-column move; asked the user to confirm before touching layout, and
   they corrected it twice: the operator (accent) column stays untouched, this is a
   within-column reorder only. `Keypad.tsx`'s `mainColumn` now renders `editingRow` →
   `historyRow` → `digitGrid`, in that order. Updated `ARCHITECTURE.md` §8.5's region table
   and the "main column" prose to match the new stacking order. Told the user this was a pure
   reorder with no style changes — wrong, see revision 1 below.
2. User reported the two columns visibly out of alignment on a live device screenshot.
   `historyRow`'s style had never carried its own `marginBottom` — it relied on always being
   the *last* row in the main column, where a trailing margin doesn't matter. Item 1's reorder
   put the digit grid after it, silently collapsing the gap between the history row and the
   `7 8 9` row and shifting every row below it out of line with the operator column's own
   evenly `KEY_GAP`-spaced rows. Fixed by giving `historyRow` an explicit `marginBottom:
   KEY_GAP`, confirmed against a real browser screenshot (Playwright, phone-sized viewport)
   showing every row landing on the same line as its operator-column counterpart. Added a
   `Keypad.test.tsx` case asserting `keypad-number-editing` and `keypad-history` share one
   `marginBottom`, verified it fails without the fix (temporarily reverted the style change,
   confirmed the new test catches it, restored the fix) — same regression-test pattern
   `2026-08-14`'s row-height bug used.
3. User reported the columns *still* misaligned on a real device after item 2's fix. The gap
   check that test added wasn't wrong, but it wasn't the whole invariant: the two columns
   only land on identical row lines because their **total natural heights match** — both
   were 318px before any of this session's changes (five rows carrying `KEY_GAP` plus one
   true last row that doesn't, on both sides — that arithmetic identity was never written
   down anywhere, just true by construction). Item 2's fix correctly gave `historyRow` its
   gap back, but left the digit grid's now-actually-last row (the decimal/`0`/`+/-` row)
   still carrying its own unconditional `marginBottom` from the shared `digitRow` style —
   trailing, wasted space that grew the main column to 324px against the accent column's
   unchanged 318px. Measured directly with Playwright `boundingBox()` against the live web
   build (`react-test-renderer`'s heights matched at 48px each in the *previous* fix's Jest
   run — it doesn't run real layout, so the actual stretch behaviour below was invisible to
   it): the operator column's `body`-level flex container (`align-items: stretch` by
   default) was stretching the shorter accent column to match the taller main column, and
   the browser distributed that 6px of slack as roughly +1px on every one of the accent
   column's six rows — an increasingly common devil, cumulative rounding under flex stretch,
   not a spacing bug localized to one row. Fixed with a new `lastRow` style (`marginBottom:
   0`) applied only to that row, restoring both columns to 318px exactly; confirmed with
   `boundingBox()` that every one of the six row pairs now sits at identical `y` (not just
   approximately — `dy === 0.00` for all six, where the prior "fixed" state showed the
   operator column drifting by ~1px per row). Replaced the marginBottom-equality test from
   item 2 with a stronger one asserting the two columns' total heights match (the actual
   invariant), added `testID`s to the three previously-anonymous digit-grid row containers
   and the last row so the test can read each row's gap directly rather than walking
   `.parent` through `DigitKey`'s internal composite-wrapper chain (verified live that
   `.parent` on a host node lands inside that internal chain, not at the JSX-level row
   `View`, and separately that `findByTestID`'s first tree match for a component like
   `OperatorKey` is the composite itself — which never receives a `style` prop at all, so
   reading `.props.style` off it silently resolved to `undefined`/0 rather than erroring).
   Verified the new test both passes with the fix and fails without it (reverted, watched
   it fail with the exact 324-vs-318 numbers above, restored).

## Knowledge revisions

**1. A row's style can carry hidden position assumptions that only break when it moves.**
*Previously believed (stated to the user, this session):* reordering `mainColumn`'s three
row groups was purely cosmetic — same components, same sizes, so nothing else could change.
*Now known:* `historyRow` had no `marginBottom` because it had always rendered last, where a
trailing margin is invisible; moving it to a non-last position exposed that omission as a
collapsed gap and a real, user-reported misalignment.
*What established it:* the user's screenshot, and reproduced by reverting the fix and
re-running the new alignment test, which failed exactly as expected.
*Standing lesson:* the same one `2026-08-14`'s entry already drew, from the opposite
direction — a layout change that starts comparing two previously-independent things (there:
two columns matching row counts for the first time; here: a row losing its "always last"
position) can expose an assumption neither side's code was ever tested against. Check what a
moved element's own styling assumed about its position, not just whether its content and
size are unchanged.

**2. Revision 1's own fix was still incomplete, and the regression test it added didn't
catch that.** *Previously believed (stated to the user and recorded above as revision 1):*
giving `historyRow` back its `marginBottom` was the complete fix, verified by a passing test
and a screenshot. *Now known:* fixing the moved row's own missing gap left a second,
downstream effect unaddressed — the row that *inherited* "last position" (the digit grid's
decimal/`0`/`+/-` row) still carried a gap that was only ever correct while something
followed it. The two columns' alignment depends on their **total** heights matching, not on
any individual row's gap being individually well-formed; revision 1's test checked two
specific rows agreed with each other, which they did, while the real total-height identity
they were both part of had already drifted 6px. *What established it:* a second live-device
screenshot from the user after the "fixed" push, then `boundingBox()` measurements against
the actual web build (not the Jest suite, which has no real layout engine and had reported
this false-fixed). *Standing lesson:* when a bug's fix is "give the moved thing back what it
implicitly relied on," check every *other* thing that same implicit assumption held for, not
just the one that moved — "last row doesn't need a trailing gap" was never a fact about
`historyRow` specifically, it was a fact about *whichever row ends up last*, and reordering
changed which row that was. A test that re-checks the specific symptom reported is weaker
than one that encodes the actual invariant; the second, stronger test (total-height
equality) is the one that would have caught both bugs in one write.
