# 2026-08-16

## Numeral size becomes a live, persisted Settings preference

### Session log

1. User asked to add a settings item that lets them change the font size — the fourth request
   in a thread that started as "the font in the cell is too big" (2026-08-15) and had, until
   now, always meant "pick a new fixed value for me." This one meant "let me pick it myself,
   permanently."
2. First check: was there already a settings surface to add to? `grep`-ing the codebase found
   none — but before building one from scratch, fetched `origin/main` on a hunch, since the
   session's own branch had been sitting behind main since it forked. Main had, in the
   meantime, merged PR #155: a Settings sheet (`SettingsSheet.tsx`, mode-strip cog, one row —
   About) landed by a different session entirely. Merged main in rather than duplicate that
   work; the user's one-line answer to a design question ("Pull the latest code") only made
   sense in hindsight, once the merge surfaced what it meant.
3. Scoped the actual change: a persisted `numeralFontSize` user preference, threaded live into
   every place that currently reads the static `tokens.numeralFontSize`, plus a Settings row
   to control it. Traced every call site first (`chains/measure.ts`, `chains/layout.ts`,
   `chains/bounds.ts`, `chains/snapping.ts`, `canvas/hitTest.ts`, `store/commands.ts`,
   `nodes/useNodeDrag.ts`, `canvas/NodeLayer.tsx`, `nodes/Cell.tsx` and the six node view
   components) before writing anything, given how much today's own earlier entries already
   established about this exact token's blast radius.
4. **Design decision, made deliberately rather than defaulted into**: `chains/*` (`measure.ts`,
   `layout.ts`, `bounds.ts`, `snapping.ts`) stay free of any store import. `fontSize` is an
   explicit parameter on every function that needs it, defaulted to `tokens.numeralFontSize` —
   the same convention `widthOf` already used. This was chosen over the alternative (read
   `usePreferencesStore.getState().numeralFontSize` directly inside those "pure" modules,
   which would have been far less code) specifically because that alternative reintroduces the
   *exact* failure class this project's own journal already named twice on 2026-08-15: a
   function whose output depends on ambient/implicit state invisible in its own signature. The
   defaulted-parameter approach kept every pre-existing test call site compiling and passing
   completely unchanged (confirmed: the full 790→830 test suite never needed a single existing
   test file touched for this), because a default parameter *is* still an explicit parameter as
   far as the type signature and every caller are concerned.
5. `persistence/load.ts` needed the same parameter threading (`fontSize` alongside `locale`,
   defaulted) rather than reading the store directly, for a structural reason rather than a
   stylistic one: §5's dependency rule (presentation → interaction → domain → engine →
   persistence, never upward) puts `persistence/` below `store/`, so it cannot import a zustand
   store at all, cycle risk or not.
6. Built a new state category: `store/preferencesStore.ts` — persisted, but not part of
   `document` and not undoable, a third kind alongside `documentStore` (persisted + undoable)
   and `uiStore` (neither). Backed by a new minimal `persistence/preferences.ts` contract
   (native: a JSON file sibling to the documents directory; web: see the IndexedDB finding
   below), deliberately without the document adapter's atomic-write/backup machinery — losing
   a font-size preference to a torn write is not the same risk class as losing a document.
7. Changing the setting needs to re-flow every open chain's positions immediately, or existing
   formulas visually desync (stored `position` was computed at the old width). That re-flow
   writes to `document.nodes[…].position` — which lives in `documentStore`, whose only sanctioned
   mutation path is `applyCommand`, which is *always* undoable — but a display-preference change
   is not something a user expects Ctrl+Z to touch, any more than panning the camera is (§7).
   Found the exact precedent already in the codebase: `documentStore.setViewport` bypasses
   undo via a direct `set()` while still notifying autosave. Added a second, general primitive
   next to it, `mutateWithoutUndo`, and a new module `store/reflowAllChains.ts` built on it —
   kept separate from `commands.ts`'s own private per-edit `reflowChain` specifically to dodge
   an import cycle (`commands.ts` already reads the live font size from `preferencesStore.ts`;
   `preferencesStore.ts` cannot then also import `commands.ts`). `reflowAllChainsForDisplay`
   takes `fontSize` as a parameter for the identical reason applied one level up — its own
   direct caller is `preferencesStore.ts`, so reading the store from inside it would just
   relocate the same cycle by one file.
8. `Cell.tsx`'s `glyphTextStyle` (a static `StyleSheet.create` constant every glyph cell
   imported) became `useGlyphTextStyle()`, a hook subscribing to the live font size — the
   weight and maths-axis offset stay from `tokens` unchanged, only the size is user-adjustable.
   Updated all six consumers (`NumberNode`, `OperatorNode`, `EqualsNode`, `ParenNode`,
   `ReferenceNode`, `ResultNode`) to call the hook instead of importing the constant; the three
   components that call `widthOf` directly for their own cell width (`NumberNode`, `ResultNode`,
   `ValueSlider`) now subscribe to the same store slice and pass it explicitly, since a
   non-reactive read would size the cell correctly on the *next* unrelated re-render but not
   immediately when the setting changes.
9. Added a "Numeral size" row to `SettingsSheet.tsx` — a plain −/value/+ stepper (14–30dp,
   step 2, clamped, disables at each end) rather than a custom drag slider: no new
   gesture-handler dependency for a settings row, and it matches every other row in that sheet
   being a plain tap target.
10. First full verification pass (tsc/lint/830 tests/`build:web`) was clean, but **live
    end-to-end verification in the browser was not** — see the IndexedDB finding below, caught
    only by actually reloading the app after changing the setting, something none of the
    automated tests could have caught since they never exercise the real `idb-keyval` adapter
    against real IndexedDB.
11. `ARCHITECTURE.md` gained a new §12.5 (this feature's full design), updates to §1.2's
    `numeralFontSize` row, §8.5's Settings sheet paragraph, §14's testing table, and a new
    decision #19 in §16, all in the same commit as the code.

### Findings

**Two independent `idb-keyval.createStore(sameDbName, differentStoreName)` calls race on who
creates the database's schema — the loser's object store silently never exists.** Built
`preferences.web.ts` to store its blob in a second object store (`preferences`) inside the
*existing* `calcmind` IndexedDB database that `adapter.web.ts` already uses for documents
(`documents` store), on the assumption that two `createStore` calls against the same DB name
would each just get their own store. They don't: `idb-keyval`'s `createStore` opens the
database and only creates the *one* object store it was asked for, inside an `upgradeneeded`
handler that only fires the first time that database name is opened (or its version bumped).
Whichever `createStore` call runs first wins and permanently fixes the schema for that
database; the second store is never created and every transaction against it throws
`NotFoundError: ... object store was not found` — for the life of that IndexedDB database on
that origin, not just that page load. This became a real, live-reproducing bug specifically
*because* of this feature's own design: `usePreferencesStore.getState().hydrate()` runs before
any document loads (`AppShell.tsx`'s startup effect, deliberately ordered so a loaded
document's reflow already knows the right font size) — so on a fresh browser profile, the
preferences store's `createStore('calcmind', 'preferences')` was *always* the first thing to
touch that database name, permanently locking `documents` out and breaking every autosave from
the very first keystroke. The misleading symptom: `autosave: write failed; will retry`
console warnings, easy to read as a transient/retriable glitch, when the object store was
gone for good and every retry would fail identically forever. Fixed by giving preferences its
own database (`calcmind-preferences`) — each `idb-keyval` store then owns its database's
entire lifecycle independently, and the ordering hazard disappears rather than needing to be
managed. **The automated test suite could not have caught this**: `preferences.web.test.ts`
injects an in-memory `PreferencesKeyVal`, exactly per this project's own established DI
pattern for keeping IndexedDB out of Jest — which is correct for testing the adapter's own
logic, but means the real `idb-keyval`/IndexedDB integration, and any interaction between two
*different* adapters sharing infrastructure, is untested by design. Only a live browser
reload — not `tsc`, not lint, not the full Jest suite, all of which stayed green throughout —
surfaced it.

**A default-parameter thread (`fontSize: number = tokens.numeralFontSize`) through a call
chain preserves every existing caller's behaviour for free, at the cost of doing the threading
by hand at every function boundary.** Chosen deliberately over reading the new preferences
store directly inside `chains/*`'s "pure" modules, specifically because 2026-08-15's own two
`nodeHeight`-change entries are, in hindsight, both about exactly this failure mode in
miniature (a self-cancelling default, and a hand-computed test literal, both silently drifting
from a token because nothing forced them to stay explicit). Applying that lesson here meant
more files touched (measure.ts, layout.ts, bounds.ts, snapping.ts, hitTest.ts, load.ts, plus
every production call site) but zero existing test files needed to change, and the resulting
signatures make every function's actual dependencies visible rather than ambient.

**`documentStore.mutateWithoutUndo`'s first draft had a real no-op-detection bug, caught by
its own test.** Modelled on `applyCommand` but using plain `produce` instead of
`produceWithPatches`, with `draft.updatedAt = new Date().toISOString()` stamped
unconditionally (matching `applyCommand`'s own unconditional stamp) — but without
`applyCommand`'s accompanying "ignore a patch that only touches `updatedAt`" filter, a
provably no-op recipe still produced a *different* object (new timestamp), so `next === document`
was never true and every call — even ones that changed nothing — set state and notified dirty.
Fixed by switching to `produceWithPatches` and porting the same meaningful-patch filter
`applyCommand` already uses. Found only because the test asserted `toBe(before)` (reference
equality) on a genuine no-op call, not just on the *value* looking unchanged — an assertion
this project's own `applyCommand` no-op test (`documentStore.test.ts`) already modelled and
that pattern was simply copied forward.

## Cell height made live too; Settings row relabelled, given a unit, made typable

### Session log

1. Two follow-on requests from the same user, in one message: the Settings row's label and
   controls needed polish ("Canvas Number Font Size", a non-editable unit, a typable value
   alongside the +/− stepper), and — separately — the number cell's *height* had stayed
   fixed across a font-size change even though its width already tracked live. The second
   one is the more consequential of the two: decision #19 (above) had only wired width,
   on the reasoning that nothing had asked for height to move. Something now had.
2. Root cause: `tokens.nodeHeight` was a plain constant, read directly (not through any
   `fontSize`-parameterised function) everywhere a cell's box gets computed —
   `chains/measure.ts`'s width floor, `chains/bounds.ts`'s `boundsOf`/`chainBounds`,
   `chains/layout.ts`'s `caretAt`, `canvas/hitTest.ts`'s `containsPoint`,
   `store/commands.ts`'s `continuationAnchor`, and the three components that draw a band
   (`Cell.tsx`, `ResultNode.tsx`, `ValueSlider.tsx`). Width had a live path
   (`widthOf(..., fontSize)`) because decision #19 built one; height never got the
   equivalent.
3. Added `ui/tokens.ts`'s `nodeHeightFor(fontSize) = fontSize + 2 × numberPaddingY`, a new
   `numberPaddingY` token (9) calibrated so `nodeHeightFor(22) === 40` — today's compiled-in
   default, unchanged. Chose *derive it from `fontSize`* over *thread a second independent
   `nodeHeight` parameter everywhere* deliberately: height isn't independent information,
   it's a function of the same font size already in scope at every one of those call sites
   except one (`caretAt`, which gained an explicit third parameter — the only site that
   didn't already have `fontSize` in hand). This is why the fix touched eight files but
   changed zero function signatures other than that one: `nodeHeightFor(fontSize)` is a
   local substitution for `tokens.nodeHeight`, not new plumbing.
4. Two call sites deliberately *not* converted, both already covered by existing doc
   comments once updated: `SPATIAL_HASH_BUCKET` in `bounds.ts` (`2 × tokens.nodeHeight`,
   still static) — a coarse performance-partition bucket size, not a hit-test bound, so it
   doesn't need to track the live value, only stay in the right ballpark. And
   `CONTINUATION_OFFSET` in `commands.ts` — kept as an exported default-size constant;
   `continuationAnchor` itself now computes the live pitch (`nodeHeightFor(fontSize) × 1.5`)
   internally rather than the exported constant becoming a function, since nothing external
   consumes it live.
5. `measuredCellWidth` (`chains/measure.ts`) needed a second, separate font-size parameter
   from its existing one: the width floor must key off the *cell's* live font size, but the
   glyph it measures for an error-mode result renders at the smaller, fixed
   `RESULT_ERROR_FONT_SIZE` — conflating the two would have floored error cells at the wrong
   (smaller) height whenever the user's chosen size exceeded the error font.
6. Full verification (tsc, lint, all 830 tests, `build:web`) was clean with **zero existing
   test files needing changes** — same outcome as decision #19's own thread, for the same
   reason: deriving locally from a parameter already in scope, rather than adding new ones,
   doesn't touch any signature a test already calls. Then verified live in a served
   `dist/` build: placed a number, opened Settings, typed a larger value into the new field,
   watched the on-canvas cell visibly grow before closing the sheet — confirming both the
   height fix and the new typable control in one pass, something the automated suite
   structurally can't check (no test renders the real web build end to end).
7. Settings UI: renamed the row's label ("Numeral size" → "Canvas Number Font Size"),
   added a non-editable "pt" `Text` label so the number's unit isn't ambiguous, and gave the
   value its own `TextInput` (`settings-numeral-size-value`, same testID as the old `Text`
   it replaces) alongside the existing +/− buttons rather than instead of them. The input
   keeps a local `draft` string state, resynced from the live store value on every change
   (including from the +/− buttons, so the two controls can't disagree) and committed
   through the existing clamping `setFontSize` on blur/submit; typing something
   non-numeric reverts the draft to the last live value instead of silently accepting it.
   Verified live: typing `999` (above `NUMERAL_FONT_SIZE_MAX`) clamps to 30; typing `abc`
   reverts to the prior value; the +/− buttons and the typed field observably agree after
   either kind of change.
8. `ARCHITECTURE.md` updated: §1.2's `nodeHeight` row, §8.5's Settings-sheet paragraph
   (row name, unit label, typable field), §12.5's threading writeup and its final bullet
   (previously "`nodeHeight` stays fixed" — now describes `nodeHeightFor`), and a new
   decision #20 in §16 (with #19's revisit-condition cell marked fired, pointing at it).

## Chain members now round and border only the chain's own outer edge, not each cell's

### Session log

1. User pointed at `docs/assets/formula-reference.svg` and named the gap directly: only the
   first and last cell of a group should have rounded corners, and interior cells should
   carry no left/right border — "a cell group looks like a rounded rectangle." Checked the
   reference SVG before touching anything, since it's the ground truth §1.1 already cites:
   its `outerClip`/`innerClip` rects are a single rounded rectangle clipping the *whole
   chain's* border-tint and fill layers, not one rounded rect per cell. Confirmed
   `Cell.tsx` had never implemented that half of §1.1 — every cell independently rendered
   `borderRadius: tokens.cornerRadius` and a full four-side `borderWidth`, regardless of
   chain position, so a snapped chain always showed a rounded-corner notch and a doubled
   border line at every interior seam. This was a gap against an already-written spec, not
   a design decision made today — §1.1's "cells sit flush ... reads as a single pill" bullet
   was already there; the implementation just never matched it.
2. Added `useGroupPosition(nodeId, chainId)` (new file) — reads a node's chain's `members`
   array and returns `'solo' | 'start' | 'middle' | 'end'`, `'solo'` covering both no-chain
   and a one-member chain (a lone cell has no interior to square off, so it keeps rounding
   and bordering exactly as before this change). Wired it into all six node components
   (`NumberNode`, `OperatorNode`, `EqualsNode`, `ParenNode`, `ReferenceNode`, `ResultNode`),
   each passing its own `groupPosition` to `Cell`.
3. `Cell.tsx` turns `groupPosition` into per-corner radii (`cornerRadii`) and left/right
   border widths (`sideBorderWidths`): a `start` cell rounds and borders its left corners
   only, `end` its right only, `middle` neither, `solo` both — top/bottom border stays a
   static full-width style on every cell regardless, matching the reference SVG's border-tint
   layer (visible as a stripe above and below every segment, but only at the two outermost
   edges horizontally). Applied the same per-corner radius to the identity ring and the
   selection-focus ring, not just the band fill — an unrounded rounded ring sitting on a
   now-square middle cell would have been a visible mismatch the reference doesn't have.
4. Verified live rather than trusting `tsc`/lint/tests alone, per this project's own
   standing lesson about that exact overclaim (`2026-08-03` revision 8, re-cited in
   `2026-08-16`'s first entry above): built `dist/`, served it, drove the real keypad
   through a Playwright script (`1221 + 3 - 20 =`) and screenshotted the result. The
   rendered chain shows a rounded left edge on the leading number cell, a rounded right
   edge on the result cell, and flat, borderless seams between every cell in between —
   matching `formula-reference.svg`'s silhouette. Full suite (830 tests, one pre-existing
   flaky timing test excluded — see below), `tsc`, lint, and `build:web` all clean.
5. Updated `ARCHITECTURE.md` §11.3, which had described "Nodes are plain RN `View`s with
   `borderRadius`" as if every cell rounded all four corners independently — added the
   `groupPosition`/`cornerRadii`/`sideBorderWidths` mechanism in the same commit as the code,
   per this project's standing rule against letting the design doc go stale.

### Findings

finding, but worth re-citing here since it's the one thing in this session's own verification
run that wasn't unconditionally green, so a reader shouldn't have to re-derive whether it was
this change's fault.
