## Findings

### Toolchain

**react-native-gesture-handler manual mock omits newly used gestures.**
The project maintains a manual RNGH mock at `__mocks__/react-native-gesture-handler.js`
(rather than transforming the package) because the real implementation requires a native
UI thread. Any new `Gesture.*` call added to production code will break the `App.test.tsx`
render test with `TypeError: Gesture.LongPress is not a function`. Fix: add the new
gesture and any new chainable methods to `makeGestureBuilder`'s `chainable` array and the
`Gesture` object.
*Misleading symptom:* the error appears inside the `Canvas` component render, which looks
like a Canvas bug rather than a missing mock.

### Correctness

**`Gesture.Race` combined with `LongPress` is the right composition for cancellation.**
Pan activates before the long-press timer fires, so a scroll attempt cancels the menu
gesture without any extra logic. This matches the precedence decision below.

## Knowledge revisions

**1. Long-press precedence: context menu wins over P3.7 chain-drag.**
*Previously believed:* the right order was unresolved — §17.1 explicitly deferred it to
P3.
*Now known:* context menu (500 ms long-press) takes precedence over P3.7 long-press-to-
move-chain. P3.7 must check `contextMenu !== null` before activating chain-drag mode.
The motivation: a deliberate-looking hold on a node should always produce the menu first;
chain-drag is a secondary affordance. This is one line in whatever gesture the chain-drag
uses; it is deliberately not baked into Canvas (which stays a generic transform container).
*What established it:* §17.1 was a deferred open question. The 500 ms gesture being `Race`d
with `Pan` already makes pan-during-drag safe; the only remaining ambiguity was which
long-press won. Context menu was chosen because it is the more explicit intent signal.
