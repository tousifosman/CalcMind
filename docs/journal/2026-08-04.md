### Toolchain

**react-native-gesture-handler manual mock omits newly used gestures.**
The project maintains a manual RNGH mock at `__mocks__/react-native-gesture-handler.js`
(rather than transforming the package) because the real implementation requires a native
UI thread. Any new `Gesture.*` call added to production code will break the `App.test.tsx`
render test with `TypeError: Gesture.LongPress is not a function`. Fix: add the new
gesture and any new chainable methods to `makeGestureBuilder`'s `chainable` array and the
`Gesture` object.
*Misleading symptom:* the error appears inside the `Canvas` component render, which looks
like a Canvas bug rather than a missing mock.

### Correctness

**`Gesture.Race` combined with `LongPress` is the right composition for cancellation.**
Pan activates before the long-press timer fires, so a scroll attempt cancels the menu
gesture without any extra logic. This matches the precedence decision below.

## Knowledge revisions

**1. Long-press precedence: context menu wins over P3.7 chain-drag.**
*Previously believed:* the right order was unresolved — §17.1 explicitly deferred it to
P3.
*Now known:* context menu (500 ms long-press) takes precedence over P3.7 long-press-to-
move-chain. P3.7 must check `contextMenu !== null` before activating chain-drag mode.
The motivation: a deliberate-looking hold on a node should always produce the menu first;
chain-drag is a secondary affordance. This is one line in whatever gesture the chain-drag
uses; it is deliberately not baked into Canvas (which stays a generic transform container).
*What established it:* §17.1 was a deferred open question. The 500 ms gesture being `Race`d
with `Pan` already makes pan-during-drag safe; the only remaining ambiguity was which
long-press won. Context menu was chosen because it is the more explicit intent signal.

### Session log

   `escape`/`arrow` commands), `commandFromHardwareKey(key)` mapping a `KeyboardEvent.key` to
   the same commands the on-screen keypad reports (§8.5), and `dispatchEditorCommand` - the
   one function both `Keypad.tsx`'s `onKeyPress` and `AppShell.tsx`'s hardware keydown
   listener call, per the task's "one dispatch function" requirement.
2. Added chain-building commands to `store/commands.ts`: `appendNumberNode`,
   `appendParenNode`, `appendEqualsNode`, `appendOperatorAndNumber`, all going through a new
   internal `appendMembersToChain`. A key press appends to the chain the *selected* node
   already belongs to (creating a one-member chain first if it doesn't have one), computing
   the new member's position with §8.1's flush-layout formula directly - this needed no
   candidate search because typing always knows exactly which chain and index to extend,
   unlike P3's drag-based snapping (§8.2-8.4), which has to disambiguate several nearby
   candidates a *dragged* node might mean to join. Recorded as decision #16 - this is a
   narrower, simpler mechanism than P3's, not a preview of it, and the two shouldn't be
   conflated later.
3. Pressing an operator appends the operator **and** a fresh empty number node in the same
   undo entry (`appendOperatorAndNumber`), so the next keystroke lands in a new operand and
   undo can't strand an operator without one.
4. Wired `AppShell.tsx`'s hardware-keyboard listener and `Keypad.tsx`'s `onKeyPress` prop to
   `dispatchEditorCommand`; added `lastInteractionPoint` to `uiStore` (set on every canvas
   tap) so a key press with nothing selected has somewhere to create its node, matching
   §8.5's "otherwise creates a new node at the caret/last-tap point."
5. Pressing anything but Backspace/Escape/arrows with a `result` node selected is a

   doesn't exist yet, and a half-built version of it would be a placeholder behaviour users

6. Extended `NumberNode.tsx`'s existing `onKeyPress` (previously only Backspace/Escape) to
   route every other recognised key through the same `dispatchEditorCommand`, so a hardware
   keyboard can complete a chain while a number is being edited, not just when nothing is
   focused. Digits, the decimal separator, and a non-empty Backspace are still left to
   `onChangeText`/`parseUserInput`, which already normalise them per locale.
7. Verified end-to-end in a real browser (not just `tsc`/tests): tapping empty canvas, typing

### Findings

#### Toolchain

- **`react-native-gesture-handler`'s web backend treats a bubbling `Enter` or `' '` keydown
  reaching a `GestureDetector`-wrapped view as that gesture's keyboard-activation
  equivalent, regardless of what element is actually focused.** Its
  `KeyboardEventManager.registerListeners()` (`web/tools/KeyboardEventManager.js`) attaches a
  plain native `keydown` listener directly on the gesture's own view, checking only
  `event.key` against `['Enter', ' ']` - it does not check whether that view itself has
  focus. `NumberNode`'s `TextInput` is a DOM descendant of `Canvas`'s `GestureDetector`-wrapped
  view, so pressing Enter while editing a number bubbles straight through it before React's
  own synthetic dispatch even runs (React 17+ delegates all synthetic events to the DOM root,
  so a plain ancestor `addEventListener` between the target and the root always sees a
  bubbling native event first, and calling `stopPropagation()` from inside a React handler -
  including react-native-web's own `TextInput.handleKeyDown`, and `preventDefault()` for that
  matter - happens too late to stop it). The result: completing a chain with Enter also
  silently completed Canvas's `Tap` gesture, at the position of whatever `keydown`'s
  `event.target` was, creating a stray free number node.
  **Misleading symptom:** the extra node appeared only after `=`, at a screen position with
  no visible connection to anything just typed, and it reproduced identically whether or not
  `blurOnSubmit`/`preventDefault` were used on the TextInput - both looked like plausible
  fixes and neither touched the actual cause, because the cause wasn't in React's event
  handling at all.
  **Fix:** `NumberNode.tsx` now adds its own **raw** `keydown` listener directly on the
  input's host DOM node (reached via a plain `ref`, which react-native-web forwards straight
  to the `<input>`) and calls `stopPropagation()` there for `Enter`/`' '` before the event can
  reach Canvas's ancestor listener - dispatching `=` itself from that same raw listener, since
  once propagation is stopped React's own `onKeyPress` for that keystroke never fires either.
  **Generalisable:** any focusable/editable element nested inside a `GestureDetector`-wrapped
  view on web can trigger that gesture via Enter/Space, independent of real pointer input;
  worth checking again if a future feature nests another interactive control inside a gesture
  view.

- **A plain `TouchableOpacity` press starts with a `mousedown`, which blurs whatever
  `TextInput` currently has focus before `onPress` fires.** `NumberNode`'s `onBlur` is
  `deselectNode`, so clicking any on-screen keypad key while editing a number cleared
  `selectedNodeId`/`editingNodeId` *before* that key's `dispatchEditorCommand` call ran -
  every key after the first landed as its own new free node instead of continuing the one
  being edited, since dispatch saw "nothing selected" every time.
  **Misleading symptom:** the very first keypad key press after a tap worked correctly (there
  was nothing focused yet to steal focus from); only the second and later presses in the same
  sequence silently stopped chaining, which reads like a chain-building bug rather than a
  focus-order one.
  **Fix:** every data-entry key in `Keypad.tsx` (`Key`, `DigitKey`, `OperatorKey`,
  `EqualsKey`) now takes `onMouseDown={(e) => e.preventDefault()}` - the standard fix for an
  on-screen keyboard's keys not stealing focus from the field they edit. Unrecognised (and
  harmless) on native, where `TouchableOpacity` has no mouse events to steal focus with.
  **Generalisable:** any future on-screen pressable meant to act on a currently-focused text
  field needs the same guard; it's easy to verify only with real clicks in a browser; a jest
  render test that just calls `.props.onPress()` directly (as this project's existing keypad
  tests do) can't see it, since it skips the DOM mousedown entirely.

### Knowledge revisions

**1. Chain construction was assumed to be entirely P3's job.** *Previously believed:*
`store/commands.ts`'s own header comment ("Chain mutations - snap, drag, detach - land in P3
once the layout pass exists to give them something to act on") plus P2.4/P2.7's addenda,
which explicitly deferred chain assembly to later phases. *Now known:* typing needs its own,
much simpler chain-building path - appending to *the chain the selected node already belongs
to* is a one-line lookup, not the geometric candidate search P3's drag/snap has to run
against several nearby free nodes - so it doesn't actually depend on P3's snapping machinery
and can (and per this task's acceptance criteria, must) exist before P3 does. Recorded as
decision #16 so this isn't re-derived as a P3 duplicate later. *What established it:* P2.8's
own acceptance criterion ("completing a full chain by typing") is unsatisfiable without some
chain-building mechanism, and none of P3's tasks are prerequisites for the simpler,
selection-anchored version this task needed.

**Standing lesson:** "P3's job" in this file's task headers describes the *drag-gesture*
mechanism specifically (§8.2-8.4's candidate resolution), not "anything that touches
`document.chains`" - a deterministic, non-geometric way to extend a chain can land earlier
if a task's acceptance criteria require it.

### Open threads

- **Continuation (§8.7) is still unimplemented**, tracked by the `TODO(P4.9)` in
  `dispatchEditorCommand` rather than a placeholder. What would close it: P4's engine
  landing far enough to produce a `ResultNode`, plus a reference-node creation command - both
  outside this task's dependencies (P2.3, P2.6, P2.7 only).
- **`appendMembersToChain` doesn't create a `ResultNode` when `=` is appended**, even though
  §9's state diagram shows "`=` appended → result node created" as one transition. Left out
  deliberately: no engine exists yet to give a result a value, and `widthOf`'s own comment for
  the `result` case already says as much ("No engine yet (P4)"). Whichever P4 task wires
  evaluation should decide whether it creates the `ResultNode` reactively (watching for a
  chain becoming `Valid` with a trailing `=`) or whether an append command needs to create an
  empty one for it to fill in - either is compatible with what's here, since a chain's
  `members` array never includes its result node in this codebase's model (§6: `ResultNode`
  points to its chain via `sourceChainId`, not the other way around).
- **Arrow-key chain navigation (`dispatchEditorCommand`'s `arrow` case) is implemented and
  unit-tested but has no chain to navigate yet in normal use** - the only way a chain exists
  at all before P3 lands is via this task's own typing-driven `appendMembersToChain`. Once
  P3's drag/snap-built chains exist too, worth a real-device pass to confirm arrow navigation
  still reads correctly across a chain assembled by dragging rather than typing.
