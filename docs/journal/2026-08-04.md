### Findings

#### Toolchain

- **`react-native-gesture-handler`'s web backend treats a bubbling `Enter` or `' '` keydown
  reaching a `GestureDetector`-wrapped view as that gesture's keyboard-activation
  equivalent, regardless of what element is actually focused.** Its
  `KeyboardEventManager.registerListeners()` (`web/tools/KeyboardEventManager.js`) attaches a
  plain native `keydown` listener directly on the gesture's own view, checking only
  `event.key` against `['Enter', ' ']` - it does not check whether that view itself has
  focus. `NumberNode`'s `TextInput` is a DOM descendant of `Canvas`'s `GestureDetector`-wrapped
  view, so pressing Enter while editing a number bubbles straight through it before React's
  own synthetic dispatch even runs (React 17+ delegates all synthetic events to the DOM root,
  so a plain ancestor `addEventListener` between the target and the root always sees a
  bubbling native event first, and calling `stopPropagation()` from inside a React handler -
  including react-native-web's own `TextInput.handleKeyDown`, and `preventDefault()` for that
  matter - happens too late to stop it). The result: completing a chain with Enter also
  silently completed Canvas's `Tap` gesture, at the position of whatever `keydown`'s
  `event.target` was, creating a stray free number node.
  **Misleading symptom:** the extra node appeared only after `=`, at a screen position with
  no visible connection to anything just typed, and it reproduced identically whether or not
  `blurOnSubmit`/`preventDefault` were used on the TextInput - both looked like plausible
  fixes and neither touched the actual cause, because the cause wasn't in React's event
  handling at all.
  **Fix:** `NumberNode.tsx` now adds its own **raw** `keydown` listener directly on the
  input's host DOM node (reached via a plain `ref`, which react-native-web forwards straight
  to the `<input>`) and calls `stopPropagation()` there for `Enter`/`' '` before the event can
  reach Canvas's ancestor listener - dispatching `=` itself from that same raw listener, since
  once propagation is stopped React's own `onKeyPress` for that keystroke never fires either.
  **Generalisable:** any focusable/editable element nested inside a `GestureDetector`-wrapped
  view on web can trigger that gesture via Enter/Space, independent of real pointer input;
  worth checking again if a future feature nests another interactive control inside a gesture
  view.

- **A plain `TouchableOpacity` press starts with a `mousedown`, which blurs whatever
  `TextInput` currently has focus before `onPress` fires.** `NumberNode`'s `onBlur` is
  `deselectNode`, so clicking any on-screen keypad key while editing a number cleared
  `selectedNodeId`/`editingNodeId` *before* that key's `dispatchEditorCommand` call ran -
  every key after the first landed as its own new free node instead of continuing the one
  being edited, since dispatch saw "nothing selected" every time.
  **Misleading symptom:** the very first keypad key press after a tap worked correctly (there
  was nothing focused yet to steal focus from); only the second and later presses in the same
  sequence silently stopped chaining, which reads like a chain-building bug rather than a
  focus-order one.
  **Fix:** every data-entry key in `Keypad.tsx` (`Key`, `DigitKey`, `OperatorKey`,
  `EqualsKey`) now takes `onMouseDown={(e) => e.preventDefault()}` - the standard fix for an
  on-screen keyboard's keys not stealing focus from the field they edit. Unrecognised (and
  harmless) on native, where `TouchableOpacity` has no mouse events to steal focus with.
  **Generalisable:** any future on-screen pressable meant to act on a currently-focused text
  field needs the same guard; it's easy to verify only with real clicks in a browser; a jest
  render test that just calls `.props.onPress()` directly (as this project's existing keypad
  tests do) can't see it, since it skips the DOM mousedown entirely.

### Findings

#### Correctness

- **`react-native-web`'s `TextInput.onKeyPress` fires from a native `keydown` listener without
  calling `preventDefault()` for you** (`TextInput/index.js`'s `handleKeyDown`: it calls
  `onKeyPress(e)` and only conditionally prevents default for `Enter`). If an app's own
  `onKeyPress` handler responds to a key by synchronously changing which node is being edited
  - as `NumberNode.tsx`'s did for every operator/paren/backspace-on-empty key, via
  `dispatchEditorCommand` - React re-renders and moves focus to a *different* `<input>` before
  the browser gets to apply that keydown's own default action (inserting the character). The
  browser then applies it to whatever is focused *now*, not to the element the keydown actually
  started on. Concretely: typing `3` then `-` fired `appendOperatorAndNumber`, which creates a
  fresh empty operand and switches `editingNodeId` to it, synchronously, inside the `-`
  keydown's own handler - and the still-in-flight default action then inserted `-` into that
  *new*, just-focused input, which should have started empty. Typing `4` next gave `"-4"`, not
  `"4"`: a hardware-typed subtraction silently negated its second operand.
  **Misleading symptom:** `+` triggers the exact same race and the exact same leaked keystroke,
  but produces no visible symptom, because `+` isn't valid canonical raw (`isCanonicalRaw`
  requires an optional **leading** `-` only) - `parseUserInput` silently rejects it and the
  keystroke vanishes without a trace. P2.8's own journal entry (session log item 7) verified a
  hardware-typed `12 + 34 =` chain and reported it correct, which was true, and also happened
  to be the one operator that couldn't have shown this bug.
  **Fix:** `handleKeyPress` now calls `e.preventDefault()` for every key it's about to hand to
  `dispatchEditorCommand`, so the browser never performs the default insertion regardless of
  which input ends up focused afterward. Digits and the decimal separator are unaffected -
  they still return early and go through `onChangeText`/`parseUserInput` as before.
  **Generalisable:** any handler that changes DOM focus synchronously in response to a keydown,
  without cancelling that keydown's default action, risks the browser applying the default to
  the new focus target instead of the original one. Test operator/command keys that also
  happen to be valid input characters (`-`, `.`) specifically - they're the ones that turn this
  class of race into a silent data-corruption bug instead of a silently-dropped keystroke.

### Knowledge revisions

**2. "Verified with a real keyboard in a browser" (P2.8) was true and still missed a real bug.**
*Previously believed:* P2.8's journal entry recorded a real-browser hardware-keyboard

## P3.2 — Node bounds and neighbour queries

### Session log

1. Added `src/chains/bounds.ts` as the geometry layer P3's snapping search needs: `boundsOf`, `verticalOverlap`, `memberBoundaries`, and `makeSnappingNeighbours`. The implementation is deliberately O(n) per §8.4, but behind a tiny `SnappingNeighbours` interface (`chainsNear`, `freeNodesNear`) so P3.3 can call a stable surface when the scan is later replaced with a spatial hash.
2. Kept the helpers pure and layout-driven rather than store-aware: node bounds come from `position` + `widthOf` + `tokens.nodeHeight`, chain bounds from `chain.anchor` plus the summed member widths, and insertion boundaries from the same left-to-right accumulation §8.1 uses. Like `layoutChain`, missing member ids are skipped rather than thrown on, so a transiently stale `members` array does not crash a read-only geometry pass.
3. Added focused tests in `src/chains/bounds.test.ts` for exact threshold behaviour, not just obvious inside/outside cases: boxes that only touch vertically still count as zero-gap, a candidate whose vertical gap is exactly `SNAP_VERTICAL - 1` is included, and one at exactly `SNAP_VERTICAL` is excluded by §8.3's strict `< SNAP_VERTICAL` comparison. Also covered self-exclusion, chained-vs-free filtering, and insertion boundaries between adjacent chain members.
4. While writing those tests, found and fixed my own first implementation error: I had compared against `tokens.snapVertical`, but snapping thresholds are interaction constants from §8.2, not design tokens from §1.2. Because no such token exists, every neighbour filter silently returned empty. The fix was to export named `SNAP_DISTANCE`, `SNAP_VERTICAL`, and `DETACH_DISTANCE` constants from `bounds.ts`, which P3.3 can now import instead of re-inlining numbers.

### Knowledge revisions

**4. Snap-threshold tests must be written against bounding-box gaps, not anchor deltas.**
*Previously believed:* placing a candidate chain at `dragged.y + SNAP_VERTICAL` exercised the exact vertical-threshold boundary.
*Now known:* `verticalOverlap` compares the gap between bounding boxes, so with 64dp-tall nodes a candidate whose `top` is only 48dp below the dragged node still overlaps it by 16dp and therefore has a vertical gap of `0`, not `48`. The real threshold case is `candidate.top = dragged.bottom + SNAP_VERTICAL` (outside) and one unit less (inside).
*What established it:* the first version of `bounds.test.ts` failed while the helper logic was otherwise correct; recomputing the geometry from `tokens.nodeHeight` and the actual `verticalOverlap` formula showed the test setup, not the algorithm, was wrong.

## P3.3 — Snap candidate resolution

### Session log

1. Implemented `src/chains/snapping.ts`: pure `resolveSnapCandidate(dragged, neighbours, nodes, locale)` returning `prepend` / `append` / `insert` / `newChain` / `null`, gathering §8.3 candidates through P3.2's `SnappingNeighbours` and keeping the nearest by the same horizontal distance that passed the threshold. Thresholds imported from `bounds.ts` (`SNAP_DISTANCE` etc.) — never inlined.
2. Table-driven tests in `src/chains/snapping.test.ts` at each threshold boundary (strict `< SNAP_DISTANCE`), both NEW_CHAIN member orders, nearest-wins between a chain and a free node, vertical gating inherited from neighbours, own-chain exclusion while still a member, and the §8.2 hysteresis case (`DETACH_DISTANCE > SNAP_DISTANCE` → just-detached node does not re-snap into the vacated slot).
3. While writing the INSERT cases, found that a center placed "just inside" one boundary can also fall inside `SNAP_DISTANCE` of the neighbouring boundary when members are narrow (operator width 34 is only 6 above `SNAP_DISTANCE` 28). Nearest-wins then returns the other index. Tests place the center on the side of boundary 1 away from boundary 2, and align exactly with boundary 2 for the second-index case.

### Findings

**INSERT threshold tests must keep neighbouring boundaries out of range.**
`memberBoundaries` are only one member-width apart. With `operatorWidth = 34` and `SNAP_DISTANCE = 28`, a dragged center within 28 of boundary *i* is often also within 28 of boundary *i±1*, and nearest-wins picks the closer one. An "INSERT at index 1 just inside threshold" fixture that sits between two boundaries will silently assert the wrong outcome (or pass for the wrong reason). Place the center on the outer side of the target boundary, or align it exactly when adjacent spacing is `≥ SNAP_DISTANCE`.

### Knowledge revisions

*(none — §8.3's pseudocode mapped onto the P3.2 neighbour interface without overturning a prior belief.)*

- Detach distance measurement itself (from home slot vs. from chain AABB vs. from press origin) is P3.5's concern; P3.3 only proves that once a free node sits `DETACH_DISTANCE` from a slot, resolve returns none.

## P3.6 — Insertion feedback

### Session log

1. Added `insertionFeedback` to `src/chains/layout.ts`: pure §8.3 mid-drag preview that

   and caret both clear when `candidate` is null, so leaving range closes the gap with no

3. 8 new tests in `layout.test.ts` covering null-candidate clear, prepend/append/insert/
   index-0, both `newChain` directions, and a missing chain id. Full suite 270 passing.

### Findings

**Gap preview must use `left` offsets, not a second `transform`.**
`PositionedNode` already applies a Reanimated `transform` for the drag delta. In RN, later
`transform` style entries replace earlier ones rather than composing, so a gap
`translateX` written beside the animated style is wiped to `0` on every frame while idle
siblings are "not dragging." Shifting via `left: position.x + gapOffset` sidesteps the
conflict and also matches commit geometry: on release, `clearDragSnap` and

`gapOffset = 0` and the laid-out `position.x` already advanced — no jump.
*Misleading symptom:* members twitch back to flush for one frame on snap commit even though
the final layout is correct.

P3.5 already publishes `uiStore.dragSnap` every drag frame for this task to consume. P3.6
adds no document/`applyCommand` writes mid-drag; the gap is a view-only offset. A true
UI-thread-only caret (shared values, no JS store) would mean redoing P3.5's candidate
publish path — out of scope here and not required once the ephemeral/document split is
respected.

to `#F3F4F6` and floored caret width at 4dp. Same class of failure as the 0×0 web page: the
structure was correct and the eye was the only detector.
*Misleading symptom:* `insertion-caret` testID count is 1 and `boundingBox` is non-null, yet the
screen looks unchanged.

### Session log

1. Implemented the pure half of the calculation engine (§10.1 pipeline through display
   formatting), as tasks P4.1–P4.5. No React, no store — `src/engine/` only.

     Empty / Incomplete / Valid / Invalid / Evaluated; `Stale` and `ErrorState` live on the
     same union for P4.7–P4.8 to apply once a result exists.
   - `parse.ts` — precedence climbing with `parsePrefix` / `parsePostfix` / `parsePrimary`
     seams for the §10.2 extension path. Implicit `×` only before `(`.
   - `evaluate.ts` — decimal.js at precision 34; errors are values; nothing throws out.
   - `format.ts` — added `formatComputedValue` / `parseComputedDisplay` for the result-cell
     half of §10.3 (12 sig digs, scientific at `1e12` / `1e-6`, locale on the mantissa).
2. Table-driven tests per §14; property test that `formatComputedValue` never emits a string
   `parseComputedDisplay` rejects. Full suite still green alongside the existing engine
   (numeric / formatForDisplay) tests.
3. Tick P4.1–P4.5 in `DEVELOPMENT_PLAN.md`; P4.6 and P4.7 are now amber (ready).

### Findings

**Scientific result display cannot round-trip through `parseUserInput`.**
`formatComputedValue` emits `1.23e+12` (locale on the mantissa only). `parseUserInput` /
`isCanonicalRaw` deliberately reject `e` — `NumberNode.raw` must stay a plain decimal so a
document written in one locale opens in another without `1.020` ambiguity (decision #11).
The property test therefore undoes through a sibling `parseComputedDisplay`, not through
`parseUserInput`. Reusing `parseUserInput` for scientific would either corrupt the raw
contract or force scientific into storage.
*Misleading symptom:* "the formatter never emits something it cannot re-parse" (§14) reads
like it names the existing parse function; it names the *round-trip property*, and the
computed-value half of `format.ts` needs its own undo.

**`validateChain` does not produce `Stale` or `ErrorState`.**
Those are lifecycle statuses (§9: Evaluated → Stale on input change; Evaluated → ErrorState
on divide-by-zero / overflow / cycle). Structural validation of the member sequence cannot
observe them. The `ChainStatus` union still carries both so P4.7–P4.8 write the same type;
P4.2's "returns exactly one of …" acceptance is satisfied by the type, with the structural
subset covered by the table-driven tests. The §9 diagram transitions into Stale / ErrorState
are integration tests for the result lifecycle, not for `validate.ts`.

**Division by zero is diagnosed before `0 ÷ 0` can become `NaN`.**
decimal.js returns `Infinity` for `1/0` and `NaN` for `0/0`. We check `right.isZero()`
before dividing and always return `DivideByZero`. That prefers the more specific diagnosis
over `NotANumber` for the indeterminate form, and keeps "never Infinity" (§10.3) as a single
branch.
