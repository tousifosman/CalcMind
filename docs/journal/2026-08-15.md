## Cell numeral font too big and too heavy

### Session log

1. User reported the font in the cell was too big and asked for it to be reduced and no
   longer bold.
2. Traced it to `glyphTextStyle` (`src/nodes/Cell.tsx`), the single shared text style every
   glyph cell renders through (`NumberNode`, `OperatorNode`, `EqualsNode`, `ParenNode`,
   `ReferenceNode`, `ResultNode` all import it) — reading `tokens.numeralFontSize` (30) and
   `tokens.numeralFontWeight` ('800'). One token change covers every cell kind.
3. Reduced `numeralFontSize` to 22 and `numeralFontWeight` to `'400'` in `src/ui/tokens.ts`.
   These were the §1.2 reference-image-sampled values (30 = 127px reference glyph, ratio

   `fontSize` argument and `GLYPH_WIDTH_AT_BASE_SIZE` scales relative to
   `BASE_FONT_SIZE = tokens.numeralFontSize`, so cell width tracks the new size
   automatically — no separate change needed there. Updated its header comment's "weight
   800" mention to 400; left the fixed per-glyph pixel table alone since it was already
   documented as a first guess to be calibrated against real rendering, not exact for either
   weight.
5. Ran the full verification set: `tsc --noEmit` clean, `lint` clean, all 790 tests green
   (`measure.test.ts`'s error-vs-numeral-width inequality still holds — different font sizes
   still produce different widths), `build:web` emits `dist/`. Confirmed visually: built the
   web target, served it, and screenshotted a live `123 + 456 = 579` chain via Playwright —
   the numerals read noticeably smaller and unbolded against the cell, `+`/`=` glyphs
   unaffected since they render through fixed-width symbol cells.
6. Updated `ARCHITECTURE.md` §1.2's token table (`numeralFontSize` row) and §16's decisions
   log in the same commit as the code change.

### Findings

None beyond what's already documented in `measure.ts` about the glyph-width table being a
first guess.

### Knowledge revisions

None — this is a design-token tuning change, not a corrected belief. The reference-image

## Cell padding still read as excessive after the font shrink

### Session log

1. User asked to also reduce the cell padding, as a follow-up to the font-size session above.
2. Before touching `tokens.numberPaddingX`, checked why a smaller glyph alone left visible
   extra whitespace: `widthOf` (`src/chains/measure.ts`) sizes number/result/reference cells
   as `measureTextWidth(text, fontSize) + 2 * numberPaddingX`, and `measureTextWidth` scales
   `GLYPH_WIDTH_AT_BASE_SIZE`'s fixed dp table by `fontSize / BASE_FONT_SIZE`. Every call site
   in the app uses the default `fontSize = tokens.numeralFontSize`, and `BASE_FONT_SIZE` is
   also `tokens.numeralFontSize` — the same token read twice — so that scale factor is `1`
   for any value the token holds. The glyph-width table's absolute dp numbers, not the token,
   are what actually drive cell width; changing `numeralFontSize` alone shrinks the rendered
   glyph but leaves the pill exactly the size it was before.
3. This means step 4 of the font-size session above was wrong to say cell sizing "tracks the
   new size automatically" — it doesn't, and that's precisely why the box now had visibly more
   room around a smaller glyph than before. Recorded as a revision below rather than editing
   that earlier claim.
4. Fixed by re-deriving `GLYPH_WIDTH_AT_BASE_SIZE`'s four entries from the original 30/800
   calibration (18/8/13/9), scaled by the 22/30 size ratio: digit 18→13, narrow 8→6, sign
   13→10, space 9→7. Left a comment on `BASE_FONT_SIZE` explaining the self-cancelling
   read so the next token change doesn't repeat this.
5. Reduced `tokens.numberPaddingX` from 12 to 8 (also ratio-scaled down from the reference,
   alongside `numeralFontSize`/`numeralFontWeight` in decision #18 — folded into the same
   decisions-log row rather than adding a new one).
6. Verified: `tsc --noEmit` and `lint` clean; full suite green except
   `snapSearch.profile.test.ts`'s cached-hash-vs-linear timing assertion, which failed once
   under the parallel test-runner's CPU contention (received 4ms against a ≤2.05ms budget) and
   passed clean in isolation and on a full re-run — a known class of flake for that file, not
   caused by this change (`numberPaddingX`/glyph widths never touch spatial-hash code).
   `build:web` emits `dist/`. Confirmed visually via the same Playwright screenshot method as
   the font-size session: the `123 + 456 = 579` chain's number/result cells are now visibly
   tighter around the digits, not just smaller-fonted inside the same box.
7. Updated `ARCHITECTURE.md` §1.2's `numberPaddingX` row and folded the `measure.ts` fix into
   decision #18 in §16, in the same commit as the code.

### Findings

**A "scale by `current / base`" ratio where both sides read the same live token is not a
scale — it's always 1, whatever the token holds.** `BASE_FONT_SIZE = tokens.numeralFontSize`
and `widthOf`'s default `fontSize` argument is also `tokens.numeralFontSize`; every ordinary
call therefore computes `tokens.numeralFontSize / tokens.numeralFontSize`. The fixed
`GLYPH_WIDTH_AT_BASE_SIZE` table is calibrated to whatever the token's value *was* when the
numbers were last hand-derived, and only actually changes when someone edits the table itself
— the token's own value does not propagate into it. Only P7's future "adjustable text size"
feature (which was always meant to pass a *different* explicit `fontSize` than the token) would
ever see this ratio move. The misleading symptom: `tsc`, lint, and all 790 tests stayed green
through the original font-size change, because nothing in the test suite asserts cell width
against an independent expectation — `measure.test.ts`'s width tests compare `widthOf` outputs
against `widthOf`/`measureTextWidth` computed the same way, so they can't catch the table
itself being stale.

### Knowledge revisions

**1. `numeralFontSize` changing was believed to reflow number-cell width automatically; it
does not.**
*Previously believed (this same file, font-size session, step 4):* "`widthOf` reads
`tokens.numeralFontSize` for its default `fontSize` argument and `GLYPH_WIDTH_AT_BASE_SIZE`
scales relative to `BASE_FONT_SIZE = tokens.numeralFontSize`, so cell width tracks the new
size automatically."
*Now known:* `BASE_FONT_SIZE` and the default `fontSize` argument are the same token read
twice, so the scale factor is always 1 on the default call path; only the fixed
`GLYPH_WIDTH_AT_BASE_SIZE` dp table drives number/result/reference cell width, and it has to
be hand-recalibrated whenever `numeralFontSize` changes. The original font-size commit shrank
the rendered glyph but left every number cell exactly as wide as before — the "padding" the
user then asked to reduce was substantially this gap, not just `numberPaddingX`.
*What established it:* reading `sumGlyphWidths`/`BASE_FONT_SIZE` in `measure.ts` after the
user's follow-up request, and confirming with the before/after Playwright screenshots that
cell width only actually changed once the table was re-derived.
*Standing lesson:* a "self-scaling" constant defined from the same live value it's meant to
scale against is a no-op in disguise; when a design token drives a derived fixed table (not a
live formula), changing the token does not change the table — grep for every place a token
feeds a *cached*/*hand-written* value, not just a live computation, before claiming a token
change "propagates automatically."

## Padding halved again (8 → 4)

### Session log

1. User asked to reduce the cell padding further, by 50%, as a second follow-up in the same
   PR (#156).
2. Changed `tokens.numberPaddingX` from 8 to 4 in `src/ui/tokens.ts`; folded into the existing
   decision #18 row in `ARCHITECTURE.md` §16 and its §1.2 token-table row, rather than adding a
   new decision for what is the same tuning thread.
3. `tsc --noEmit`, `lint`, and the full 790-test suite all stayed green; `build:web` still
   emits `dist/`.
4. First visual check was a false negative: re-ran the same `123 + 456 = 579` Playwright
   screenshot used for the prior two commits and it looked pixel-identical to the padding=8
   version. Cause, not a bug: `widthOf`'s `measuredCellWidth` is
   `max(nodeHeight, text + 2 × numberPaddingX)`, and for 3-digit numbers at the current glyph
   table (`digit: 13`), `13×3 + 2×4 = 47` and `13×3 + 2×8 = 55` both land under the `nodeHeight`
   floor of 64 — so this fixture can't distinguish the two padding values and hasn't been able
   to since the padding=8 commit either. Re-verified against a 7-digit number
   (`1,234,567`, past the floor): measured bounding-box width came back 111px, matching
   `13×7 (digits) + 6×2 (two grouping commas) + 2×4 (padding) = 111` exactly.
5. Standing note for future padding/font tuning in this project: pick a fixture with enough
   digits to clear `nodeHeight` (roughly 5+ digits at the current glyph width) before trusting
   a screenshot to show a padding change — a 3-digit demo chain will look unchanged even when
   the token moved, because the floor, not the padding, is setting its width.

### Findings

**`nodeHeight` floors `measuredCellWidth`, so short numbers can fully absorb a padding change
with zero visible effect.** `Math.max(tokens.nodeHeight, measureTextWidth(text, fontSize) + 2 *
tokens.numberPaddingX)` — any number whose glyph-width-plus-padding sum stays under 64 renders
at exactly 64 regardless of what `numberPaddingX` is. The misleading symptom: a before/after
screenshot of a 3-digit demo (`123`, `456`, `579`) reads as "the change did nothing," when the
change is real and only invisible on cells too short to clear the floor. Use a longer number
(or check the rendered `boundingBox()`/`widthOf` output directly) to confirm a padding or
glyph-width change actually landed.

### Knowledge revisions

None — the floor behaviour above is existing, documented design (`measuredCellWidth`'s
`Math.max` with `nodeHeight`), not a corrected belief; the finding is about which fixture
proves a change, not about what the code does.

## Vertical space above/below the cell text

### Session log

1. User reported "a lot of space above and below the cell" — a different axis from the three
   prior horizontal-padding follow-ups: `Cell.tsx`'s `band` style holds `height:
   tokens.nodeHeight` fixed at 64 and centres its content with flex, so shrinking the glyph
   (30→22, this session's first commit) left more of that fixed 64dp band empty above and below
   the now-smaller text.
2. Reduced `tokens.nodeHeight` 64→48 in `src/ui/tokens.ts`, and scaled `mathAxisOffset` 4→3
   alongside it to hold the same ~0.063-of-band-height ratio the §1.2 reference geometry set
   (`nodeHeight` is what that offset is a fraction of).
3. Audited every `tokens.nodeHeight` read before changing it (`hitTest.ts`, `bounds.ts`
   including `SPATIAL_HASH_BUCKET = 2 × nodeHeight`, `commands.ts`, `measure.ts`'s width floor)
   — all read the live token, unlike the self-cancelling `BASE_FONT_SIZE` bug from this
   session's first follow-up, so no equivalent silent no-op risk here. Grepped for hardcoded
   `64` literals tied to it in source and tests; found none outside comments and one unrelated
   `connectorPath` test fixture.
4. Found one real casualty: `SNAP_VERTICAL = 48` (`bounds.ts`) is documented in
   `ARCHITECTURE.md` §8.2 as "0.75 × `nodeHeight`" from when `nodeHeight` was 64. It's a
   hardcoded interaction-tuning constant, not derived from the token, so its value didn't move
   — but the ratio claim in the doc became false (48 is now 1.0×, not 0.75×, of the new 48dp
   `nodeHeight`). Left the constant itself untouched — it governs live drag-snap feel, which
   this change had no reason to also retune — and corrected the doc to explain why the ratio
   note is now stale instead of silently deleting it.
5. Full verification caught a second, more concrete casualty: `keymap.test.ts`'s continuation
   test asserted `contChain.anchor.y` against a hardcoded `sourceChain.anchor.y + 96` — 96 being
   `CONTINUATION_OFFSET.y` (`commands.ts`, `tokens.nodeHeight * 1.5`) evaluated at the old
   `nodeHeight`. Fixed by importing and asserting against the live `CONTINUATION_OFFSET`
   constant instead of the literal, so the test can't silently drift from the token again.
6. `tsc --noEmit`, `lint`, and the full 790-test suite green (this was the first of the four
   font/padding/height follow-ups today where a real, not-a-floor-artifact test failure
   surfaced — see Findings). `build:web` emits `dist/`. Verified visually: rendered
   `123 + 456 = 579` and measured the number cell's `boundingBox()` directly — 48×48,
   matching the new token exactly — then screenshotted and confirmed the vertical whitespace
   around the glyphs visibly tightened while `+`/`=` stayed legible and centred.
7. `ARCHITECTURE.md` §1.2's `nodeHeight`/`mathAxisOffset` rows, §8.2's `SNAP_VERTICAL` note,
   and §16's decision #18 all updated in the same commit.

### Findings

**A token read consistently everywhere is not automatically safe to change — hardcoded
constants *derived from* its old value, in both source and tests, are a separate audit.**
Every production read of `tokens.nodeHeight` was live (no repeat of the `BASE_FONT_SIZE`
self-cancelling bug from earlier today), but `CONTINUATION_OFFSET.y` — itself correctly derived
live as `tokens.nodeHeight * 1.5` — had its *result* hardcoded as a bare `96` in a test
assertion, which only breaks the moment the token's value actually changes. Grepping for the
token's name finds every live reader; it does not find a numeral test authors computed by hand
once and pasted in. Cross-check hardcoded numerals in tests against the constants they were
computed from, not just against the token itself.

### Knowledge revisions

None — no belief here was wrong; this is new tuning plus overdue debt (the stale test literal,
the stale doc ratio) that only surfaces when the underlying token actually moves.

## `nodeHeight` still looked spacious at 48; cut again to 40, and a second stale-geometry test

### Session log

1. User pushed back on the screenshot from the previous follow-up: still "a lot of space above
   and below the numbers" at `nodeHeight = 48`. Checked the ratio: 22/48 ≈ 0.46 is actually very
   close to the *original* reference ratio (30/64 ≈ 0.47) — the two prior cuts (font, then
   height) had tracked each other closely enough that the band-to-glyph proportion barely moved
   from where it started. The original proportion just reads emptier at regular weight and a
   smaller absolute size than it did at the reference's bold 800/30px, even though the fraction
   is nearly identical.
2. `nodeHeight` also sizes the cell's tap/drag hit box (`canvas/hitTest.ts` uses it directly;
   there is no separate `hitSlop`), so cutting it further is a real interaction-size trade-off,
   not a purely cosmetic one — asked the user how far to take it rather than guessing past a
   common accessibility floor unprompted. Chose "moderate, ~40dp" over "hug the text, ~32dp" or
   an exact number.
3. Set `nodeHeight = 40` and `mathAxisOffset = 2` (rounded from the same ~0.0625 reference
   ratio applied twice: 0.0625 × 40 = 2.5, rounded down).
4. Full suite caught a second, subtler geometry casualty beyond the `keymap.test.ts` one from
   the previous cut: `snapping.test.ts`'s "just past `DETACH_DISTANCE` from the vacated insert
   slot does not re-snap" started returning an `append` candidate instead of `null`. Root cause
   traced algebraically, not guessed: the test's fixture chain is `[a="12", c="3"]`, and single/
   double-digit numbers floor to `tokens.nodeHeight` width (`measuredCellWidth`'s `Math.max`).
   The dragged node's placement — `slotX + DETACH_DISTANCE - halfW`, `halfW = nodeHeight / 2` —
   correctly targets the *insert* boundary between `a` and `c`, but the gap from the dragged
   node's left edge to the chain's unrelated *right* edge works out to
   `DETACH_DISTANCE - 1.5 × nodeHeight`, which only stays outside `SNAP_DISTANCE` (28) while
   `nodeHeight` is large enough — exactly `48` was the knife-edge (`28` vs `SNAP_DISTANCE`'s
   strict `>=` 28, i.e. still just excluded), and `40` pushed it to `16`, inside the threshold.
   Fixed by widening `c` to an 8-digit raw so its measured width (and the chain's right edge)
   stays safely far from the dragged node regardless of `nodeHeight`'s value, instead of
   depending on `c` happening to floor to the same width as the dragged node.
5. `tsc --noEmit`, `lint`, full 790-test suite green (including 3 repeat isolated runs of the
   perf-flake test from the CI-failure thread below, all clean), `build:web` emits `dist/`.
   Verified visually: `boundingBox()` on the rendered number cell read exactly 40×40; screenshot
   confirmed visibly tighter still than the 48 version, with `+`/`=` still centred.
6. `ARCHITECTURE.md` §1.2's `nodeHeight`/`mathAxisOffset` rows, the §8.2 `SNAP_VERTICAL` note
   (now numerically *larger* than `nodeHeight`, not just a stale ratio), and §16 decision #18
   updated in the same commit.

### Findings

**A fixture value that happens to equal a floored/derived quantity for unrelated reasons can
make a geometry test pass by cancellation, not by correctness — and the cancellation has a
threshold that silently flips.** `snapping.test.ts`'s vacated-slot test used a single-digit `c`
not because the test cared about `c`'s width, but incidentally it floored to `tokens.nodeHeight`
just like the dragged node did; the resulting gap-to-chain-end formula
(`DETACH_DISTANCE - 1.5 × nodeHeight`) held for two different `nodeHeight` values (64, 48) by
comfortable-then-exact margins before failing at the third (40). Passing tests at two prior
values were not evidence the geometry was `nodeHeight`-independent — the margin was shrinking
monotonically each time and nobody had computed where it would cross zero. When a token this
central changes again, re-derive (don't just re-run) any test whose fixture reuses that token's
value for an unrelated node, and prefer fixture values chosen to be *stable* against the token
(here: a wide member whose width comes from digit count, not the floor) over values that happen
to work at the current setting.

### Knowledge revisions

None — consistent with the prior two follow-ups today: overdue geometric debt surfacing under a
token change, not a wrong belief.
