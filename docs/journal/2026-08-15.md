## Cell numeral font too big and too heavy

### Session log

1. User reported the font in the cell was too big and asked for it to be reduced and no
   longer bold.
2. Traced it to `glyphTextStyle` (`src/nodes/Cell.tsx`), the single shared text style every
   glyph cell renders through (`NumberNode`, `OperatorNode`, `EqualsNode`, `ParenNode`,
   `ReferenceNode`, `ResultNode` all import it) — reading `tokens.numeralFontSize` (30) and
   `tokens.numeralFontWeight` ('800'). One token change covers every cell kind.
3. Reduced `numeralFontSize` to 22 and `numeralFontWeight` to `'400'` in `src/ui/tokens.ts`.
   These were the §1.2 reference-image-sampled values (30 = 127px reference glyph, ratio
   0.496, at the reference's own 800 weight) — this is a deliberate departure from that
   sampled geometry, recorded as decision #18 in `ARCHITECTURE.md` §16.
4. `src/chains/measure.ts`'s `widthOf` reads `tokens.numeralFontSize` for its default
   `fontSize` argument and `GLYPH_WIDTH_AT_BASE_SIZE` scales relative to
   `BASE_FONT_SIZE = tokens.numeralFontSize`, so cell width tracks the new size
   automatically — no separate change needed there. Updated its header comment's "weight
   800" mention to 400; left the fixed per-glyph pixel table alone since it was already
   documented as a first guess to be calibrated against real rendering, not exact for either
   weight.
5. Ran the full verification set: `tsc --noEmit` clean, `lint` clean, all 790 tests green
   (`measure.test.ts`'s error-vs-numeral-width inequality still holds — different font sizes
   still produce different widths), `build:web` emits `dist/`. Confirmed visually: built the
   web target, served it, and screenshotted a live `123 + 456 = 579` chain via Playwright —
   the numerals read noticeably smaller and unbolded against the cell, `+`/`=` glyphs
   unaffected since they render through fixed-width symbol cells.
6. Updated `ARCHITECTURE.md` §1.2's token table (`numeralFontSize` row) and §16's decisions
   log in the same commit as the code change.

### Findings

None beyond what's already documented in `measure.ts` about the glyph-width table being a
first guess.

### Knowledge revisions

None — this is a design-token tuning change, not a corrected belief. The reference-image
sampling in §1.2 wasn't wrong about the reference; it's now knowingly not being followed for

## Cell padding still read as excessive after the font shrink

### Session log

1. User asked to also reduce the cell padding, as a follow-up to the font-size session above.
2. Before touching `tokens.numberPaddingX`, checked why a smaller glyph alone left visible
   extra whitespace: `widthOf` (`src/chains/measure.ts`) sizes number/result/reference cells
   as `measureTextWidth(text, fontSize) + 2 * numberPaddingX`, and `measureTextWidth` scales
   `GLYPH_WIDTH_AT_BASE_SIZE`'s fixed dp table by `fontSize / BASE_FONT_SIZE`. Every call site
   in the app uses the default `fontSize = tokens.numeralFontSize`, and `BASE_FONT_SIZE` is
   also `tokens.numeralFontSize` — the same token read twice — so that scale factor is `1`
   for any value the token holds. The glyph-width table's absolute dp numbers, not the token,
   are what actually drive cell width; changing `numeralFontSize` alone shrinks the rendered
   glyph but leaves the pill exactly the size it was before.
3. This means step 4 of the font-size session above was wrong to say cell sizing "tracks the
   new size automatically" — it doesn't, and that's precisely why the box now had visibly more
   room around a smaller glyph than before. Recorded as a revision below rather than editing
   that earlier claim.
4. Fixed by re-deriving `GLYPH_WIDTH_AT_BASE_SIZE`'s four entries from the original 30/800
   calibration (18/8/13/9), scaled by the 22/30 size ratio: digit 18→13, narrow 8→6, sign
   13→10, space 9→7. Left a comment on `BASE_FONT_SIZE` explaining the self-cancelling
   read so the next token change doesn't repeat this.
5. Reduced `tokens.numberPaddingX` from 12 to 8 (also ratio-scaled down from the reference,
   alongside `numeralFontSize`/`numeralFontWeight` in decision #18 — folded into the same
   decisions-log row rather than adding a new one).
6. Verified: `tsc --noEmit` and `lint` clean; full suite green except
   `snapSearch.profile.test.ts`'s cached-hash-vs-linear timing assertion, which failed once
   under the parallel test-runner's CPU contention (received 4ms against a ≤2.05ms budget) and
   passed clean in isolation and on a full re-run — a known class of flake for that file, not
   caused by this change (`numberPaddingX`/glyph widths never touch spatial-hash code).
   `build:web` emits `dist/`. Confirmed visually via the same Playwright screenshot method as
   the font-size session: the `123 + 456 = 579` chain's number/result cells are now visibly
   tighter around the digits, not just smaller-fonted inside the same box.
7. Updated `ARCHITECTURE.md` §1.2's `numberPaddingX` row and folded the `measure.ts` fix into
   decision #18 in §16, in the same commit as the code.

### Findings

**A "scale by `current / base`" ratio where both sides read the same live token is not a
scale — it's always 1, whatever the token holds.** `BASE_FONT_SIZE = tokens.numeralFontSize`
and `widthOf`'s default `fontSize` argument is also `tokens.numeralFontSize`; every ordinary
call therefore computes `tokens.numeralFontSize / tokens.numeralFontSize`. The fixed
`GLYPH_WIDTH_AT_BASE_SIZE` table is calibrated to whatever the token's value *was* when the
numbers were last hand-derived, and only actually changes when someone edits the table itself
— the token's own value does not propagate into it. Only P7's future "adjustable text size"
feature (which was always meant to pass a *different* explicit `fontSize` than the token) would
ever see this ratio move. The misleading symptom: `tsc`, lint, and all 790 tests stayed green
through the original font-size change, because nothing in the test suite asserts cell width
against an independent expectation — `measure.test.ts`'s width tests compare `widthOf` outputs
against `widthOf`/`measureTextWidth` computed the same way, so they can't catch the table
itself being stale.

### Knowledge revisions

**1. `numeralFontSize` changing was believed to reflow number-cell width automatically; it
does not.**
*Previously believed (this same file, font-size session, step 4):* "`widthOf` reads
`tokens.numeralFontSize` for its default `fontSize` argument and `GLYPH_WIDTH_AT_BASE_SIZE`
scales relative to `BASE_FONT_SIZE = tokens.numeralFontSize`, so cell width tracks the new
size automatically."
*Now known:* `BASE_FONT_SIZE` and the default `fontSize` argument are the same token read
twice, so the scale factor is always 1 on the default call path; only the fixed
`GLYPH_WIDTH_AT_BASE_SIZE` dp table drives number/result/reference cell width, and it has to
be hand-recalibrated whenever `numeralFontSize` changes. The original font-size commit shrank
the rendered glyph but left every number cell exactly as wide as before — the "padding" the
user then asked to reduce was substantially this gap, not just `numberPaddingX`.
*What established it:* reading `sumGlyphWidths`/`BASE_FONT_SIZE` in `measure.ts` after the
user's follow-up request, and confirming with the before/after Playwright screenshots that
cell width only actually changed once the table was re-derived.
*Standing lesson:* a "self-scaling" constant defined from the same live value it's meant to
scale against is a no-op in disguise; when a design token drives a derived fixed table (not a
live formula), changing the token does not change the table — grep for every place a token
feeds a *cached*/*hand-written* value, not just a live computation, before claiming a token
change "propagates automatically."
