## `()` moved into the accent column; `Add components` and `Notes` placeholders

### Session log

1. Follow-up request: move `()` from the number-editing row to sit underneath the `+` operator
   (i.e. into the accent column, between `+` and `=`), and use its vacated number-editing-row
   slot plus one more new slot for two placeholder buttons — `Add components`
   (`squares-plus` glyph) and `Notes` (`pencil-square` glyph) — both sharing `Create link`'s blue
   fill. Behaviour for the two new buttons was explicitly deferred ("I'll tell you details of
   these buttons later").
2. `()` now renders via the generic `Key` component inside `accentColumn`, with a new
   `parenAccentKey` style override (`height: 44, marginHorizontal: 0, marginBottom: KEY_GAP`) so
   it stacks flush with `OperatorKey`/`EqualsKey` rather than inheriting `key`'s narrower
   horizontal margin. Kept its neutral grey fill rather than picking up accent amber — it is
   structural (opens/closes a group), not an operator — and its `disabled` rule is unchanged
   (`numberEditingKeysDisabled`, off while an operator is selected).
3. `Add components` and `Notes` follow the codebase's existing "declared, not yet functional"
   convention (the context menu's `Copy`, the canvas menu's `Add number` / `Add graph`): rendered
   always-disabled, no `onPress`. `KeyProps.onPress` had to become optional to allow that —
   previously every `Key` required a real handler; `ModeKey` already had this as an optional prop
   for exactly the same reason, so this brings `Key` in line with that existing precedent rather
   than inventing a new one. Recorded the two buttons in `DEVELOPMENT_PLAN.md`'s "Deferred beyond
   v1" list so a later session doesn't have to rediscover why two disabled buttons with icons
   exist without wondering whether wiring them up is expected of it.
4. Writing the regression test for `()`'s new position caught a real, pre-existing test-hygiene
   bug: `Keypad.test.tsx`'s `beforeEach` reset `selectedNodeId`, `editingNodeId`, and
   `groupSelectedIds` but never `allSelected`. The "disabled while Select all is active" test
   (added yesterday, in the `Create link` describe block) leaves `allSelected: true` in the
   store; every test after it inherited that leftover state. Nothing between that test and today
   asserted a data-entry key was *enabled* with a fresh, empty selection, so the gap stayed
   invisible until my new `()`-position test tried exactly that and got `disabled: true` instead
   of `false`. Fixed by adding `allSelected: false` to the `beforeEach` reset.
5. Verified live: rebuilt and served the web target, drove it with the same headless-Chromium
   session. Screenshot showed what looked like a bare `0` glyph where `()` should be — reading a
   small, blurry parenthesis pair as a zero at that resolution — so cross-checked with a direct
   DOM text-content query on `keypad-paren` rather than trusting the screenshot alone; it read
   `"()"`, confirming the glyph was correct and the screenshot was just misleading at that
   render size. `Add components` / `Notes` render with their icons, `Create link`'s blue, and the
   same faded-disabled treatment as any other disabled key.

### Findings

**A screenshot can visually misrepresent a short, thin glyph at small render sizes — verify
suspicious-looking text against the DOM, not just the pixels.** `()` at `neutralKeyLabel`'s
18px/400-weight rendered compact enough in a compressed PNG to read as a bare `0` on first look.
Querying `element.textContent()` directly settled it in one call rather than guessing from a
zoomed crop.

### Knowledge revisions

**1. `Keypad.test.tsx`'s `beforeEach` didn't reset every ephemeral UI flag it depended on.**
*Previously believed (implicitly, by every test in the file up to yesterday):* resetting
`selectedNodeId`, `editingNodeId`, `groupSelectedIds`, `clearConfirmVisible`, and the document was
a complete reset of the state these tests care about.
*Now known:* `allSelected` is also read by every data-entry `disabled` computation
(`dataEntryLocked = allSelected`) and was never included, so a test that calls `selectAll()`
leaks `true` into every test that runs after it in the same file until something calls
`selectAll`'s inverse or the flag is reset. No test happened to need a fresh `false` there until
today.
*What established it:* a new test asserting `()` was enabled with nothing selected failed with
`disabled: true`; tracing it to `useUiStore`'s stale `allSelected` from the prior test file
section.
*Standing lesson:* when a `beforeEach` enumerates fields to reset, treat it as needing to cover
every field the code under test reads, not just the ones today's new test happens to touch —
listing fields individually (rather than replacing the whole store slice) is exactly the shape of
reset that silently rots as the store gains fields.

## `/prpreview` comment command for `deploy-pr-preview.yml`

### Session log

1. User asked whether the manual `Deploy PR preview` workflow could be triggered by writing
   a comment on the PR (`@prpreview`-style), instead of always going through the Actions tab.
2. Added an `issue_comment: [created]` trigger to `deploy-pr-preview.yml` alongside the
   existing `workflow_dispatch` and `pull_request: closed` triggers. `determine`'s `if` now
   gates the comment path on three things: the comment is on a PR (`issue_comment` fires for
   plain issues too), the commenter has write access (`author_association` in
   `OWNER`/`MEMBER`/`COLLABORATOR`), and the body starts with `/prpreview`. A comment failing
   any of those is a silent no-op; one that passes gets a 👀 reaction so the commenter has
   visible confirmation.
3. Chose `/prpreview` / `/prpreview remove` over an `@prpreview` mention: a literal `@` name
   reads as a GitHub user/team mention and would notify a nonexistent account, where `/` is
   the established slash-command convention other PR bots use.
4. Caught and fixed a script-injection risk before pushing: the first draft interpolated
   `${{ github.event.comment.body }}` directly into a `run:` bash block to parse the
   `remove`/`deploy` argument. That's the documented GitHub Actions injection vector — a
   comment body containing backticks or `$(...)` would execute inside the runner's shell,
   and `author_association` gates who can *trigger* the job, not what's safe to interpolate
   into a script once it runs. Fixed by passing the body through `env: COMMENT_BODY` and
   reading `$COMMENT_BODY` instead, which the shell treats as inert data.
5. Updated `README.md`'s PR-previews paragraph and `docs/WORKFLOWS.md`'s workflow #3
   section to describe the comment trigger, and reworded the preview-deployed PR comment
   (posted by the `deploy` job) to mention `/prpreview` / `/prpreview remove` instead of
   "re-running this workflow."

### Findings

**Interpolating `${{ github.event.* }}` text directly into a `run:` shell block is unsafe
even behind a permission check.** `author_association` filtering (`OWNER`/`MEMBER`/
`COLLABORATOR`) controls who can cause the job to run at all — it says nothing about what
characters are safe to splice into a bash script once it does. The two are independent
concerns: the fix for untrusted-content-in-a-script is always routing the value through
`env:` and referencing it as a shell variable (`$COMMENT_BODY`), never string-interpolating
it into the script body, regardless of who's allowed to trigger the job.

### Knowledge revisions

None — no prior belief here to overturn; this is new surface area, not a correction.

## `()` and decimal/`+/-` recoloured to match their neighbours

### Session log

1. Third follow-up on the same keypad rework: give `()` the same fill as the other operator
   keys, and give decimal / `+/-` the same fill as the number keys.
2. `()` switched from the generic `Key` component (neutral grey, via the now-removed
   `parenAccentKey` style) to `OperatorKey` outright — it already renders the exact amber
   `rolePalette.operator.fill` + white label every other accent-column key uses, so reusing
   the component was simpler and more consistent than adding a colour override to `Key`.
3. Decimal / `+/-` stay on the generic `Key` component (they still need `label`, not an
   `OperatorKey`'s fixed styling) but `gridEditingKey` gained `backgroundColor:
   rolePalette.number.fill`, and `Key` gained an optional `labelStyle` prop (mirroring the
   `style` prop added two sessions ago) so their glyph could switch to `keyLabel` — literally
   the same white/20px/400-weight style `DigitKey` already uses for `0` — rather than the
   default dark `neutralKeyLabel`, which would have read poorly against teal.
4. Verified live: rebuilt and served the web target. Screenshot shows the bottom digit row
   (`. 0 +/-`) as one unbroken teal band, and `()` sitting amber alongside `÷ × − +` in the
   accent column.
5. Added colour-locking tests (`Keypad.test.tsx`): reused `../nodes/testUtils`'s
   `findHostByTestID` (this file's own `findByTestID` resolves to the `Key`/`OperatorKey`
   *composite* — useful for `disabled`/`onPress`/`label`, but its `.props.style` is only
   whatever `style` prop *we* passed at the call site, not the merged, rendered style; asserting
   the actual paint colour needs the host node) to check `keypad-paren`'s fill equals
   `keypad-op-add`'s, and `keypad-decimal`/`keypad-sign`'s fill equals `keypad-digit-0`'s (and
   is explicitly *not* the operator amber, to catch a future edit accidentally leaving them on
   the wrong role fill).

### Findings

**This file's `findByTestID` helper resolves to the composite component, not the rendered
host — fine for props you passed in, wrong for asserting computed style.** Probed with
`findAllByProps`/`findByProps` directly: `testID` (and other shared props) appear on several
instances along the render chain for a single on-screen key (`Key`/`OperatorKey` composite →
`TouchableOpacity` → `Animated(View)` → host `View`), and `renderer.root.findByProps({testID})`
resolves to the *shallowest* of those — the composite — rather than throwing on the ambiguity.
`.props.style` there is literally the `style` value the JSX passed to that composite (an object,
or `undefined` if none was passed), not the three-way-merged array/flattened object the host
`View` actually paints with. `../nodes/testUtils`'s `findHostByTestID` (filters to
`typeof instance.type === 'string'`) reaches that host and gets the real, already-flattened
style object instead.
